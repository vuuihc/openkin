# Kin mobile (iOS)

A Capacitor shell that runs **the Hub's own console**. There is no second UI to
keep in step: `mobile/` adds a native iOS project around the console in
`../ui`, and at runtime the app loads the console from the Hub.

That last part is the design decision worth knowing. The console signs in with a
cookie, and a cookie is only first-party when the page came from the origin that
set it. Loading the Hub's URL directly makes the webview that origin, so login,
`/api` calls, and the SSE/long-poll sync all behave exactly as they do in a
browser. A bundled copy of the console still ships inside the app as a starting
point, but the Hub's copy is what runs. (The Electron desktop shell works the
same way.)

## Build it

Set the origin your Hub is reachable at and build. The origin is baked in at
sync time, so the app is per-deployment: rebuild to point it somewhere else.

```bash
cd mobile
KIN_HUB_URL=https://kin.example.com npm run build:ios          # simulator
KIN_HUB_URL=https://kin.example.com npm run build:ios:device   # device (needs a team)
```

`scripts/build-ios.sh` builds the console first, syncs the native project, and
then runs `xcodebuild`. The device build signs with the team in the Xcode
project (`DEVELOPMENT_TEAM`), creating the provisioning profile on the way.

```bash
npm run open     # Xcode, to run from the IDE
npm run sync     # re-copy web assets + plugins after a console change
```

For a Hub on the LAN over plain http (`kin serve --lan`), pass
`KIN_HUB_URL=http://192.168.1.20:7777`; the config enables cleartext for http
origins so iOS does not block it.

## Ship it to TestFlight

```bash
KIN_HUB_URL=https://kin.example.com scripts/release-ios.sh
KIN_HUB_URL=https://kin.example.com scripts/release-ios.sh --archive-only
```

Archives, exports for App Store Connect, and uploads. Points to a real origin
on purpose: a TestFlight build lives for 90 days, so baking in a quick-tunnel
URL (or localhost) means the app is dead before the build is. The script refuses
those. Each upload needs a build number nothing has used, so the default is a
UTC minute timestamp; `KIN_BUILD_NUMBER` overrides it.

Two things it cannot do for you: the app record has to exist in App Store
Connect first (Xcode's Organizer can create it; the command line cannot), and
the Mac has to be signed in to the Apple ID that owns the team.

## Notes

- **The webview is edge to edge on purpose.** `ios.contentInset` is `never` and
  `ios.backgroundColor` is the console's dark page colour. The console already
  asks for the whole screen (`viewport-fit=cover`) and pads itself with
  `env(safe-area-inset-*)`, so letting UIKit inset the scroll view as well
  applied the safe area twice; the strip left over was the webview's own
  background, which is the system's — white on a light-mode phone — and read as
  a white bar above and below the page. Cases in `ui/src/design/tokens.test.ts`
  keep the native background and the launch colour equal to `--kin-page`.
- **Delete the app once when moving from the SwiftUI build.** iOS persists the
  `UISceneSession`, and a session created by the pre-Capacitor SwiftUI app keeps
  `SwiftUI.AppSceneDelegate` even after the update — the shell then launches to
  a black window with no view. Uninstalling the old app clears the session; the
  next install is fine.
- **First build may fail fetching the Swift package.** Xcode resolves
  `capacitor-swift-pm` over git; on a machine where git cannot reach GitHub
  directly, the error names a cache directory that does not exist.
  `scripts/build-ios.sh` seeds that mirror with a plain `git clone --mirror`
  before building, which is what gets past it. On Xcode 26 the scripts also
  pass `-scmProvider system`; on Xcode 16+ they pass
  `-packageAuthorizationProvider netrc`. Without them `xcodebuild` can stop
  at "Resolve Package Graph" indefinitely — once when git is wrapped by a
  credential helper or a proxy, and once when package resolution reaches for
  a keychain prompt that a non-interactive build cannot answer.
- `ios/App/App/public/` and `ios/App/App/capacitor.config.json` are generated by
  `npm run sync` and are not committed. The latter holds the baked Hub origin.
- The app icon comes from `desktop/scripts/gen-icons.mjs`, which draws the same
  artwork for the macOS app and the phone, and writes
  `ios/App/App/Assets.xcassets/AppIcon.appiconset/AppIcon-1024.png` (opaque,
  edge to edge — iOS draws the rounded corners itself). Run it from `desktop/`
  after changing the glyph. The launch screen is a plain view in the page
  colour, not an image, so a cold start goes dark straight into the console
  instead of flashing Capacitor's white splash.
- Backgrounding the app kills the event stream. On resume the console notices,
  reconnects, and catches up from its cursor — that is the same path a dropped
  network takes, so there is no mobile-specific sync code here.
