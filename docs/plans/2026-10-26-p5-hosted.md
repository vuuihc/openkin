## 1. 现状实测

### 1.1 隔离机制已经完整，缺的是「门」

不是绿地。树里已经有：

| 件 | 位置 |
|---|---|
| 账号 / 身份 / 会话 / 引导令牌四张表 | `internal/store/migrate.go:127`（`migrationIdentityTables`） |
| 角色 `owner` / `member` | `store/identity.go:24-25`；`normalizeRole` 失败时**落到 member**（`:402`） |
| 唯一的授权判据 | `store/task_scope.go:27` `ScopeForPrincipal` |
| 「谁持有这台机器」 | `store/task_scope.go:51` `ActsForHolder` = 同一个判据换个方向读 |
| 两道门 | `operatorOnly`（`api/api.go:538`）/ `holderOnly`（`api/api.go:680`） |
| 逐行判据 | `taskInScope`（`api/api.go:715`）、`gateOnTaskOwner`（`api/api.go:646`） |

`TaskScope` 零值**匹配不了任何行**（`task_scope.go:55-56`、`:78`），方向是**故意**的：
handler 忘了设 scope 会得到一个空列表（看得见的 bug），而不是全 daemon 的任务（泄漏）。

**而且它盖住的是整棵子树，不是一两个 handler。** `api/api.go:352-355`：

```go
// Everything that names one task goes through taskInScope. Scoping only
// the list would leave the id as a way around it.
r.Route("/api/tasks/{id}", func(r chi.Router) {
    r.Use(s.taskInScope)
```

`taskInScope`（`api/api.go:715`，说明在 `:704`）取行、`scope.Matches(t)`、不匹配回
**404**（不是 403 —— 不泄漏存在性），且 id 为空时**拒绝而不是放行**。workspace 的文件读写
（`/workspaces/{workspace_id}/file`、`/workspace/file`、`/source/file`）都在这棵子树里。
本文下面那条洞**不是**「这条路由漏了 scope」—— 它盖住了。

### 1.2 但第二个账号**不可能存在**

`users` 行只有两个来源，都通向同一个函数 `Service.claim`（`internal/auth/service.go:195`）：

- `POST /api/auth/bootstrap`（路由 `api/api.go:269`）→ `ClaimWithPassword`
- OIDC 首次登录 → `ClaimWithIdentity`（`service.go:172`）—— **非测试代码里没有任何调用者**

而 `claim` 的第一件事就是：

```go
needs, err := s.NeedsBootstrap(ctx)   // CountUsers == 0
if !needs { return Session{}, ErrRegistrationClosed }   // service.go:202
```

`ErrRegistrationClosed = "auth: this hub already has an owner"`（`service.go:39`），
面向前端的两处映射在 `api/auth.go:331`（人读的句子）与 `:352`（机器读的 code
`registration_closed`）。**所以一台 Hub 永远只能有一个账号，就是 owner。**
角色 `member` 在代码里存在、在数据里从不产生。

顺带一条 S1 会用到的：前端已经有一条**类型化的错误码**通道
（`ui/src/lib/accountGate.ts:13` 的 `"claim_code_invalid"` 那一族，
经 `authErrorText`（`:44`）查 `account.errors.${code}`），
所以 `join` 模式的失败不需要新造展示方式，加 code 就行。

### 1.3 真正的洞：`cwd` 没有收口，收口收到了**请求者自己选的**那个根上

先把对的部分说清楚，因为它们决定了修法有多小：

- **拥有者是从 principal 盖的，不是从 body 读的**（`api/api.go:942`）：

  ```go
  // Fill the owner from the authenticated principal, never from the body: a
  // client that could name its own owner could write a task into someone
  // else's list, or hide one from its own.
  if p, ok := remote.PrincipalFromContext(r.Context()); ok {
      req.OwnerUserID = p.UserID
  }
  ```

- **文件读的收口是真的**（`api/workspace.go:94`、`:102`，两次：字面一次、解完 symlink 再一次）：

  ```go
  if !pathWithinRoot(e.Root, candidate) { ... }
  ```

  `pathWithinRoot` 在 `:119`，而 `e.Root` 就是这条任务的 `EffectiveCwd()`（`workspace.go:180`）。

问题在于**这个根是请求者自己填的**。`Engine.Create` 里对 `cwd` 的全部校验是
（`internal/task/engine.go:1403`，函数在 `:1398`）：

```go
if req.Cwd == "" {
    return store.Task{}, fmt.Errorf("cwd is required")
}
```

`engine.go` 全文里 `filepath.Abs` / `filepath.Clean` / `IsAbs` **零命中**（实测 0）——
创建路径上没有任何路径规范化，更没有 containment。本机执行时另有一个 `os.Stat`
（`workspace/probe.go`），但它只回答「这个路径在**这台**机器上存在吗」，
不回答「这个主体**有资格**用它吗」。

于是完整链条是：

1. member `POST /api/tasks {cwd: "/Users/owner", ...}` → 接受；
2. 任务盖的是 member 自己的 `owner_user_id` → 它**确实是** member 的任务；
3. `taskInScope` 匹配通过（合法：这就是他的任务）；
4. `GET /api/tasks/{id}/workspaces/.../file?path=.ssh/id_rsa` → `pathWithinRoot` 也通过
   （`e.Root` 就是 `/Users/owner`）。

**每一道检查都在正确工作，而结果是持有人整台机器可读。** 这是本片 §1.2 那扇门打开之后
**唯一**挡在验收标准前面的东西，也是为什么计划原文把「member 的 `cwd` 收口」和「注册入口」
并列交付 —— 原作者看对了。

写那条路是 `operatorOnly`（`api/api.go:367` 一带），读不是 —— 但读有 `taskInScope`，
所以**写出不去**；出得去的只是**读**，而读的就是第 4 步那台机器上的文件。

修法因此很小：**在创建路径上给非 holder 的 principal 加一条 cwd containment**，
其余一道都不用动。

### 1.4 Node 侧的收口是真的，而且已经写成了「一份规则，两处读」

`internal/node/roots.go` 是这条规则的**唯一**实现：

```go
// internal/node/roots.go:57
func (rs rootSet) contains(path string) bool {
	target, err := resolvePath(path)      // EvalSymlinks
	if err != nil { return false }        // 不存在的路径不在任何 root 里
	return withinRoots(target, rs.resolved())
}

// internal/node/roots.go:70 —— 分段比较，不是字符串前缀
func withinRoots(resolved string, roots []string) bool {
	for _, root := range roots {
		if resolved == root || strings.HasPrefix(resolved, root+string(filepath.Separator)) {
			return true
		}
	}
	return false
}
```

`rootSet`（`:17`）的注释把**为什么只有一份**写死了：Executor 在跑一轮前问它、
Responder 在回答一个目录问题时问它，**两者答得不一样不是小 bug** ——
「列表说可以、派发说不可以」等于把人送到一堵墙上。所以 `responder.go:340`、`:439`
与 `executor.go:339` 读的是同一个函数。**这是本片该抄的形状。**

roots 从哪来：`workRoots`（`internal/server/node.go:264`）= checkout root
＋ `nodeRoots`（`node.go:158`，即 `st.ProjectRoots(ctx)` ＋ `--root`），
注释明写「The list returned here is what the hello advertises and what a console offers」；
它同时喂给 `node.Responder`（`server/server.go:621`）与 `node.Executor`（`:942-947`），
后者的注释是这句话的 Node 版：

> The same list the console reads and the Hub is told about: what this machine
> offers to work in is what it will accept work in.

**Hub 侧不做拒绝。** 派发给设备的任务，Hub 拿 cwd 去比对该设备上报的 roots 只为了
**找一个 anchor**：`internal/task/anchors.go:58` 走
`store.MatchDeviceRoot`（`store/workspace_anchor.go:496`），匹配不上就 `return ""`
（`anchors.go:59-62`）—— 没有 anchor，任务照常派出去。所以「这台设备根目录之外的路径」
不是被拒绝的，只是没有 anchor 可挂。**判据存在，但用在了错的地方。**

### 1.6 「持有人」在树里有**两个**判据，而且它们**故意**不同

这一条决定了 §2.2 用哪个，所以单独写。

| 判据 | 位置 | master | device | owner | member |
|---|---|---|---|---|---|
| `ActsForHolder` / `ScopeForPrincipal` | `store/task_scope.go:27,51` | ✅ | ✅ | ✅ | ❌ |
| `isOperator` | `api/api.go:550` | ✅ | **❌** | ✅ | ❌ |

`isOperator` 的注释把理由写死了：

> Two qualify. … The role is read from the account record, so an account whose role is
> missing or unrecognized **falls through to the denial below**.

**这不是 `task_scope.go` 警告的那种漂移。** 那句警告说的是「同一个问题在两个地方回答」；
这里是**两个不同的问题**：

- `ActsForHolder` 答「**它能看见什么**」（任务、项目、例程、产物、会话）—— 设备算持有人，
  因为「a phone is enrolled by the holder and is a full client of the machine, not a guest」；
- `isOperator` 答「**它能重配这台 daemon 吗**」（写文件、建项目、导入会话、配对）——
  设备不算，因为它只是客户端。

两者的缝被 `canQueryGitHub`（`api/api.go:573`，说明从 `:555` 起）显式缝合，注释里有一句
直接相关：

> **Members stay refused. A member is another person on this node, not one of the
> owner's devices.**

**P5 要用的是 `ActsForHolder`**，理由是设备凭证**只能由 operator 铸**
（`POST /api/pairing/sessions` 本身是 operator-gated），所以设备按构造就是持有人自己的
客户端 —— 与 §1.7 的假设同源。

用 `isOperator` 会把**手机**挡在外面：手机上没法开原生目录对话框去选 Hub 那台机器的目录，
于是 `cwd` 收口一旦按 `isOperator` 判，用户「只用手机 dogfood」这个**主目标**就直接受损。
这是本片最容易搞错的一处，写在这里免得下一个人「顺手统一」这两个判据。

### 1.7 设备配对与 `devices.owner_user_id`

`devices.owner_user_id` 存在（`migrate.go:59`，索引 `:71`），**被读、从不被写**：
所有 `INSERT/UPDATE devices` 都没有这一列（`store/device_registry.go`、`store/devices.go`）。

`task_scope.go:23-26` 已经把 P5 要付的账写在那里了：

> A device is unscoped because pairing is operatorOnly, so a device credential is minted by the
> machine's holder and acts for them. **When members can pair their own devices this has to read
> the enrolling account's role instead of assuming it**; devices.owner_user_id already exists to
> carry that.

也就是说：**只要 member 不能配对设备，这个假设就仍然成立**；一旦能，`ScopeForPrincipal`
必须改成读配对账号的角色。这是 P5 自己开出来的洞，必须同一片里处理掉。

### 1.8 跨设备会话同步：今天两边都不通

- Hub 列出会话读的是**数据库**（`store/agent_sessions.go:226`），写库只有导入接口
  （`api/agent_sessions.go:192`，`operatorOnly`）。
- 导入扫的是**本进程的 $HOME**：`adapter/claudecode/plugin.go`、`codex/plugin.go`、
  `droid/plugin.go` 里全是 `os.UserHomeDir()`。**那条路上没有设备参数。**
- 落库统一盖 **Hub 自己的 device id**：`fromAgentSession(session, s.DesktopID)`
  （`api/agent_sessions.go:246`）。
- Node 的线协议**没有会话目录这一类帧**：Hello 只报 `workspace_roots` + `max_concurrent`
  （`node/conn.go:148`），`internal/remote/worker/*.go` 里没有 session 消息。

所以「点亮跨设备会话同步」= 新增一条 Hub→Node 的目录查询 + 按 Node 的设备 id 落库。
这正是 P4 里那条「产地 ≠ 执行设备」的路径第一次变得可达的地方 —— **P4 的单测就是它的验收**。

## 2. 目标形状

### 2.1 门：持有人发邀请，被邀请人自己开账号

`claim` 的形状本来就是对的（`code + user + buildIdentity + meta`，角色在唯一一处设置），
所以不重写它，**加一条旁边**：

- 新表 `invite_tokens`（形状照 `bootstrap_tokens`：`token_hash` PK / `created_at` /
  `expires_at` / `used_at`），**不复用 `bootstrap_tokens`**：那张表的语义是
  「这台 Hub 还没有主人」，而 `BootstrapCodeActive`（`auth/service.go:133`）驱动着前端的
  「认领 / 登录」二选一（`ui/src/lib/accountGate.ts:32` 的
  `gateFor` = `account.needsBootstrap ? "claim" : "login"`）。
  **一张待用的邀请会让第一个访客看到「认领这台 Hub」。**
- `Service.IssueInvite(ctx)` / `Service.RedeemInvite(ctx, code, email, password, name, meta)`，
  后者建 `RoleMember` 的账号，**不经过 `NeedsBootstrap`**。
- `POST /api/auth/invite`（`operatorOnly`，返回一次性的明文邀请码）与
  `POST /api/auth/join`（未认证）。
- 控制台：`ui/src/components/AccountScreen.tsx:20` 的 `type Mode = "claim" | "login"`
  加第三个 `"join"`（该组件已经到处按 mode 分支，加一个分支是它现成的形状）；
  入口是 URL 上的 `?invite=CODE`，照 `bootstrapTokenFromURL()`
  （`ui/src/api/client.ts:156`，在 `ui/src/main.tsx:27` 被调）已有的先例。

**为什么是邀请制而不是开放注册**：Hub 可能挂在公网隧道后面（`--funnel`），开放注册
等于把令牌铸造权交给任何能打开这个 URL 的人。邀请制把门交给持有人，且与既有的
「首次认领要一个终端里打出来的码」是同一个形状。

### 2.2 `cwd` 收口：member 只能选持有人策展过的目录

判据落在**引擎**，不是 API —— 因为 MCP（`mcp/server.go:263`）和 A2A（`a2a/server.go:211`）
也走 `Engine.Create`，写在 API 层就是三处各写一份，而这是 P3b 反复咬到的形状。

**但「加一个 `CreateRequest` 字段、三处各盖一次」是错的形状。** 三个面确实都在盖
`OwnerUserID`（REST `api/api.go:942`、MCP `mcp/server.go:263`、A2A `a2a/server.go:211`），
但那是**身份**；收口要的是**身份背后的角色**。给 `CreateRequest` 加一个 `Role` 或
`AllowedRoots` 字段，就多出三个「记得盖」的地方，而这个字段的零值必须同时满足两件
互斥的事：既不能默认为 holder（忘了盖就是洞），又不能默认为 member（现有一大批直接构造
`CreateRequest` 的测试和内部调用全红）。**一个忘了盖就漏、且选不出安全零值的字段，不该加。**

正确的形状是**从已有的可信输入推出来**。`OwnerUserID` 已经是三个面从 principal 盖的、
引擎已经在收（`engine.go:1517`），那就用**它**去问一次角色：

```
role   := <查 users[req.OwnerUserID].Role>        // users 今天只有 1 行；create 路径一次查询
holder := store.ActsForHolder(remote.Principal{
    Kind: remote.PrincipalUser, Role: role, UserID: req.OwnerUserID,
})
```

这样：

- **不引入新的可信输入**，所以不产生新的「哪个面忘了盖」。
- **判定仍然只有一处**。`task_scope.go` 写着：两个地方回答「谁持有这台机器」，
  其中一个是泄漏。引擎里**绝不能**写第二个 `role == "owner"` —— 构造 principal 去调
  `ActsForHolder`（`task_scope.go:51`，它就是 `ScopeForPrincipal(p).All`），复用它。
  **注意用 `ActsForHolder` 而不是 `isOperator`** —— 两者故意不同，理由和后果见 §1.6；
  用错那个会当场削弱手机。
- **零值自动安全，且不炸测试**：`OwnerUserID` 为空 = 还没有账号的单机 daemon
  = 没有第二个人可防，不设限。这不是洞：无主任务按 `task_scope.go:20-22` 明写的教义
  **本来就属于持有人**，member 的 `OwnedBy` 也匹配不到它 ——
  所以「某个面忘了盖 owner」是自败，不是可利用。
- **查不到的用户 → 当成非 holder 收口**（fail-closed），与 `TaskScope` 零值同一个方向。

规则：**非 holder 创建任务时，`cwd` 必须落在一个已有 project root 之下。**
「已有 project」是持有人策展的（创建 project 是 `operatorOnly`，§1.5），所以这条既满足计划
原文的「白名单 / 只能选已有 project」，又不需要新造一个白名单实体。
数据来源是现成的：`store.ProjectRoots(ctx)`（`store/projects.go:180`），
`nodeRoots`（`server/node.go:158`）已经在用它。

实现细节（都是踩过的形状，`internal/node/roots.go` 已经写对了一遍，抄它）：
- **先规范化再比**：两侧都做 `EvalSymlinks`（`roots.go:38` 的 `resolved()` 就是这么做的）。
- **空 roots 返回 false** —— 空声明不等于「哪儿都行」。
- **比路径分段，不是字符串前缀**：`/Users/owner2` 不能匹配 `/Users/owner`。
  抄 `withinRoots`（`roots.go:70-77`）的 `== root || HasPrefix(root+separator)`。
- **`os.Stat` 不能当判据**（§1.3）：它答「存不存在」，不答「准不准用」。
- 判据放在 `Engine.Create` 里 `req.Cwd == ""` 那条的**旁边**（`engine.go:1403`），同一个出口。
- **拒绝的文案要能读懂**：说清「只能选已登记的项目目录」，不是一句 "invalid cwd"。

要一起处理的入口：
- `Engine.Create`（REST / MCP / A2A / 例程都过这里）
- `POST /api/agent-sessions/{id}/attach`（`api/agent_sessions.go:358-360` 从 body 取 cwd，
  取不到时回落到会话行的 cwd —— 但它自己也走 `Engine.Create`，引擎里那一条同时盖住它）
- `store.RecentCwds`（`store/store.go:1770`）—— 见 §6 未决；它今天跨 owner 聚合
  （`api/api.go:397` 是 `holderOnly`，所以 member 根本调不到），但 member 的目录选择器要显示
  什么需要一并定
- **派发给设备的任务**：Hub 今天也不拿 cwd 比对那台设备上报的 roots（§1.4）。
  这条**不在本片**（它是 device 面，不是 member 面），但记进 §6 —— 同一个判据将来该复用

### 2.3 设备配对：把假设钉住，而不是默默依赖它

`ScopeForPrincipal` 里 device → `Unscoped()` 的理由是「配对是 operatorOnly」（§1.7）。
P5 有两条路可走：

- **(a) 保持配对 operatorOnly**：member 用控制台，不配对设备。`ScopeForPrincipal` 不用改，
  但要**加一条测试钉住这个不变量**（member 伪造的配对请求必须被拒），否则下一个人放开配对时
  不会知道这里有个假设。
- **(b) 允许 member 配对**：`ScopeForPrincipal` 改成读 `devices.owner_user_id`，
  配对时写入该列。

本片选 **(a)**：它是「member 看不到持有人任何东西」的充分条件，且不做无谓扩张。
(b) 的账记进 §6，`devices.owner_user_id` 留着。

### 2.4 跨设备会话同步

Hub→Node 一条查询（沿用既有 worker query 机制，`node.Queries` / `askDeviceResult`），
Node 扫自己的 `$HOME` 返回目录，Hub 按 **Node 的 device id** 落 `agent_sessions` 行。
落库之后：手机控制台能看到 Mac 上的 Claude Code 会话，attach 出来的是一个
「产地 = Mac、执行设备 = 这台」的任务 —— **P4 的 S2/S3 就是为这一刻写的**。

**这一片比前两片加起来大**，而且它改的是线协议，所以单独成片、单独一个 commit 序列。

### 2.5 明确不做

- 不改 `ScopeForPrincipal` 的 device 分支（§2.3 选 a）。
- 不给 projects 加 owner 列（那会把「策展」变成「每人一套」，是另一个产品）。
- 不做开放注册。
- 不动 `kin_messages` / transcript 语义。
- 不给 member 开终端（它已经是 `loopbackOnly` + `operatorOnly`）。

## 4. 守卫

1. **member 读不到持有人的文件**：S2 的判据 + 一条端到端测试 —— member 建任务指向持有人目录
   必须被拒；这是验收标准的原话。
2. **member 看不到持有人的任务**：今天已经成立（`TaskScope`），加一条回归测试防止 S1 把角色写错。
3. **owner 与手机不受影响**：S2 的收口用 `ActsForHolder`（§1.6），所以
   owner / master / **device** 的创建行为逐字不变。必须有一条**设备**的对照 ——
   只测 owner 不够，因为用错判据（`isOperator`）时 owner 那一条照样绿，红的只有设备那条。
   这是本片最该有的一条对照：**「修好了」和「把手机锁死了」在只测 owner 的测试里长得一样。**
4. **邀请码一次性**：用过即废（`used_at`），过期即废。
5. **认证门不放松**：`/api/auth/join` 是新的未认证路由，必须只吃邀请码，且不能顺带建 owner。
6. **收紧方向**：`ScopeForPrincipal` 的零值语义不能被 S1 改坏（S1 只加角色，不改判据）。
7. **两个判据不被「顺手统一」**：`ActsForHolder` 与 `isOperator` 故意不同（§1.6）。
   加一条测试把差别钉住（设备：看得见、但不是 operator），否则下一个人会觉得那是重复代码。

## 6. 风险与未决

| 项 | 说明 |
|---|---|
| S4 改线协议 | Hub 与 Node 的版本可能不一致（用户的 Mac 与 NAS 上跑的是旧二进制）。查询要能被旧 Node 拒绝得体面，而不是挂住 |
| member 的 recent cwds | 收口之后 member 能选什么？`RecentCwds`（`store/store.go:1770`）今天跨 owner。倾向：member 只看到自己的 + project roots，但那要改 `store.RecentCwds` 的签名（多一个 scope 参数） |
| member 能 attach 策展目录里的会话吗 | attach 的 cwd 默认取会话行的 cwd（`api/agent_sessions.go:358-360`），收口之后这条会走判据。策展目录里的会话对 member 可见是否合适，取决于「策展 = 共享」是否成立 |
| `devices.owner_user_id` 仍然不写 | §2.3 选 (a) 的直接后果。留着，等真允许 member 配对时用 |
| `senderOnly`/`holderOnly` 的名单 | S1 之后要复查一遍：新加的角色会不会让某条 `holderOnly` 路由变得该对 member 开放（例如 `/api/agents` 今天任何认证主体可读） |
| commit 里的作者邮箱 | 全仓 633/633 是私人地址。提交时留意 |
| **P4 门禁留下的账（N5）** | `startOne` 的「session not resumed」通知按 **ref** 判，不按「这个 agent 的 resume 机制到底用不用 ref」。托管 transcript 的 agent（`registry.Sessions != nil`，今天只有 kinagent，`internal/adapter/kinagent/plugin.go:89`）靠 `kin_messages` 恢复，根本不读 native ref，却会收到这条通知 —— 对它而言是在报告一次没有发生的拒绝。**今天不可达**（P4 §6：没有路径能产出外地 ref）；**S4 点亮跨设备会话同步的那一刻就可达**，所以 S4 里要把通知条件改成「这个 agent 确实会用这个 ref」 |
