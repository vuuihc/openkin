# P4 — 续接正确性（模型债）

主计划 `2026-10-23-lody-parity.md` §6 P4 的施工文档。交付原话：`tasks.session_ref` →
`(device_id, agent_id, external_ref)` 三元组；7 个 adapter 一次性改到位；跨设备续接语义明确。
验收原话：**在 A 机开始的会话，从 B 机继续，不会静默重开上下文**。

依赖 P0。大小 M。

---

## 1. 现状实测

### 1.1 三元组**已经在树里**了，缺的不是它

主计划把这条写成「单列原生 id 形状不对，换掉」，AD（`docs/adr/0022-hub-node-multi-device-sessions.md`）
D6 也早写明：*native agent session ids are device-scoped … The binding identity is
`(device_id, agent_id, external_ref)`. Crossing devices clears the native session reference and
rebuilds context from Kin's own transcript — the mechanism that already exists for crossing agents.*

实测：三元组**已经建好**，而且比计划假设的更完整。

| 已有 | 位置 | 说明 |
|---|---|---|
| `agent_sessions` 表 | `internal/store/migrate.go:641-658` | `UNIQUE(device_id, agent_id, external_ref)` —— 三元组就是主键语义 |
| 它的注释 | `internal/store/agent_sessions.go:43-50` | 「两台机器各自的 claude-code 有各自的 session id，两边同一个 ref 是两个会话，不是要合并的冲突（ADR 0022 D7）」 |
| 契约测试 | `internal/store/agent_sessions_test.go:275` | `TestAgentSessionIdentityIncludesTheMachine` —— 全树**唯一**一条跨设备身份断言 |
| 任务↔会话绑定 | `task_agent_sessions`（`InsertTaskAgentSession`） | 任务与会话是多对多，带 `role`/`state` |
| 跨 agent 换上下文 | `internal/task/approvals.go:1008` `DetachTaskAgentSessions(…, "cross-agent handoff")` | ADR 说「跨设备复用跨 agent 那套机制」——那套机制**已经在跑** |

**所以这一片的债不是「建三元组」，是：续接路径根本不查它。** 计划里「7 个 adapter 一次性改到位」
这条也要按实测改写 —— 见 §1.4。

### 1.2 续接路径读的是一个没有设备维度的标量

`tasks.session_ref TEXT`（`internal/store/migrate.go:187`，`migration001` 的 `CREATE TABLE tasks`）。
**它没有 `ADD COLUMN` 迁移**（033→034 那一轮补的是 `owner_user_id / origin_device_id /
executing_device_id / workspace_anchor_id / hub_seq`，`migrate.go:2182`）—— 也就是说
`session_ref` 比所有设备概念都老。类型是 `*string`（`store.go:81`）。

续接的闸门只有三条，**没有一条问设备**（`internal/task/approvals.go:924-937`）：

```go
sameAgentResume := !handoff && !interrupted && !orchestrate && !modelSwitch &&
    canResume && fromAgent == targetAgent          // agent 比的是名字
...
sameAgentResume = sameAgentResume && t.SessionRef != nil && *t.SessionRef != ""
```

拿到 spec 的方式同样是裸读（`internal/task/engine.go:2412-2413`）：

```go
sessionRef := ""
if t.SessionRef != nil { sessionRef = *t.SessionRef }
```

而这段在 `if remote {` **之前**，所以远端分支照拿不误；再往下
`internal/node/adapter.go:38-46` 把 `spec.SessionRef` 原样塞进 `worker.Dispatch`，
`internal/remote/worker/turn.go:41-53` 的注释直接写着它是
*"the Node's own reference … opaque to the Hub"*。**一句话：Hub 把一个它自己都读不懂的 ref
转手给了另一台机器，并假定那边读得懂。**

### 1.3 三个具体出口，其中一个是活路径

ref 归属设备与执行设备不一致时，今天的实际后果：

- `claudecode` `--resume <ref>`（`adapter.go:145-146`）、`grok -r <ref>`（`:63-64`）、
  `codex exec resume <ref>`（`:61-63`）—— 三个都是**盲传**，不校验这个 ref 是不是本机的。
- `droid` 只在「找到了但这个会话忙」时 fail closed（`blockedResumeReason`，`adapter.go:313-322`）；
  找不到时冒上来的是 `droid.load_session` 的 JSON-RPC 错误 —— 是报错，不是静默重开。
- `acp` 最危险也最诚实：`session/load` 一个对方没有的 ref，若 agent 没回放内容，只发一条软
  `notice`（`adapter.go:459-468`）——*"session loaded without replay … the next turn may not have
  the earlier context"*。**这条 notice 是全树离「检测到不匹配」最近的东西，而它分不清
  「换了机器」和「agent 选择不回放」。**

**活路径**：`internal/api/agent_sessions.go:315` 用 `GetAgentSessionByID` 取会话行 —— **不带设备过滤**；
`:370` 把 `row.ExternalRef` 塞进 `task.CreateRequest.SessionRef`，而 `req` **不设
`ExecutingDeviceID`**，于是新任务在本机跑。**只要那一行的 `device_id` 是别的机器，本机 adapter
就拿到一个它解析不了的 ref。** 这条路今天就通，不需要等任何未来改动。

> **收尾时的更正（S3 阶段实测）**：上面说的「通」是**代码层**的 —— 这条路确实不按设备过滤。
> 但 §1.6 量到 `agent_sessions.device_id` 今天恒等于 Hub 自己的 id（导入接口只扫本机），
> 所以**没有任何数据能让那一行是别的机器**。结论见 §6 第一行：这条路径的数据侧今天也走不到。

### 1.4 adapter 的账要按实测改口径

计划写「7 个 adapter 一次性改到位」。实测是：**续接 ref 只有一个共同入口 `spec.SessionRef`**，
每个 adapter 只是把它翻成自己 CLI 的参数或协议字段。

| adapter | 接受 ref | 形式 | 读哪个字段 |
|---|---|---|---|
| `claudecode` | 是 | `--resume <ref>` | `spec.SessionRef` |
| `codex` | 是 | `codex exec resume <ref> --json` | `spec.SessionRef` |
| `droid` | 是 | JSON-RPC `droid.load_session` 的 `sessionId` | `spec.SessionRef` |
| `grok` | 是 | `-r <ref>` | `spec.SessionRef` |
| `acp` | 是 | `session/load` 的 `SessionID` | `spec.SessionRef` |
| `kinagent` | **否** | 自己管 `kin_messages`，从不读 `spec.SessionRef` | —— |
| `genericcli` | **否** | 未声明 `CapabilityResume`，`:924` 直接短路成 context pack | —— |
| `rawpty` | **否** | 同上（`KIN_ENABLE_RAWPTY=1`，可选） | —— |

**所以 adapter 侧不需要改。** 要改的是**引擎往 `spec.SessionRef` 里放什么**。
把这句话记在这里，是因为计划里的「7 个 adapter」会让下一个人以为有七处要动。

顺带一条实测异常：`kinagent` 声明了 `CapabilityResume`（`kinagent/plugin.go:46`）却从不读
`spec.SessionRef`；它落库的 ref 是合成常量 `kin:<taskID>`（`adapter.go:113`），
result 路径上甚至报字面量 `"kin-loop"`（`loop.go:772`）—— **不带任何身份**。
今天不出事只因为 `approvals.go:928-936` 用 `managedTranscript` 把它单独摘出去了。

### 1.5 写入侧：ref 与「谁产的」从来没一起写过

`tasks.session_ref` 有五个写入点，没有一个记录设备：

1. `store.CreateTask`（`store.go:779`）← `CreateRequest.SessionRef`（`engine.go:1379-1380`）
2. `TaskPatch.SessionRef`（`store.go:943-947`）
3. `TaskPatch.ClearSessionRef` —— 注释就写着 *"sets session_ref NULL (handoff across agents)"*
4. **绕过 store 的裸 SQL**：`internal/store/retry.go:399` 的 `session_ref = NULL`
5. 实时轮次事件：`engine.go:2685-2690`（`task_started`）与 `:2704-2710`（`result`）

第 5 条是关键。两处都是**无条件**写：

```go
_ = e.store.UpdateTask(ctx, id, store.TaskPatch{SessionRef: &sid})
e.syncNativeSessionBinding(ctx, id, speaker, sid)   // ← 这个函数会自己判设备
```

`syncNativeSessionBinding`（`engine.go:1591-1609`）第一件事就是
`if e.isRemoteDevice(t.ExecutingDeviceID) { return }`，注释写得很清楚：
*"A ref a turn reported from another machine belongs to that machine's agent. …
The ref still travels on the task; the machine that owns the session indexes it."*

**判断是对的，只是做晚了一步**：索引不收了，标量照收。于是「ref 还在任务上旅行」这句注释，
在标量这一层变成了「ref 在没有产地标签的情况下继续旅行」。

### 1.6 三元组的设备分量今天恒等于本机

`UpsertAgentSession` 只有两个调用者：`engine.go:1618/1645`（本机，`e.selfDevice()`）和
`api/agent_sessions.go:246`（导入接口）。后者是 `fromAgentSession(session, s.DesktopID)` ——
`ListSessions` 扫的是**本机**已注册 agent 的文件系统，然后统一盖上**本机**的 `DesktopID`。

也就是说 `agent_sessions.device_id` 结构上是对的，**取值上永远是 Hub 自己的 id**：
Hub 从不记录另一台机器发现的会话。所以就算续接路径改去查 `agent_sessions`，它今天也答不出
「这个 ref 是 B 产的」—— **`agent_sessions` 里根本没有 B 的行**。

这条决定了 §2 的形状：产地必须在**写 ref 的那一刻**记下来，而不是事后去 `agent_sessions` 反查。

## 2. 目标形状

### 2.1 ref 和它的产地必须同时写下

在 `tasks` 上补一列 `session_ref_device_id TEXT`，与 `session_ref` **同一个 patch、同一时刻**写。

不选「改去查 `agent_sessions` 反查产地」，理由是 §1.6：远端产的 ref 在本机**没有行**，
反查会把「B 产的」和「谁都没产」混成同一个答案 —— 而这两种情况的正确处置不同
（前者要重建上下文并说明，后者本来就该冷启动）。

补上这一列之后，`tasks` 行自己就带着完整三元组：`executing_device_id`（设备）+ `agent`（agent）
+ `session_ref`（external ref），另加 `session_ref_device_id` 说明 ref 的产地。
`agent_sessions` 保持它现在的角色 —— 本机会话目录，不承担产地说明的职责。

### 2.2 跨设备 = 走跨 agent 那条已有的路

ADR 0022 D6 已经定了处置：**清掉原生 ref，用 Kin 自己的 transcript 重建上下文**。
这条路今天就在跑（换 agent 时），要复用的正是它：`ClearSessionRef` + `handoffContext`
造 context pack + `DetachTaskAgentSessions(…, "cross-agent handoff")`。

所以判据从「agent 名字相同」扩成「**agent 名字相同 且 ref 的产地就是执行设备**」。

### 2.3 不静默：换了机器要说出来

「静默重开上下文」的反面不是「报错」，是**说出来**。跨设备续接是一次正常的、预期内的降级：
用户在两台机器上用同一个任务，本来就该按第二台机器能看见的东西继续。要做的是一句话，
不是一次失败。

这条落在既有的通知/事件通道上（与跨 agent handoff 同一处），并在 §4 里定成守卫。

### 2.4 明确不做

- **不删 `tasks.session_ref`。** ADR 0022 已定它是 compatibility projection（五个 adapter 的入口），
  实测也确认 adapter 侧不需要动（§1.4）。删它要同时改五个 adapter 的入参形状，收益为零。
- **不做「把 B 的会话文件搬到 A」。** ADR 0022 明确拒绝过（Alternatives considered:
  *Copying provider transcripts into Kin for portability*），理由是会复制大文件、且源路径在别处仍不可解析。
- **不做 `agent_sessions` 的跨设备同步。** Hub 不从远端拉会话目录（§1.6）。
  要让 Hub 看见 B 的会话是另一件事（P5 的「跨设备会话同步点亮」），不塞进这一片。

## 3. 切片

### S1 — 产地列与写入

`migrate.go`：`migration001` 的 `CREATE TABLE tasks` 补列 + 一条 upgrade `ADD COLUMN`
（照 033→034 那个循环的写法，老库补空值）。`store.go`：`Task` 加字段、`taskColumns` 加列、
scan 加目标、`TaskPatch` 加 `SessionRefDeviceID *string`。

写入侧三处一起改，**同一个 patch**：
- `engine.go:2685-2690` 与 `:2704-2710` —— 写 `SessionRef` 时同时写产地：
  远端轮次写 `t.ExecutingDeviceID`，本机轮次写 `e.selfDevice()`。
- `CreateTask` 路径 —— `CreateRequest` 带产地（attach 流程 `api/agent_sessions.go:370` 填 `row.DeviceID`）。
- `ClearSessionRef` 与 `retry.go:399` 的裸 SQL —— **清 ref 必须同时清产地**，
  否则会留下一个「有产地、没 ref」的行，读起来像「ref 还在 B 上」。

验收：老库升级后不报错、新列全空；清 ref 的行产地也为空。

### S2 — 续接闸门加设备判据

`approvals.go:924-946`：`sameAgentResume` 追加一条 —— 产地为空（老行，视为本机）或等于执行设备。
不等时走已有的 handoff 分支（`ClearSessionRef` + context pack），并记录原因。

`engine.go:2412`：读 `t.SessionRef` 时同样判一次。**这里不是重复**：`applyFollowUp` 只管
follow-up，而 `Run`/`Create` 路径上的 spec 也要经过同一个出口。两处共用一个判据函数，
不各写一份（这是 P3b 那两轮复查反复咬到的形状）。

### S3 — 说出来

跨设备续接发生时，用既有的通知/事件通道说一句：这个会话原本在另一台机器上，
已按 Kin 自己的 transcript 重建上下文。与跨 agent handoff 用同一处措辞风格。

### S4 — kinagent 的合成 ref 收口

`kinagent` 声明 `CapabilityResume` 却从不读 `spec.SessionRef`，落库的是 `kin:<taskID>`、
result 路径报 `"kin-loop"`（§1.4）。**这不是本片的交付**，是顺手记下的实测异常：
它今天被 `managedTranscript` 单独摘出去，动它要碰 transcript 语义，属于 S1–S3 之外的独立关注点。
本片只把它记进 §6，不改。

## 4. 守卫

1. **产地随 ref 走**：清 ref 必须清产地（S1）。单测：`ClearSessionRef` 后两列都空。
2. **跨设备不静默**：产地 ≠ 执行设备时，`sameAgentResume` 必须为 false（S2）。
   单测直接构造这个任务行断言。
3. **老行按本机算**：产地为空时不改变今天的行为（P4 之前建的任务不能因为升级就丢上下文）。
4. **本机续接不受影响**：产地 == 执行设备时，行为与 P4 之前逐字一致。
   这条要有一条「改之前先变红」的对照 —— 否则「修好了」和「全关了」在测试里长得一样。
5. **engine 出口也判**：S2 的两处共用一个判据函数；单测直接测那个函数，
   避免「页面/引擎各写一份」在 P3b 里出现过的形状。

### 7.1 收尾实测推翻的一条（重要）

本文 §1.3 把 attach 路径记成「今天就通的活路径」。S3 阶段复核发现：**代码层**通（不按设备过滤），
