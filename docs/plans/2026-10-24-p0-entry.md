## 1. 这一层要删掉的那个决定

parity §0 第四条的判据是「这个功能替用户删掉了哪一个**必须坐到电脑前才能做的决定**」。
这一层的答案只剩一句话：

> **手打一个绝对路径。** 手机上你不知道那台机器的目录结构，而 Kin 今天要求你记得它。

验收（parity §6 原文）：**只用手机开两个新会话——一个换到远端机器、进到一个你不能凭记忆
打出路径的目录；一个是从没 clone 过的仓库。全程不碰电脑。**

两条路径的产物是同一个东西：一次 `POST /api/tasks`（`cwd` + `executing_device_id`）。
**这一层不发明新的任务类型，只发明「怎么在手机上把 cwd 填出来」**——这是它敢做得小的原因。

```
新建会话
├── 通用：机器 → 文件夹（浏览）→ 分支
└── 快捷：GitHub → owner/repo → 分支   →  机器上 clone 出来，路径回填
```

**缺陷 1（本次修）：`/api/git/branches` 与 `/api/git/checkout` 不知道机器是谁。**
两者直接拿 `cwd` 去读**本机**文件系统（`internal/api/git.go:29-38`、`:52-58`），

桌面「选远端机器 + 该机器上的 cwd」今天就能走到这里：同一个路径在两台机器上都存在
（那正是 anchor 的前提），于是**分支列表可能来自错误的副本**，而不是报错。
手机流程是第一个**必然**指向另一台机器的调用者，所以它必须先把端点补成有机器概念的。

## 3. 形状：唯一的新机制是「Hub 向 Node 提问」

通道上今天只有两类帧：Hub→Node 的**命令**（`turn.dispatch` / `turn.cancel` /
`approval.decision`）和 Node→Hub 的**报告**（`turn.*` / `approval.request` / `heartbeat`）。
**缺的是一次带答案的提问**——手机在 Hub 上，目录在那台机器上，Hub 不能替它回答。

### 3.1 帧

`internal/remote/worker/protocol.go` 的 `allowedFrameKinds` 是封闭集合，加两个：

| 帧 | 方向 | 载荷 |
|---|---|---|
| `query` | Hub → Node | `{id, method, params}` |
| `query.result` | Node → Hub | `{id, error?, result?}` |

一个信封 + 一个**封闭的方法表**，而不是每种问题一对帧：方法表是一处 switch，
两侧都能一眼读完；帧种类继续封闭，不长的协议不给自己造 N 个几乎相同的分支。

- `id` 由 Hub 生成，进程内唯一（一个计数器，`q-<n>`），两侧都校验（非空、长度上限）。
  待答表的键是 `(device, id)`——device 在键里而不在 id 里，因为 id 本来就撞不上；
  device 进键是为了让「哪台机器的问题」在表里一眼可读。
- `params` / `result` 是 `json.RawMessage`，各自方法的类型在方法表里解码；
  **解不开的参数是错误，不是空值**。
- 未知 method：Node 侧回 `query.result{error}`（有答案比沉默好——沉默会让 Hub 等到超时）。

### 3.2 Hub 侧：待答表 `node.Queries`

```
Ask(ctx, sender, method, params) (json.RawMessage, error)
Route(sender, frame) error      // query.result → 配对
Abandon(sender) []string        // 连接结束：把所有还没答的提问立刻结束
```

- 按 `(device, id)` 存一个 channel；`Ask` 发帧后等，超时/ctx 结束/连接结束都返回错误。
  条目同时记下**这条连接**（`Sender.Generation()`）：`Abandon` 是按连接结算，不是按机器
  ——重连时新 socket 先入表、旧连接的结束后到，窗口期里问到新连接上的问题不能被旧
  socket 的死亡结算掉。`Turns.Abandon` 与 `Approvals.Abandon` 早就是这条规则，`Queries`
  是三个里唯一漏掉的（评审发现，已修 + 红验证）。
- `NewConnections(onEnded)` 已经存在的钩子（`internal/server/server.go:335`）里加一句
  `Abandon`：**连接断了不能让提问挂到超时**——那是一个必然失败的等待。
- 超时按方法给（列目录/列分支 15s；clone 5min）。超时值是一处常量表，不是散落的魔数。
- 同一 device 上的两次提问互不干扰（各有 id），并发提问不需要串行化。

### 3.3 Node 侧：`node.Responder`

```go
type Responder struct {
    Roots        []string  // 与 Executor.Roots 同一份：这台机器同意工作的目录
    CheckoutRoot string    // 这台机器放它 clone 出来的仓库的地方
    Warn         func(format string, args ...any)
}
```

- `OnFrame` 的分派里加一个 case（`internal/server/node.go:265`），与 `approval.*` 并列。
- **每个方法都以这台机器自己的 roots 为界**，containment 判定复用 `Executor.allowedCwd`
  的那套（`filepath.EvalSymlinks` 之后的真路径比较）——抽成一个共用函数，两处调用，
  一处实现。理由与 Executor 上那段注释相同：Hub 是另一方，不能由它来界定自己。
- **写操作的目的地由机器自己推导**。Hub 只说「哪个仓库」，不说「放到哪」——
  Hub 能指定路径就等于 Hub 能在任意 root 里落文件，而 roots 是「可以跑 agent」的许可，
  不是「Hub 可以直接写」的许可。

### 3.4 方法表（v1 + S5）

| 方法 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `fs.list` | `{path}` | `{path, parent, roots[], entries[{name}]}` | 空 `path` = 这台机器的 roots。**只列目录**，不返回文件、大小、内容：这不是通用文件浏览器。目录项按名字排序，上限 500 条 + `truncated`。根之上没有 `parent`（边界可见）。 |
| `repo.branches` | `{repo}` | `{clone_url, default_branch, branches[]}` | `git ls-remote --heads`，不 clone。私有仓库用**那台机器**的 git 凭据。回的是 clone URL 而不是 canonical 名，理由见 §8 的缺陷 1。 |
| `repo.prepare` | `{repo, branch}` | `{path, branch, cloned}` | 目的地 = `<checkout_root>/<host>/<owner>/<repo>`，由 Node 推导。**幂等**：已存在同源 checkout 就 fetch + 切分支，已存在但不是这个仓库就拒绝。目的地加锁，双击不会并发 clone。 |
| `git.branches` | `{path}` | `{cwd, is_git, current?, detached?, dirty?, branches[], reason?}` | 读**那台机器已经有的** checkout。与 `repo.branches` 分开：一个够到网络、用那台机器的凭据，一个只看本地目录；而且「远端有的名字」不等于「这里有的名字」。字段与 `workspace.BranchStatus` 逐个对齐，前端同一个控件画两种答案。 |
| `git.checkout` | `{path, branch}` | `{cwd, current}` | 表里唯一的写，而且落在**人选定的**目录里（不是机器推导出来的），所以边界与一次 dispatch 相同：先 `resolvePath` 再 `withinRoots`。`branch` 过 `argument`（前导 `-` 与控制字符）后才会成为 git 的参数。 |

`repo` 接受 `owner/repo`（GitHub 简写）或完整 URL；规范化复用
`workspace.CanonicalRemote`（`internal/workspace/anchor.go:115`，已经会剥 userinfo——
token 不会随 URL 进日志或库）。

### 3.5 HTTP 面（`holderOnly`）

```
GET  /api/machines/{device}/dirs?path=
GET  /api/machines/{device}/repo/branches?repo=
POST /api/machines/{device}/repo/prepare   {repo, branch}
GET  /api/git/branches?cwd=&device=          # S5：无 device / self / 本机 id = 本机
POST /api/git/checkout {cwd, branch, device} # S5
```

- `{device}` 取 `self` 或本机 `desktop_id` 时走**本地分支**（Hub 自己也是一台机器：
  手机浏览 Hub 的目录同样要能用）。`fs.list` / `repo.*` 的本地分支就是
  `LocalMachine` 那个 responder——和 Node 上跑的是同一份代码；两个 `git.*` 路由不是，
  它们直接调 `s.Workspace`（见下一条），这是有意的差别，不是漏接线。
- 不在线的机器：`409` + 「机器离线」；未知/已吊销：`400`（复用 `ValidateExecutingDevice`
  的判定口径）。
- 门槛是 `holderOnly`（`internal/api/api.go:629`）：配对手机是这台机器的完全客户端，
  访客账号不是。
- **两个 `git.*` 路由是旧的 `/api/git/*`，不是 `/api/machines/{device}/*`**：它们是
  桌面早就有的分支控件，S5 只是给它加了一台机器。无 `device` 时语义与改动前逐字相同
  （直接走 `s.Workspace`，不受 roots 限制）——桌面在原生对话框里选的目录未必是
  project root，加限制会让它退化。
- `git.checkout` 的路径门槛从 `operatorOnly` 降到 `holderOnly`，但**本机那一支在
  handler 里仍然要求 `isOperator`**：换掉本机的 checkout 是在动操作者自己会话所在的
  目录，而换掉**别的机器**的 checkout 由那台机器的 roots 兜底——那正是配对存在的意义。
  路由守卫读不到 body，所以这条规则只能在 body 读出来之后判。

### 3.6 不改的东西（重要）

- **不加表、不加任务字段、不动 engine**。
- 远端任务在 Hub 侧仍是 **shared 工作区**：`engine.go:1343-1364` 明确拒绝
  「远端 + worktree」，并写明「它的工作区就是那台机器自己的 checkout」。
  所以这一层的会话**跑在那台机器的一个真实目录里**（已有的 checkout，或刚 clone 出来的
  那一个），不是每任务隔离的 worktree。
  - 已知限制：同一仓库的第二个手机会话落在**同一个 clone**（两个会话互相看得见改动）。
  - 远端隔离 = 让 Node 拥有 workspace 层（generation / worktree / 清理），
    那是独立的一层，且是 **P0b（publish 需要分支）的前置**——在那一层单独设计，
    不在这里顺手做半个。

### 3.7 checkout root

`--checkout-root`（默认 `<stateDir>/checkouts`，取 `off` 关闭）是这台机器放 clone 的目录，
**它进入这台机器上报的 roots**——否则 `Executor.allowedCwd` 会拒绝在那里跑会话。

这是一次**有意**的边界放宽：Hub 从此能让这台机器 clone 一个它选的仓库并在里面跑 agent。
收窄它的方式写在这里，也写在启动日志里：

- 放宽的只有这一个目录，且由这台机器的操作者命名；
- `--checkout-root=off` 时快捷路径直接拒绝（`repo.prepare` 报「这台机器没有 checkout 目录」）；
- 派发回合仍然过 `AllowYOLO`（`internal/node/executor.go:143`）那道闸。

## 4. UI 形状

**规则**：桌面 + 本机 → 原生对话框（**一行不改**）；其余（手机、浏览器、远端机器）→ 浏览。

- `CwdPicker` 增加浏览模式：当前路径 + 子目录列表（点进去）+ 上一级 + roots 快捷入口，
  手打输入框**保留**（浏览是给人用的，手打是给记得路径的人的逃生口）。
- 快捷路径是同一个入口的第二档：`owner/repo` + 分支 → `repo.prepare` → 用返回的 path 建任务。
  分支来自 `repo.branches`（先选仓库再选分支，顺序与 LODY 一致）。
- 所有文案进 i18n（中英同改）；手机宽度（390×844）实测。

## 6. 不做

- 不做通用文件浏览器（只列目录；不读文件内容、大小、mtime）。
- 不做「列出你的 GitHub 仓库」（v1 手输 `owner/repo`；列表需要账号级凭据，见 §2.7 边界）。
- 不做远端的每任务隔离与清理（§3.6）。
- 不动桌面原生目录对话框，不改本机 `--root` 语义。

## 7. 风险与未验证

- **真实验收在手机上**，而手机连的是你 NAS 上那个 Hub：这份代码要跑到那里才算数。
  本机能验证的等价路径：**本机起一个 Hub + 本机 Node 走真实 ws 通道**，
  再用手机宽度（390×844）的浏览器把两条路径各开一个会话。NAS 的部署不在本次自动授权里。
- 私有仓库 clone 依赖那台机器上 `gh`/git 的凭据状态；本机当前**没有**可用的 GitHub 凭据
  （见 P0 实测），所以 S3 的私有仓库分支只能靠单元测试覆盖，实机走公开仓库。
- 无独立评审：本环境所有 subagent 都走 Codex 网关，而它 429（配额耗尽）。
  每个切片以自审 + 红测试顶替，残余风险写在这里。

### 2026-10-26 真机入口的断点：控制台经 Relay 打开是一张白屏（打开这一下已修；刷新与 PWA 仍未修）

去走真实链路时撞上的，不是读代码读出来的：把 `relay.pairing_url` 拿 390×844 的无头浏览器
打开——HTML 是 **200**（1,282 字节，与 `web/dist/index.html` 逐字节相同），但它引用的两个资源
全是 **400**，页面文本为空、localStorage 为空。**手机在这个入口上看到的就是白屏。**

- **为什么 400**：Worker 的 `fetch` 对**每一个**请求都要求 `room`
  （`relay/relay.js`：`if (!room || room.length > 128) return json({error:"room is required"}, 400)`），
  `proxyHTTP` 再要求 `key` 等于房间里那把。文档**自己的 URL** 带着这两个参数，
  文档**里面写的** `/assets/index-*.js`、`/assets/index-*.css`、`/manifest.webmanifest`、`/icons/*`
  不带——浏览器不会替子资源继承父文档的查询串。
- **影响面不止"某个入口"**：`ui.base_url` 本身就是那个 Relay 地址（设置页「通知」一节写着
  「深链使用 ui.base_url」），推送落点 `<ui.base_url>/inbox?focus=<id>` 也落在它上面。
  也就是说「手机上点开这条通知」这条产品自己写下来的路径，今天通向白屏。
- **修在哪**：`internal/remote/relay`（daemon 侧的桥）在转发 HTML 时，把根绝对引用改写成
  带上自己 room/key 的形式。选桥而不是 Worker，因为 Worker 的改动要动用户自己的 Cloudflare
  部署才生效，而桥的改动在 daemon 里，落地即生效、回滚即还原。
- **为什么可以改字节**：桥的 `newLocalRequest` 剥掉 `accept-encoding`（`isHopHeader`），
  Go transport 自己协商 gzip 并透明解压，响应头白名单又不带 `Content-Encoding`——
  到手的 body 一定是 identity 的。改写之后 `ETag`/`Last-Modified` 必须丢掉：它们描述的是
  改写**前**的字节。
- **证据（三条独立）**：
  1. **表驱动**（`TestRewriteDocumentLeavesWhatItCannotRoute`）：该改的改（script / stylesheet /
     manifest / 自己带查询串的用 `&` 接），不该碰的不碰（`//host`、外部 `https://`、`#frag`、
     相对路径、已经带过凭据的 → 幂等）。
  2. **真实响应路径**（`TestRelayResponseRewritesTheConsoleDocument`）：走 `relayResponse`，
     `text/html` 那次断言改写 + 验证器被丢，JSON 那次断言**一个字节不动**且 `ETag` 保留。
  3. **出货文档**（`TestShippedConsoleHasNoReferenceTheRelayCannotRoute`）：把
     `web/dist/index.html` 从 embed 里读出来、经真实响应路径、断言**每一条**根绝对引用都带上了
     room/key。扫描器（`absoluteRefs`）是**独立**按字节写的，不复用实现用的那条正则——
     用被测表达式当判据，只能证明它和自己一致。输入与输出都先断言引用数非 0，否则这条测试会空过。
     断言用 `url.Parse` 而不是子串：**凭据必须落在 query 里**，且 path 与 fragment 与改写前一致。
- **评审抓出来的真缺陷：凭据被写进 fragment**（同一模型 subagent，68 次工具调用）。原实现把
  `?room=…&key=…` 追加在**整个属性值的末尾**，于是 `/icons/icon-512.png#v=2` 变成
  `…png#v=2?room=…&key=…`——fragment 对浏览器是不透明的，实际请求仍是 `/icons/icon-512.png`
  且**不带查询串**，Worker 照样 400。出货文档今天没有带 fragment 的引用，所以这是**修得不全**
  而不是回归；但**判据本身看不见它**：原来的 `strings.Contains(value, "room=")` 对埋在 fragment
  里的凭据一样为真。评审在 scratch 副本里往 `index.html` 加了一条带 fragment 的引用，

### 2026-10-26 手机四件事：真起了会话，四面都走到了（390×844，经真 Worker）

上一节两条"没验"的根因是**手上没有真实数据**（没有 pending、没有改动）。这一轮补上了：在
一个**一次性 scratch 仓库**（独立 git repo，不在任何真实工作树里）起会话，让改动只落在那儿。

| 面 | 结果 |
|---|---|
| **发起对话** | ✅ 从手机建起 3 个会话：填提示词 → 选权限/机器/主持/模型 → 发。落点 `/tasks/<id>`，1.6s 跳转。**工作区路径也能改**（面板里 `工作区 → 编辑`，输入框写路径，**失焦才提交**——不失焦直接点「好了」会丢掉这次编辑） |
| **看进度** | ✅ 运行态、流式分段、用量摘要都在。provider 挂掉时逐条显示 `reconnecting 1/5…2/5…`，最后给出终态 + 「重试」。**失败路径是清楚可读的**，不是白屏 |
| **批准权限** | ✅ 端到端走通：worker `claude-code` 要 `Write` 一个文件 → 手机上出现「需要权限 · 来自 worker claude-code · Write · <path> · + world」，收件箱角标 +1 → 点**「批准」** → 会话继续跑完，文件真的写出来了，pending 归零 |

#### 新发现：经 Relay 打不开 diff 预览——懒加载 chunk 不带凭证

上一轮修的 bridge 重写只覆盖**服务端发出的 HTML 里那 5 个引用**
（`/assets/index-*.js`、`/assets/index-*.css`、manifest、2 个图标）。
`CodeViewer` 不在其中：它是 `WorkspacePanel.tsx` 里的 `lazy(() => import("./CodeViewer"))`，
chunk URL 由 **Vite 的模块加载器在运行时**拼（`base` + 文件名），**不带 query**，于是被
Worker 挡在门外：

| 同一个资源，两种请求 | 结果 |
|---|---|
| `/assets/CodeViewer-<hash>.css` | **400** `{"error":"room is required"}` |
| 同上 + `?room=…&key=…` | **200** `text/css` |

这不是猜的：在真机页面上用 `fetch` 对同一个 URL 发了两次，对照如上。

**波及面**：控制台里 `lazy()` 只有这一个（`ui/src` 全仓 grep 就一处），所以坏的是**文件/diff
预览**这一块；Monaco 自己的语法 chunk 挂在它后面，同理会一起中招。
首屏、列表、会话、发消息都不受影响——它们在 `index-*.js` 里。

**两条修法，代价不同：**

1. **Worker 记 cookie**（`relay/relay.js`，约 15 行）：带 `room`+`key` 的请求回一个
   `Set-Cookie`，此后同源请求由**浏览器自动带上**。一次修好**懒加载 chunk + 刷新 + PWA 启动**
   三件事。**代价：要重新部署你的 Cloudflare Worker（外部系统，等你一句话）。**
2. **构建期给资源 URL 挂凭证**（`ui/vite.config.ts` 的 `experimental.renderBuiltUrl` + 一个
   运行时 helper 读 localStorage）：只修懒加载 chunk，**不修刷新/PWA**，且是 experimental 钩子。
   好处是不用动外部系统。

推荐 1：刷新、PWA、懒加载是**同一个根因**（浏览器不会把 query 带过文档边界），而 cookie 正好是
浏览器会自动携带的凭证——用它是顺着浏览器的设计走，而不是在每个 URL 生成点打补丁。

#### 这一轮的方法学教训（免得下次再踩）

- **合成 `input` 事件 ≠ 真打字**：给受控 input 直接 set value + 派发 `input/change`，React 状态
  有时收不到，于是"发了但内容是空的"。**用真实按键事件**（browse 的 `type`）才可信。
- **对话框和会话底部是两套 composer**，`document.querySelector('textarea')` 会抓到**对话框后面**
  那个。我因此一度以为"新建对话会追加到旧会话"——那是选择器抓错了元素，**不是产品缺陷**。
- 起真会话会花额度：这一轮用的是 scratch 仓库 + 最短提示词。量到的用量：一个
  `@claude-code` worker 步 ≈ 37.5k in / 525 out。

**没验的**：手机自己的网络往返（上一节那条 0.5s 是这台 Mac 的），真值只能在你的手机上量。
