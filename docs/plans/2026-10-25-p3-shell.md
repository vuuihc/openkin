# P3 — 会话外壳：多标签 + 右侧面板

> 上位计划：`2026-10-23-lody-parity.md` §6「P3」（验收、依赖、大小以那里为准）。
> 上一片：`2026-10-24-p2-session-view.md`（P2，已落地并合入）。
> **本文件的职责**：动手前先写清这一层的正确形状（§10 施工原则），然后是切片、守卫、
> 验证方法与风险。进展记在 §8。

**验收原句**（parity §6 P3）：**同时开 3 个会话**，各自标签之间切换不丢状态；
`Cmd+.` 能一键清屏。

**这一片是桌面片，判据与 P2 不同。** P2 按「手机上不做会怎样」排序（队列第一，因为那是
当时唯一在损坏数据的）。多标签在手机上不是需求——手机用的是会话列表（`SessionsPage`），
标签栏在 390px 上只是多一层壳。所以 P3 按**验收句本身的依赖顺序**排，且：
**任何一步都不许让手机上的现有体验变差**（多标签、zen、面板容器都在桌面断点以上才出现，
或至少在窄屏退化成今天的样子）。

## 1. 现状实测（2026-10-25，全部对着 `feat/p2-session-view` 的树读出来的）

### 1.1 多标签：贵的部分**已经有了**，缺的是两件便宜的事

| 事实 | 出处 |
|---|---|
| 最多 8 个会话**同时挂载**，非活动的用 CSS `hidden` 藏起来，所以切回来时组件状态**原样还在** | `ui/src/pages/TaskSessionHost.tsx:44-57`、`ui/src/lib/sessionCache.ts:4` `MAX_CACHED_SESSIONS = 8` |
| 它挂在 `<Routes>` **外面**，因此切路由不会卸载它 | `ui/src/App.tsx:145` |
| active 会话**已经在 URL 里** | `/tasks/:id`（`ui/src/App.tsx:154`），路径解析见 `ui/src/lib/sessionCache.ts:23-24` |
| 「已打开的会话」这张**表**在组件 state 里，不是持久化的——刷新后只剩一个 | `sessionCache.ts` 全是纯函数（`touchSessionCache` / `dropSessionCache`），数组本体在 `TaskSessionHost` |
| 没有任何标签栏；最像标签栏的东西是**终端自己的**标签栏 | `ui/src/components/terminal/TerminalTabs.tsx:1`（含 `ArrowLeft/ArrowRight` 的 roving focus，`:41-46`）；手机底部那三个是导航，不是会话标签（`ui/src/components/layout/MobileTabBar.tsx:6-9`） |
| 没有分屏 | `grep -rni "split\|side-by-side" ui/src/components ui/src/pages` 只命中 `String.split` 与 `IconPanel` |

**结论**：多标签不是「造一套会话状态机」，而是「给已有的 keep-alive 缓存加一张标签栏 +
把这张表的顺序持久化」。这和 §5「先问正确形状，再决定复用」的结论一致：正确的形状已经在树里了。

### 1.2 右侧面板：五个表面共用一个 z-index，写者有两个

今天 `absolute inset-0 z-40` 这个「满屏表面」的写法有 **5 处**：

| 表面 | 出处 |
|---|---|
| 终端 | `ui/src/components/terminal/TerminalPanel.tsx:237` |
| PR 面板 | `ui/src/components/pr/PullRequestPanel.tsx:218` |
| 发布面板 | `ui/src/components/pr/PublishPanel.tsx:181` |
| 任务页的 files 表面 | `ui/src/pages/TaskDetailPage.tsx:1278` |
| （另外两处是移动端抽屉，不是面板：`layout/Sidebar.tsx:641`、`pages/NewChatPage.tsx:790`） |

而「哪个表面开着」这个状态有**两个写者，在两个组件里**：

- 任务页自己的 `const [overlay, setOverlay] = useState<Overlay>(null)`，`Overlay = "files" | "pr" | "publish" | null`（`ui/src/lib/overlay.ts:16`，用在 `ui/src/pages/TaskDetailPage.tsx:149`）；
- 外壳自己的 `const [terminalOpen, setTerminalOpen] = useState(false)`（`ui/src/components/layout/AppShell.tsx:140`）。

**两者互不知道**：`grep "setOverlay(null)|setTerminalOpen"` 在 `AppShell.tsx` 与
`TaskDetailPage.tsx` 里只命中各自的关闭回调，没有任何交叉关闭。

**这是一个能说清后果的真 bug**（读代码得出，**未实测**——原因见 §7）：桌面端打开一个任务 →
`Ctrl+\`` 开终端 → 在任务页里点开 Files。终端在 `AppShell` 里画在路由**之后**，同 z-index
下它盖住 Files。此时 Files 是「开着但看不见」的状态，它自己的关闭按钮点不到，唯一出路是先关终端。

**还差一块面板**：parity §2.2 要求 `files / changes / pr / terminal` 四块。今天 `files`、`pr`、
`publish` 是 overlay id，**`terminal` 不在那张联合类型里**（它是外壳的另一个 atom），
**`changes` 根本不是面板 id**——它是 files 表面**内部**的一个镜头：
`ui/src/components/workspace/WorkspacePanel.tsx:84` `type SidebarTab = "changes" | "files"`（`:364` 选中）。

### 1.3 终端：已经全套建好了，P3 只是「挪个位置」

- UI：`ui/src/components/terminal/{TerminalPanel,TerminalView,TerminalTabs,TerminalProfileMenu}.tsx`，桌面独占挂载（`AppShell.tsx:533`），开关 `:335` 绑 `Ctrl+\``，可用性 `terminalAvailable={desktop}`（`:547`），`desktop = isKinDesktop()`（`:64`）＝ `!!window.kinDesktop?.isDesktop`（`ui/src/lib/desktop.ts:44-46`）。
- 客户端 API：`ui/src/api/client.ts:2343,2347,2351,2359`。
- Go 侧完整：`internal/api/api.go:492-499` 注册 `GET/POST /api/terminal/sessions`、`DELETE …/{id}`、`GET …/{id}/ws`，在 `loopbackOnly + Auth.Middleware + operatorOnly` 之后；WS 处理在 `internal/api/terminal.go:128`，manager 在 `internal/terminal/manager.go`。

**所以「右侧面板扩到 terminal」是收编，不是新建。** 这是 P3 里最大的一处省钱。
另外 `TerminalPanel` 有个要保留的行为：第一次打开后**保持挂载**（`hasOpened`，
`TerminalPanel.tsx:231`），关闭时用 `hidden` + `aria-hidden={!open}`（`:239-241`），
好让 PTY socket 活过开关——「隐藏」不是「卸载」，收编时不能改成条件卸载。

### 1.4 zen 与命令面板：都是空的

- `Cmd+.` **没有任何绑定**（全树 0 命中），也没有 zen / focus / hide-chrome 这类模式；最近的东西是托盘那个无壳表面（`ui/src/App.tsx:110-126`）。
- 全局键盘只有一处：`ui/src/components/layout/AppShell.tsx:325-343`（`⌘N`、`⌘K`、`Ctrl+\``）；其余都是组件各自的 `document.addEventListener`。
- 命令面板 `ui/src/components/CommandPalette.tsx`，条目在一个 `useMemo` 里**写死**（`:94-171`）：`new` / `inbox` / `tasks` / `artifacts` / `usage` / `settings` 六条 + 一条**条件出现**的 `terminal`（`:159`，靠 `terminalAvailable` 这个 prop 传进来）+ 配方（`:211`）+ 实时任务行（`:228`）。

## 2. 目标形状（先写形状，再写切片）

### 2.1 面板：一张表，一个写者，一块表面

parity §4.2 第 1 条「**一个关注点只有一个写者**」在今天的树里是**被违反的**：
「哪个表面开着」有两个写者（§1.2），「表面长什么样」有五个副本。

正确的形状：

```
PANELS: PanelDescriptor[] = [{ id, titleKey, icon, Component, available(ctx) }, …]
activePanel: PanelId | null        // 唯一写者：外壳
<PanelSurface>                     // 唯一渲染 inset-0 z-40 的地方
```

- **可用性是描述符的一部分**（`available(ctx)`），不是各自的 prop。今天终端要一路把
  `terminalAvailable` 传到命令面板（`AppShell.tsx:547` → `CommandPalette.tsx:159`），
  这正是「写者分散」的症状。
- **`available` 必须是纯函数**（`ctx = { desktop, taskId, hasPr, … }`），这样「哪些面板此刻可用」
  能在没有 DOM 的地方测（§6.1 的同一条理由）。
- 收编顺序按风险从低到高：先 `publish`/`pr`/`files`（本来就在**同一个** `overlay` atom 里，
  搬进表是纯搬运），再 `terminal`（它跨组件，是这次要修的 bug 所在）。
- **只有一块表面**这条要能被守卫抓住（§5），否则下一个人加面板时会再写一个 `z-40`。

### 2.2 标签：**id 是持久的，面板是派生的**

- **持久化的是顺序表**（`kin.sessionTabs.v1`，与 `kin.sessionScroll.v1`、`kin.workspace.sidebarWidth`、
  `kin_terminal_height` 同一条约定），**不持久化任何面板状态**。
- **active 仍然只由 URL 决定**（LODY 也是「URL 持有 active tab」，parity §2.2）。不为 active 再存一份，
  否则就有了两个写者。
- **刷新后按需挂载**：启动时只从持久化的 id 列表画出标签栏，**哪个被点开才挂哪个**
  （`sessionCache` 的 keep-alive 只在本次会话内生效）。这样刷新不会一次开 8 条 SSE 流。
  **明说代价**：刷新后切到一个没挂过的标签，那个会话的界面状态是新的——
  验收句要求的是「**切换**之间不丢状态」，不是「刷新不丢」，这条差异写进 §7。
- 标签栏的键盘行为**复用** `TerminalTabs` 那套 roving focus 的写法（`:41-46`），不发明第二套。
- **拖拽排序**：parity §2.2 说 LODY 有、可拖拽。P3 的验收句里没有它，而指针拖拽在触屏上是
  另一件工作（长按、占位、自动滚动）。**决定：先做键盘可完成的重排（`Alt+←/→` 移动当前标签），
  指针拖拽留给 P3b 与手机一起做**——理由：P3 是桌面片，而唯一必须拖拽的场景（手机上理不清一堵
  标签墙）恰好是 P3b 的场景。这条要写进 §7，不能让「LODY 有」悄悄变成范围。

### 2.3 zen：推导的，不回写偏好

parity §4.2 第 6 条：「**表现状态是推导的，不回写偏好**（zen / compact 从偏好算出，不存）」。
所以 `Cmd+.` 是一个**瞬态**开关，不进 localStorage、不进设置页、不产生偏好键。
「一键清屏」= 隐藏外壳（侧栏、标签栏、右栏、页头），**不隐藏会话本身**；再按一次回来。
守卫：这条「不回写」要能被测（§5），否则半年后会有人给它加一个持久化键。

### 2.4 命令面板：从注册表派生，不再手列

今天面板/导航/终端三处各写一份清单。正确形状是**一个来源**：

- 导航项 ← 路由表（`ui/src/App.tsx:146-168`）；
- 面板项 ← `PANELS`（§2.1），可用性由 `available(ctx)` 决定；
- 会话项 ← 标签顺序表（§2.2）。

这样「新加一个面板，它在命令面板里自动出现」是**结构保证**，而不是记得去改两处。
parity §4.3 里那条「用测试断言没有被任何样例呈现的 token 就是缺口」是同一个想法，
这里落成：**每个面板 id 与每条路由都必须在面板里出现**（§5）。

### 2.5 `files` 与 `changes` 是两块面板还是两个镜头：**未决**（见 §7）

parity §2.2 把 LODY 的右侧面板记成 `files / changes / pr / browser / ios-simulator / side-session`
六块并列，而 Kin 今天是一个表面内的两个镜头（`WorkspacePanel.tsx:84`）。P3 的交付句要求
「扩到 `files / changes / pr / terminal`」——**先要回答这两个词是不是两块面板**。

判据（不是偏好）：**今天有没有东西同时需要「文件树」和「diff」在场**。如果有，它们是两个镜头；
如果没有，它们是两块面板。要量的是 `changedFileFace` / 审批卡的「看改动」入口与
`WorkspacePanel` 的 `openPath` 是否落在同一个「选中文件」状态上。**动手前先量，量完再定**。

## 5. 验证方法

沿用 P2 §6.1（不引入 DOM 环境）。P3 需要的新测量：

1. **3 个标签不丢状态**：夹具里开 3 个会话 → 在 A 里上滚、展开一张工具卡、切到 B、再回 A →
   `$B js` 量 A 的 `scrollTop` 与展开态是否原样。**这是验收句的直接测量**，不是看图。
2. **只有一个表面**：开着 Files 再开终端 → 数 DOM 里 `inset-0 z-40` 的表面数，必须是 1。
   **前置条件**：夹具今天进不了终端（`isKinDesktop()` 在普通 Chromium 里是 false），
   所以夹具要能 stub `window.kinDesktop`（这是夹具的改动，不是产品的）。
3. **zen**：`Cmd+.` 前后量外壳节点数与会话节点数；再量 localStorage 键集合没变。
4. **窄屏不变差**：390×844 下 `documentElement.scrollWidth === 390`（P2 的老验收句），
   且标签栏与 zen 在窄屏的行为是**明确决定过的**，不是碰巧。

## 6. 风险与未决

| 风险 / 未决 | 处置 |
|---|---|
| §1.2 那个覆盖 bug 是**读代码**得出的（终端盖住 Files），**没实测** | 夹具进不了终端：`TerminalPanel` 的可用性来自 `isKinDesktop()`，而夹具是普通 Chromium。**不假装盖住**：S2 的验收就是「只能有一个表面」，那时用 §5 第 2 条量出来。在那之前这条按「已定位、未复现」记 |
| 8 个标签 = 8 份挂载成本（每个 pane 可能各有一条 SSE 订阅与轮询） | keep-alive 的上限今天就是 8。**S5 要量**：8 个 pane 挂满时的订阅数与轮询请求数，然后决定要不要给后台标签降频（桌面片里这可能只是「不需要」，但要有数） |
| 刷新后标签会重新挂载，界面状态不保留 | 有意（§2.2）。验收句要求的是切换之间；这条差异写在这里，dogfood 时若觉得别扭再谈持久化视图状态 |
| 拖拽排序不做（只做键盘重排） | 有意（§2.2）：唯一非拖拽不可的场景在手机上，而那属于 P3b |
| `files` / `changes` 是两块还是一块，**未决** | §2.5 的判据，S3 动手前先量。在这之前不许写表项 |
| zen 的「清屏」到底隐藏什么，容易变成审美争论 | 用 `Cmd+.` 的**可测定义**收敛：外壳节点数为 0、会话节点数不变、再按一次回到原样（§5 第 3 条） |
| `Cmd+.` 在 Electron/系统层是否被占用 | **未核实**：`desktop/` 里没有任何 accelerator / `globalShortcut` / `before-input-event`（全树 0 命中），但壳层是否拦截树外的事测不到。落地时在桌面上按一次即可判定 |
