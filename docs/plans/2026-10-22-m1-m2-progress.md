## 三条铁律（写死，避免走偏）

1. **只有 Hub 分配序号。** Node 从不写自己的事件日志，只上行事件。
2. **秘密不出设备。** provider key、agent 登录凭据永不上行；Hub 只存非敏感能力元数据。
3. **一个会话同时只有一个活跃 turn。**

外加一条本次明确的前提：**不写兼容层**。旧数据、旧行为、旧接口一律直接改；
`tasks.session_ref` 这类"兼容投影"直接换成 `(device_id, agent_id, external_ref)` 三元组，
牵动的 adapter 一次改到位（ADR 0022 结论里"保留 session_ref"那段按此作废）。

**验收口径（照抄设计 §P0-A）：** ① Hub 在 A，浏览器在 A、iOS 在 B；② A 上新建会话并跑完一个 turn；
③ B 无刷新可见，且 `GET /api/tasks/{id}/events` 的 `seq` 连续无洞；④ B 断网 5 分钟后重连靠游标补齐且无重复。

**M1.7 实测怎么做的（2026-10-22）：** 起了一个用完即弃的 Hub（`/tmp/kin-m17`，state dir 独立），
前面套一个自己写的 TCP 转发（`127.0.0.1:7799` → Hub 的 `7800`）。两个独立浏览器标签页都连 7799：
A 页就是"机器 A 上的浏览器"，B 页是"机器 B"。**断网 = 杀掉那个转发**，Hub 本身照常跑，
所以"B 掉线期间 Hub 上还在变"是真的，不是模拟出来的。

| 验收项 | 结果 |
|---|---|
| ① A 建会话，B 不刷新即见 | ✅ B 页 2 秒内出现该会话（走 SSE） |
| ② 完整 turn 的事件 seq | ✅ m17-beta 跑完一个真 turn：18 条事件 `seq 1..18` 无洞；另三个会话 `1..3` / `1..2` 无洞 |
| ③ B 断网后仍然陈旧（证明断的是真网） | ✅ 5 秒内出现"正在重连"横幅；期间 Hub 上新增/删除的三个会话 B 一个都不知道，且**原有行一条没丢** |
| ④ 断网满 5 分钟 → 恢复 → 靠游标补齐 | ✅ 恢复后 B 的会话集合与 Hub **完全一致**（6 条），被删的那条正确消失，无重复行（每个会话在侧栏恰好一行；另加详情页标题链接共 2 个锚点），横幅消失 |

顺带发现并修掉一个真问题：`streamEvents` 原来把"连不上 Hub"也算作"这条网络不能推流"，
两次失败后就永久放弃流，一个睡醒的笔记本从此只能靠 long-poll（不丢数据，但白白多 25 秒延迟）。
现在两种情况分开了——**连不上就继续重试**（这是暂时的），**只有 Hub 收下了请求却一个字节不发**
（CDN 缓冲）才判定为不能推流并永久降级。新增 `ui/src/api/client.stream.test.ts` 三个测试钉住这条策略。

**M1.3 的一处与原设计不同：** 设计文档说"`MAX(hub_seq)+1` 天生单调无洞，不需要额外的序列表"。
这句话漏了**删除**：删掉游标最大的那条会话，它的号会被下一个写入者重用，持有该游标的客户端
就永久看不到那次变更。所以删除时写一行 `task_tombstones`（迁移 035），它既是"这条会话没了"的
通知，也是游标的下界。墓碑永远不清理（一行几十字节），离线再久的客户端也能补齐。

## M2 — 各设备用自己的 agent 干活

目标：手机上发一个任务 → 在装了 agent 的那台桌面机上跑起来 → 过程回到手机 → 能批准/拒绝权限请求。

**内部顺序是硬性的：先用现有 adapter 把链路跑通，再把执行层换成 ACP。**
这样 ACP 出问题时有一个已知可用的对照组，而不是两个新东西同时不确定。

### 四条定死的决定

1. **控制通道是 Node 主动外连 Hub 的 WebSocket**（`GET /api/node`，用设备令牌认证），帧用现有
   `worker.Frame` 信封，按设计 §6.1 补上 `turn.*` 那几个 kind。Node 在 NAT 后面不用开端口；
   以后要挂到 relay 上（P0-E）也不用换协议。
2. **远端执行实现成一个 `adapter.Adapter`**：`Start` 发 `turn.dispatch`，返回的 handle 把
   `turn.event` 帧喂进 `Events()`，`Cancel()` 发 `turn.cancel`。Hub 侧一行引擎代码都不用改——
   这是 D8「一条代码路径」的落法，也让 standalone 与远程走完全相同的下游。
3. **秘密不过线**（D7）：`turn.dispatch` 不带 `ProviderCfg`/API key，Node 用自己的本地配置。
4. **`session_ref` 是设备本地的**：派发时按 `(device_id, agent_id)` 取那一台自己的 ref。
   M1.1 推迟的 `agent_sessions` 唯一键重建，就在这一步一次改到位。

## M2.1 / M2.2 落地细节

### M2.1 的一处结构性更正：Node 角色搬进 daemon

原计划写的是 `kin node --hub …`——一个独立的瘦客户端进程。**这是错的，已改成
`kin serve --hub URL --token TOK`。** 理由：会干活的机器本身就是一个 daemon（有自己的
state dir、自己的 agent registry、自己的 adapter），一个不持有数据库的旁路进程根本起不了
一个 turn；而且两个进程抢一个 `~/.kin` 是自找麻烦。M2.7 的验收口径本来就写着"两个 daemon
（不同 state dir）+ 一个 Hub"，现在代码和它对上了。`kin node` 命令与其解析器已删除，
不留第二条路径。

### M2.2 turn 派发

链路（一次远端 turn 的完整路径）：

```
Hub: POST /api/tasks {executing_device_id: <dev>}
  → engine.startOne：不是本机 ⇒ 用远端 adapter（本机 registry 完全不参与）
  → node.Adapter.Start：Turns.Open(turn_id) + 发 turn.dispatch（**不带 ProviderCfg**）
Node: 收 turn.dispatch
  → Executor：cwd 在自己声明的根里？不在就直接 turn.finish(error)，agent 一次都不启动
  → 起本地 adapter，事件逐条 turn.event 上行（局部 seq 从 1 开始、连续）
Hub: 每条 turn.event 走原有 runLoop → 原有 store.AppendEvent → **Hub 分配 seq**
  → turn.finish(ok) 关闭 handle → 引擎照常收尾
```

关键点：

- **Hub 侧引擎、事件落库、seq 分配、总线、游标、控制台一行没改。** 远端执行就是一个
  `adapter.Adapter`（D8「一条代码路径」），所以远端 turn 在控制台里和本机 turn 长得一模一样。
- **去重与收敛按 `(turn_id, local_seq)`**：重复序号丢弃（重连会重发），**跳号直接终结该 turn**
  并把原因写进 transcript——事件丢了就是丢了，等不回来，留着洞比失败更糟。
- **`Cancel()` 立刻关闭 Hub 侧 handle**，不等设备回话，否则引擎的并发槽会被一个没人跑的 turn
  永久占住（测试抓到的真 bug）。
- **设备身份只认凭据**：`turn.event` 只能投给它所属设备的那条 turn，另一台设备发来的同 id 帧被拒。
- **Node 侧的边界是容器边界**：`cwd` 必须落在这台机器自己声明的根里（本机 `project_roots` +
  `--root`），**没声明就什么都不跑**——空声明不能被读成"哪里都行"。判定发生在拥有文件系统的那台
  机器上，Hub 是另一方可信不过（测试含"只共享前缀的路径"和"相对路径逃逸"）。

**一处顺带修掉的真问题（e2e 测试抓到的）：** `Engine.Create` 用**本机** registry 校验 agent，
于是 Hub 会拒掉它唯一该接受的那类任务——NAS 上的 Hub 一个 agent 都没装，任务全是给笔记本的。
现在改成：任务指向别台设备时，按那台**上报的清单**（`device_agents`）判定；没上报过清单的设备
不判（交给派发去说话）；上报了的就用它的理由拒绝，比如「agent "codex" is not available on
device X: not signed in」。

**一处推迟（同 M1.1，仍记在账上）：** `agent_sessions` 唯一键重建为
`(device_id, agent_id, external_ref)` **不在 M2.2**。远端 turn 的 `syncNativeSessionBinding`
本来就该跳过——Hub 没有、也不该有另一台机器的 `SessionCatalog`/`InspectSession`。远端 turn
正确地不产生 native binding。重建随 M2.3 的按设备路径解析一起做，那时才有 `(device_id,
agent_id) → path/ref` 的解析器可写。

**怎么验的：** `internal/api` 里有一条真链路 e2e——真的 `api.Server` + 真 store + 真引擎
（**本机一个 adapter 都没注册**，本地跑必然失败）、真的 WebSocket、真的 `node.Executor`：
建任务 → 派发 → 对端跑 → 事件落 Hub 库，断言 `seq` 连续无洞、`session_ref`/token/成本都回来了、
两边都没有残留 turn。另外覆盖：越界 cwd 被拒且 agent 没启动、设备不在线、设备上报的 agent 与实际
不符、跑到一半断线必须收敛成 failed 并说明原因、建任务时未知设备 400。

### M2.2 的复审：修掉的问题与记在账上的

高模型子代理复审（1 blocker / 7 major / 8 nit）后逐条修，修完的：

1. **（blocker）Hub 在派发前把远端任务的工作区"准备"了一遍。** `Engine.Create` 原来无条件走
   `workspace.Manager`：它按 Hub 的路径 `stat` 一个只存在于笔记本上的目录，或在 Hub 上切一个
   worktree，于是远端任务在 Hub 侧直接 400，或者带着一份属于 Hub 的工作区元数据上线。
   现在：`executing_device_id` 不是本机时，工作区元数据就是"共享、cwd 即根"，准备动作交给拥有
   文件系统的那台机器。回归测试 `TestRemoteTaskIsNotPreparedOnTheHub`（关掉修复会真的红）。
2. **（major）`agent_sessions` / native binding 写错机器。** `syncNativeSessionBinding` 会把远端 turn
   报上来的 `session_ref` 绑到 Hub 自己的 agent 会话表里。现在远端任务直接跳过（与 M2.3 的重建同一方向）。
3. **（major）权限天花板只是句口号。** 派发进来的 `permission_mode=yolo` 原来照跑。现在机器自己决定：
   没带 `--allow-yolo` 就一直拒，agent 一次都不启动。
4. **（major）cwd 容器边界可被符号链接绕过。** 判定改成解析后的真实路径（`filepath.EvalSymlinks`），
   并要求绝对路径；测试补了符号链接、相对路径、前缀共享、不存在的路径。
5. **（major）turn 关闭与投递竞态会 panic。** 引擎关 handle 与设备帧投递在不同 goroutine 上，
   原来"先查再发"会打到已关闭的 channel，panic 会带走整条控制通道（连同这台机器上所有 turn）。
   现在发送有闸门 + `WaitGroup`，先亮"已关闭"再等发送者退出，最后才关 channel。并发测试跑 100 轮。
6. **（major）重连顶掉旧连接时，旧连接上的 turn 成了孤儿。** Node 侧 turn 的生命周期挂在派发它的那条
   连接上，所以被顶掉的连接的 turn 必须在 Hub 侧一并放弃，否则引擎永远等一个不存在的 socket。
7. **（major）不可解析的事件被吞。** 现在解析失败即终结该 turn 并把原因写进 transcript——序号一旦被
   消费就代表"这条事件收到了"，吞掉它等于用下一个事件盖住一个洞。
8. **（major）吊销的设备仍可被指定。** 建任务时就拒（REST / MCP / 例程三个建任务入口共用同一个校验），
   否则任务会被接受、排队，直到第一次 turn 才失败——正是那段注释说要避免的结果。

**记在账上、本轮不修的**（都不是 blocker/major，写清楚免得以后当成新发现）：

- **一台设备的帧读取会被它自己最慢的 turn 拖住**：上行事件先进每条连接 64 个槽的缓冲，缓冲满了读循环
  就停在那条 turn 上，同一台机器上其它 turn 的事件一起等。真实场景是一台机器同时跑多个 turn 且其中
  一个的消费者卡住；M2.4 做收敛与重连时会连同背压一起处理。
- **重复派发是"忽略"而不是"幂等"**：Hub 重发 `turn.dispatch` 时 Node 只是警告并忽略（不会回一个
  finish 把正在跑的 turn 打死）。真正的 at-least-once 语义（带派发代次、可安全重放）属于 M2.4。
- **一个 turn 属于"设备"，不属于"那条连接"**：设备重连顶掉旧连接时，Hub 放弃的是该设备名下所有
  turn。若在"换连接"的瞬间正好有新 turn 派发到新连接上，它会被一起误杀（窗口极小，且要两个 Node
  进程共用一个凭据才会稳定复现）。正确做法是把 turn 绑在派发它的那条连接上（`Turns.Open` 记住
  sender，路由与放弃都比对 sender）——这属于 M2.4 的收敛与重连。
- **`tasks` 的 `owner_user_id`/`origin_device_id`/`executing_device_id` 没有外键约束**：SQLite 加外键
  要重建表；而且 Hub 自己也是一个合法的 `executing_device_id`，它不一定有 `devices` 行。建任务时的
  校验已经盖住实用场景。
- **控制台里的 git / 终端入口仍按 `task.cwd` 直接调 Hub 的接口**：这些接口收的是裸路径而不是任务 id，
  Hub 无法判断用户指的是自己机器上的 `/code/foo` 还是笔记本上的同名目录。任务作用域的文件接口已经
  改成返回 409（见下），这两类要等 M2.3 的锚点给控制台一个可指定的设备。
- `internal/task` 的 `TestRoutineCompletionNoteworthyPush` 在 `-race` 下偶尔红，是既存问题，与本次无关。

### 已知问题：新二进制第一次启动会卡在钥匙串授权（2026-10-22 实测）

换了二进制路径（`study/kin/kin` → `study/kin-multidevice/kin`）之后，daemon 启动时

### 追根：为什么每次重打包都要重新授权（2026-10-22 晚，已解决）

不是 macOS 脾气怪，是**签发身份丢了**。仓库里本来就有 `scripts/dev-sign.sh`：用固定的
`Apple Development` 证书给 `kin` 签名，让钥匙串 ACL 的 designated requirement 绑在**证书 + identifier**
（`dev.openkin.kin`）上，而不是绑在每次 `go build` 都会变的 ad-hoc cdhash 上。身份从
`.kin-codesign-identity` 读——而这个文件是 **gitignored 的**，所以建 `kin-multidevice` 这个新工作树时
它没有跟过来。于是从新检出打的每一个包都是 ad-hoc 签名，每次重建都等于"一个全新的 App"，
"始终允许"自然每次都失效。

修法就是把这个文件补回新检出（内容与 `~/Workspace/study/kin` 里那份一致：
`Apple Development: SHIHAO ZHU (A28AKNWZB9)`）。补上之后 `make desktop-dev` 一次就过：
`[kin-desktop] daemon ready version=0.0.0-dev pid=5645` → `WS connected` → 主窗口打开，
**没有再弹框**（证书 + identifier 已是这台机器授权过的身份）。
实测确认：`/api/health` ok；带 master token 的 `/api/version` 返回
`{"desktop_id":"desktop-<desktop-id>","desktop_name":"MacBook Pro"}`；`/api/devices` 正常返回；
控制台入口 `/` 与磁盘上的 `web/dist/index.html` 指向同一个 `assets/index-ikuWiKfV.js`（4.4 MB，200）。

**注意**：这只解决了"重复弹框"。`dev-sign.sh` 自己的注释也承认它只是开发便利——
真正该改的还是下面「待办」第 1 条（启动路径不该读密钥库）。

## 跨设备终端：Codex 与 Lody 怎么做的（2026-10-22 调研）

**Codex**（本机 0.157 的 app-server 协议；用 `codex app-server generate-json-schema --experimental` 导出，
逐条读的 schema）：

- 会话 = `thread`，一次执行 = `turn`，两者之下每个动作（消息、命令、文件改动、推理）都是 `item`；
  所有流式输出走**同一条**通知流：`turn/started` → `item/started` → `item/commandExecution/outputDelta`
  → `item/completed` → `turn/completed`。
- 终端就是其中一个 item：`process/spawn` 的原文是"在 app server 所在的那台主机上"起进程，带 PTY 尺寸；
  配套 `process/resizePty` / `writeStdin` / `kill`。**pty 属于跑会话的那台机器，不属于客户端。**
- 重连：`thread/backgroundTerminals/list|terminate|clean`——后台终端挂在 thread 上，客户端重连后能列出来再挂回去；
  另有 `thread/resume`、`thread/read`、`thread/turns/list`、`thread/items/list` 做历史分页。
- 跨机：`environment/add {environmentId, execServerUrl}`（WebSocket，可设连接超时）+ `thread/environment/connected`
  ——一个 thread 可以绑到远端 exec server 上。配对是协议的一等公民：`remoteControl/pairing/start` 返回
  `{pairingCode, manualPairingCode, expiresAt}`，`remoteControl/client/list|revoke` 管客户端。

**Lody**（`~/Workspace/works/Lody`，只读查看）：

- 会话是 Loro CRDT 文档，经它自己的云 API 同步 + E2EE（`packages/loro-streams-rpc`、`packages/e2ee-core`）。
  和我们的选择不同：我们让 Hub 当权威并独占分配 `seq`。
- 终端在 CLI daemon 里（`apps/cli/src/lib/terminal-pty-service.ts`，`@lydell/node-pty`），经**本机 unix socket**
  （`local-terminal-server.ts`）给 Electron 用；打开参数只有 `{sessionId, cols, rows}`。
  即 **Lody 的终端只在本机**，跨机器没做（它有 agent 的 machine target 概念，但没有远端终端）。
- 可借的一条原则（它 spec 里的原话）：多个 machine target 之间"没有回退"——和我们"解析不到就明确失败"一致。

**给我们的结论**：走 Codex 那条路最省。终端输出变成会话流上的 item（和 ADR 0022 D8
"远端执行就是一个 `adapter.Adapter`"同一条原则），pty 归拥有工作区的那台机器，Hub 只转发 + 分配 `seq`，
控制台不需要第二条通道，重连复用现成的游标。**一条安全边界必须先定**：远端终端比派发 turn 的洞更大
——它是不经任何审批通道的交互式 shell，所以必须是 Node 操作者自己的显式开关（如 `--allow-terminal`，
默认关），拒绝时给出理由。这件事排在 M2.3 的设备选择之后。

### 一处结构性更正（针对 M2.1 已提交的做法）
上面 M2.1 那条里原先写的命令是 `kin node --hub …`——**一个独立的瘦客户端进程，这是错的**。
一个会干活的机器本身就是一个 daemon（自己的 state dir、自己的 agent registry、自己的 adapter），
不持有数据库的旁路进程根本起不了 turn，两个进程抢一个 `~/.kin` 也是自找麻烦。所以 Node 角色搬进
daemon：`kin serve --hub URL --token TOK [--root DIR]`，`kin node` 命令与其解析器直接删除，
不留第二条路径。M2.7 的验收口径（"两个 daemon（不同 state dir）+ 一个 Hub"）本来就该这么读。
