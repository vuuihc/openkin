## 三条铁律（写死，避免走偏）

1. **只有 Hub 分配序号。** Node 从不写自己的事件日志，只上行事件。
2. **秘密不出设备。** provider key、agent 登录凭据永不上行；Hub 只存非敏感能力元数据。
3. **一个会话同时只有一个活跃 turn。**

外加一条本次明确的前提：**不写兼容层**。旧数据、旧行为、旧接口一律直接改；
`tasks.session_ref` 这类"兼容投影"直接换成 `(device_id, agent_id, external_ref)` 三元组，
牵动的 adapter 一次改到位（ADR 0022 结论里"保留 session_ref"那段按此作废）。

## Dogfood 部署（2026-10-23 上午，🟢 已跑通）

**跨设备这条线现在真的能用了**：公网打开就是 Hub 控制台，Mac 作为 Node 领活、
在自己机器上跑 `claude`，要权限时问题落到 Hub，人批了才动手。

| 角色 | 在哪 | 怎么起来 |
|---|---|---|
| Hub | NAS `<nas-host>`（192.168.1.42），容器 `openkin-kin-1` | `/volume1/docker/openkin` 下 `docker compose -f docker-compose.dogfood.yml up -d` |
| 公网入口 | Cloudflare 快速隧道，容器 `openkin-tunnel` | `https://random-words.trycloudflare.com` |
| Node | 这台 Mac（`MacBook Pro`，`node-<node-id>`） | `./kin supervise --hub http://192.168.1.42:7777 --token … --root ~/Workspace` |
| 桌面壳 | `/Applications/Kin.app` | 直接打开。它会 attach 到 :7777 上已在跑的 node，不另起 daemon |

验收（真跑过一遍，不是读代码）：Hub 上建任务 → 派给那台 Mac → Mac 上真起了 `claude`
→ Write 工具要权限 → 问题进 Hub 收件箱（`/api/approvals` 里能看到 `tool_use` 和文件路径）
→ 批准 → Mac 上文件真被写出来（`~/Workspace/kin-dogfood-smoke/hello.txt`）→ 任务 `succeeded`。
Hub 重启一次：认领码不变、Node 自己重连、公网照常 200。

**这台 NAS 的两个坑**（跟 Kin 无关，但会让 `docker compose build` 必挂）：

1. `registry-mirrors` 第一面是已停服的 `hub-mirror.c.163.com`，BuildKit 取 `# syntax=` 前端镜像时直接 EOF。
2. 容器 DNS 指向 `192.168.1.10`，那是 fake-ip（返回 `198.18.x.x`），只有走 `192.168.1.10:7893`
   代理才通——所以 `apk` / npm / go 在构建容器里全部超时。

绕法：镜像在 Mac 上造好再 `docker save | ssh nas docker load`，NAS 只负责跑：

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath \
  -ldflags "-s -w -X main.version=dogfood-$(git rev-parse --short HEAD)" -o /tmp/kin-dogfood/kin ./cmd/kin
# runtime 阶段照抄仓库 Dockerfile，但去掉 apk：alpine:3.21 自带 ca-certificates，
# 那一层只多买一个 tzdata，而 daemon 里没有任何 time.LoadLocation
docker build --platform linux/amd64 -t openkin:dogfood /tmp/kin-dogfood
docker save openkin:dogfood | ssh nas 'docker load'
```

要让这台 NAS 原生 build，得改 daemon.json 的 dns/mirrors 并重启 Docker
（会连带重启 gitlab/postgres 那一堆容器），**没做**。

**公网入口现在是临时的**：快速隧道的域名每次重建容器都会变，也没有可用性承诺。
换自己的域名三步：① Cloudflare Zero Trust → 现有那条隧道 → Public Hostname
`kin.<你的域名>` → `http://192.168.1.42:7777`；② `.env` 里 `KIN_DOMAIN` 换成 `kin.<你的域名>`；
③ `docker compose -f docker-compose.dogfood.yml up -d`，然后 `docker rm -f openkin-tunnel`。

**还没做的**：iOS TestFlight —— 见下面「M3」一节，剩下的两件事需要产品所有者出手。
在那之前手机上用 Safari 打开公网地址、加到主屏幕就能用（控制台带 manifest，是 PWA）。
**公网入口仍是临时的**：快速隧道的域名随容器重建而变，TestFlight 之前必须换成自己的域名。

## M3 — 手机上的 Kin（TestFlight dogfood）

目标：**用 TestFlight 装到 iPhone 上，远程操控 NAS 上的 Hub**。已经落地的部分：

### 控制台 IA：机器 → 项目 → 会话

原来的侧栏按「项目」聚合，Agent 是项目里的一个切换维度；问题是**同一台机器上同一个项目
分不出是哪个 agent 在跑，不同机器上的同一个项目又会糊成一行**。现在分三层：
机器（带在线/离线点）→ 项目 → 会话，本机永远排第一，然后在线机器按最近活跃排。
`ui/src/lib/deviceSidebar.ts` 是这一层，`Sidebar.tsx` 只剩渲染。

配套的后端字段：`AgentSession.device_id`（`internal/api/agent_sessions.go` +
`api/openapi.yaml` + 生成的 TS 类型）。**没有这个字段时，导入进来的会话只能按"本机"归类**，
而它们其实可能是别的机器上的 agent 留下的。

复审（与本会话同模型，不是 Codex 网关）：**0 blocker / 1 major / 11 nit**，全部修掉并逐条红验。
那条 major 是 `install-node-service.sh` 不带 PATH——见下。几条值得记的 nit：
- `showMachineLabels` 用 `groups.length + archivedGroups.length > 1` 判断"要不要画机器标题"，
  一台机器同时有活跃和归档项目时会被数两次，于是**单机控制台也会长出一个机器标题**。改成数
  device id 的集合。
- 活跃/归档两个 `DeviceSection` 共用 `device:<id>` 这个折叠键，折了活跃那台会把归档那台也折上。
  键里加 mode。
- 徽章数字数的是这台机器的**全部任务**（含归档），不是这一节真正列出来的行数；归档那一节因此
  会出现「48」压着一行的情况。改成数渲染出来的行。
- 草稿的「New chat」行只按 cwd 匹配，而同一个 cwd 现在可以同时是好几台机器的项目——会**每台机器
  都嵌一行**。改成认准一台。

**残留风险（复审指出，记账）**：会话那一半目前**实际是空转的**——只有拥有数据库的那台机器会
索引会话（`internal/task/engine.go` 跳过远端设备），所以控制台拿到的会话永远带本机身份。
代码是对的，要等跨设备会话同步落地才会亮。

### Mac 上的 node 交给 launchd

`scripts/install-node-service.sh` 写一个 LaunchAgent（`dev.openkin.node`），登录即起、崩了重拉。
**这次实测踩到两个真坑，都不是脚本本身的写法问题：**

1. **launchd 给的 PATH 是 `/usr/bin:/bin:/usr/sbin:/sbin`**，而 `claude` 在 `~/.local/bin`、
   `codex` 在 nvm 下。daemon 只用 `exec.LookPath` 找 agent、没有兜底目录，所以这样起的 node
   **会显示在线、却一个 agent 都认不出来**——看着健康，实际接不了活。修法是把登录 shell 的
   PATH 抓下来写进 plist 的 `EnvironmentVariables`（已实测：日志里 `claude-code` /
   `codex` 都解析到了正确路径）。
2. **node 连不上局域网里的 Hub**：`--hub http://192.168.1.42:7777` 在 launchd 起的进程里
   稳定报 `no route to host`，而同一条 URL 从终端 curl 是 200。macOS 15 起的
   **本地网络访问授权**是按二进制给的，`~/.kin/node/kin` 没被授权，`/usr/bin/curl` 被授权了。
   改成让 node 拨 Hub 的**公网地址**：既绕开这个授权，也顺带解决"人不在同一个局域网"的问题——
   这台 Mac 本来就会到处跑。

顺带对齐了两处：token 落点改成 `<state-dir>/node-token`（**daemon 自己的默认路径**，
见 `internal/server/node.go`，原来脚本写的是 `~/.kin/node/token`，两个文件会各说各话）；
plist 里直接放 argv、不再套 `/bin/sh -c "$(cat …)"`，没有 shell 就没有要转义的东西。

### 定下来的方向（产品所有者拍板，2026-10-23）

- **导航模型：底部 Tab + 列表→详情。** 三个 tab（会话 / 收件箱 / 设置），每个 tab 一个 push 栈。
  现状是"桌面三栏 IA 塞进手机"——hamburger 抽屉里装完整的 机器→项目→会话 树。
  手机上保留这个 IA，但压成**一层列表**：机器做 section header，项目降为行内副标题。
- **设置类控件不常驻。** 执行 / 路由 / 工作区都是"开新会话"才做的决定，看会话时不需要。
  改成新建页一行 44px 摘要，点开才是底部 sheet。
- **审批内联在消息流里**，不必跳去收件箱再跳回来。
- **设计稿用真机尺寸 HTML 可点稿**，不用 Pencil：能直接落成组件，少一道转译。

**M1.1 的一处推迟：** `agent_sessions` 的唯一键改成

**验收口径（照抄设计 §P0-A）：** ① Hub 在 A，浏览器在 A、iOS 在 B；② A 上新建会话并跑完一个 turn；

**M1.7 实测怎么做的（2026-10-22）：** 起了一个用完即弃的 Hub（`/tmp/kin-m17`，state dir 独立），
前面套一个自己写的 TCP 转发（`127.0.0.1:7799` → Hub 的 `7800`）。两个独立浏览器标签页都连 7799：
A 页就是"机器 A 上的浏览器"，B 页是"机器 B"。**断网 = 杀掉那个转发**，Hub 本身照常跑，
所以"B 掉线期间 Hub 上还在变"是真的，不是模拟出来的。

| 验收项 | 结果 |
|---|---|
| ① A 建会话，B 不刷新即见 | ✅ B 页 2 秒内出现该会话（走 SSE） |
| ② 完整 turn 的事件 seq | ✅ m17-beta 跑完一个真 turn：18 条事件 `seq 1..18` 无洞；另三个会话 `1..3` / `1..2` 无洞 |
| ③ B 断网后仍然陈旧（证明断的是真网） | ✅ 5 秒内出现"正在重连"横幅；期间 Hub 上新增/删除的三个会话 B 一个都不知道，且**原有行一条没丢** |
| ④ 断网满 5 分钟 → 恢复 → 靠游标补齐 | ✅ 恢复后 B 的会话集合与 Hub **完全一致**（6 条），被删的那条正确消失，无重复行（每个会话在侧栏恰好一行；另加详情页标题链接共 2 个锚点），横幅消失 |

顺带发现并修掉一个真问题：`streamEvents` 原来把"连不上 Hub"也算作"这条网络不能推流"，
两次失败后就永久放弃流，一个睡醒的笔记本从此只能靠 long-poll（不丢数据，但白白多 25 秒延迟）。
现在两种情况分开了——**连不上就继续重试**（这是暂时的），**只有 Hub 收下了请求却一个字节不发**
（CDN 缓冲）才判定为不能推流并永久降级。新增 `ui/src/api/client.stream.test.ts` 三个测试钉住这条策略。

**M1.3 的一处与原设计不同：** 设计文档说"`MAX(hub_seq)+1` 天生单调无洞，不需要额外的序列表"。
这句话漏了**删除**：删掉游标最大的那条会话，它的号会被下一个写入者重用，持有该游标的客户端
就永久看不到那次变更。所以删除时写一行 `task_tombstones`（迁移 035），它既是"这条会话没了"的
通知，也是游标的下界。墓碑永远不清理（一行几十字节），离线再久的客户端也能补齐。

## M2 — 各设备用自己的 agent 干活

目标：手机上发一个任务 → 在装了 agent 的那台桌面机上跑起来 → 过程回到手机 → 能批准/拒绝权限请求。

**内部顺序是硬性的：先用现有 adapter 把链路跑通，再把执行层换成 ACP。**
这样 ACP 出问题时有一个已知可用的对照组，而不是两个新东西同时不确定。

### 手头已经有的（先说清楚，免得重造）

盘点了一遍代码，M2 需要的东西一半已经在仓库里，只是没接线：

| Worker 协议类型：`Hello` / `Heartbeat` / `Frame`（带校验） | `internal/remote/worker/protocol.go` | 帧信封直接用。`Hello` 已改成报一份 agent 清单（M2.1 改的）；`Assignment`/`TaskEvent`/`Capability` 从没被任何代码构造过，已删 |

### 四条定死的决定

1. **控制通道是 Node 主动外连 Hub 的 WebSocket**（`GET /api/node`，用设备令牌认证），帧用现有
   `worker.Frame` 信封，按设计 §6.1 补上 `turn.*` 那几个 kind。Node 在 NAT 后面不用开端口；
   以后要挂到 relay 上（P0-E）也不用换协议。
2. **远端执行实现成一个 `adapter.Adapter`**：`Start` 发 `turn.dispatch`，返回的 handle 把
   `turn.event` 帧喂进 `Events()`，`Cancel()` 发 `turn.cancel`。Hub 侧一行引擎代码都不用改——
   这是 D8「一条代码路径」的落法，也让 standalone 与远程走完全相同的下游。
3. **秘密不过线**（D7）：`turn.dispatch` 不带 `ProviderCfg`/API key，Node 用自己的本地配置。
4. **`session_ref` 是设备本地的**：派发时按 `(device_id, agent_id)` 取那一台自己的 ref。
   M1.1 推迟的 `agent_sessions` 唯一键重建，就在这一步一次改到位。

## M2.1 / M2.2 落地细节

### M2.1 的一处结构性更正：Node 角色搬进 daemon

原计划写的是 `kin node --hub …`——一个独立的瘦客户端进程。**这是错的，已改成
`kin serve --hub URL --token TOK`。** 理由：会干活的机器本身就是一个 daemon（有自己的
state dir、自己的 agent registry、自己的 adapter），一个不持有数据库的旁路进程根本起不了
一个 turn；而且两个进程抢一个 `~/.kin` 是自找麻烦。M2.7 的验收口径本来就写着"两个 daemon
（不同 state dir）+ 一个 Hub"，现在代码和它对上了。`kin node` 命令与其解析器已删除，
不留第二条路径。

### M2.2 turn 派发

链路（一次远端 turn 的完整路径）：

```
Hub: POST /api/tasks {executing_device_id: <dev>}
  → engine.startOne：不是本机 ⇒ 用远端 adapter（本机 registry 完全不参与）
  → node.Adapter.Start：Turns.Open(turn_id) + 发 turn.dispatch（**不带 ProviderCfg**）
Node: 收 turn.dispatch
  → Executor：cwd 在自己声明的根里？不在就直接 turn.finish(error)，agent 一次都不启动
  → 起本地 adapter，事件逐条 turn.event 上行（局部 seq 从 1 开始、连续）
Hub: 每条 turn.event 走原有 runLoop → 原有 store.AppendEvent → **Hub 分配 seq**
  → turn.finish(ok) 关闭 handle → 引擎照常收尾
```

关键点：

- **Hub 侧引擎、事件落库、seq 分配、总线、游标、控制台一行没改。** 远端执行就是一个
  `adapter.Adapter`（D8「一条代码路径」），所以远端 turn 在控制台里和本机 turn 长得一模一样。
- **去重与收敛按 `(turn_id, local_seq)`**：重复序号丢弃（重连会重发），**跳号直接终结该 turn**
  并把原因写进 transcript——事件丢了就是丢了，等不回来，留着洞比失败更糟。
- **`Cancel()` 立刻关闭 Hub 侧 handle**，不等设备回话，否则引擎的并发槽会被一个没人跑的 turn
  永久占住（测试抓到的真 bug）。
- **设备身份只认凭据**：`turn.event` 只能投给它所属设备的那条 turn，另一台设备发来的同 id 帧被拒。
- **Node 侧的边界是容器边界**：`cwd` 必须落在这台机器自己声明的根里（本机 `project_roots` +
  `--root`），**没声明就什么都不跑**——空声明不能被读成"哪里都行"。判定发生在拥有文件系统的那台
  机器上，Hub 是另一方可信不过（测试含"只共享前缀的路径"和"相对路径逃逸"）。

**一处顺带修掉的真问题（e2e 测试抓到的）：** `Engine.Create` 用**本机** registry 校验 agent，
于是 Hub 会拒掉它唯一该接受的那类任务——NAS 上的 Hub 一个 agent 都没装，任务全是给笔记本的。
现在改成：任务指向别台设备时，按那台**上报的清单**（`device_agents`）判定；没上报过清单的设备
不判（交给派发去说话）；上报了的就用它的理由拒绝，比如「agent "codex" is not available on
device X: not signed in」。

**一处推迟（同 M1.1，仍记在账上）：** `agent_sessions` 唯一键重建为
`(device_id, agent_id, external_ref)` **不在 M2.2**。远端 turn 的 `syncNativeSessionBinding`
本来就该跳过——Hub 没有、也不该有另一台机器的 `SessionCatalog`/`InspectSession`。远端 turn
正确地不产生 native binding。重建随 M2.3 的按设备路径解析一起做，那时才有 `(device_id,
agent_id) → path/ref` 的解析器可写。

**怎么验的：** `internal/api` 里有一条真链路 e2e——真的 `api.Server` + 真 store + 真引擎
（**本机一个 adapter 都没注册**，本地跑必然失败）、真的 WebSocket、真的 `node.Executor`：
建任务 → 派发 → 对端跑 → 事件落 Hub 库，断言 `seq` 连续无洞、`session_ref`/token/成本都回来了、
两边都没有残留 turn。另外覆盖：越界 cwd 被拒且 agent 没启动、设备不在线、设备上报的 agent 与实际
不符、跑到一半断线必须收敛成 failed 并说明原因、建任务时未知设备 400。

### M2.2 的复审：修掉的问题与记在账上的

高模型子代理复审（1 blocker / 7 major / 8 nit）后逐条修，修完的：

1. **（blocker）Hub 在派发前把远端任务的工作区"准备"了一遍。** `Engine.Create` 原来无条件走
   `workspace.Manager`：它按 Hub 的路径 `stat` 一个只存在于笔记本上的目录，或在 Hub 上切一个
   worktree，于是远端任务在 Hub 侧直接 400，或者带着一份属于 Hub 的工作区元数据上线。
   现在：`executing_device_id` 不是本机时，工作区元数据就是"共享、cwd 即根"，准备动作交给拥有
   文件系统的那台机器。回归测试 `TestRemoteTaskIsNotPreparedOnTheHub`（关掉修复会真的红）。
2. **（major）`agent_sessions` / native binding 写错机器。** `syncNativeSessionBinding` 会把远端 turn
   报上来的 `session_ref` 绑到 Hub 自己的 agent 会话表里。现在远端任务直接跳过（与 M2.3 的重建同一方向）。
3. **（major）权限天花板只是句口号。** 派发进来的 `permission_mode=yolo` 原来照跑。现在机器自己决定：
   没带 `--allow-yolo` 就一直拒，agent 一次都不启动。
4. **（major）cwd 容器边界可被符号链接绕过。** 判定改成解析后的真实路径（`filepath.EvalSymlinks`），
   并要求绝对路径；测试补了符号链接、相对路径、前缀共享、不存在的路径。
5. **（major）turn 关闭与投递竞态会 panic。** 引擎关 handle 与设备帧投递在不同 goroutine 上，
   原来"先查再发"会打到已关闭的 channel，panic 会带走整条控制通道（连同这台机器上所有 turn）。
   现在发送有闸门 + `WaitGroup`，先亮"已关闭"再等发送者退出，最后才关 channel。并发测试跑 100 轮。
6. **（major）重连顶掉旧连接时，旧连接上的 turn 成了孤儿。** Node 侧 turn 的生命周期挂在派发它的那条
   连接上，所以被顶掉的连接的 turn 必须在 Hub 侧一并放弃，否则引擎永远等一个不存在的 socket。
7. **（major）不可解析的事件被吞。** 现在解析失败即终结该 turn 并把原因写进 transcript——序号一旦被
   消费就代表"这条事件收到了"，吞掉它等于用下一个事件盖住一个洞。
8. **（major）吊销的设备仍可被指定。** 建任务时就拒（REST / MCP / 例程三个建任务入口共用同一个校验），
   否则任务会被接受、排队，直到第一次 turn 才失败——正是那段注释说要避免的结果。

**记在账上、本轮不修的**（都不是 blocker/major，写清楚免得以后当成新发现）：

- **一台设备的帧读取会被它自己最慢的 turn 拖住**：上行事件先进每条连接 64 个槽的缓冲，缓冲满了读循环
  就停在那条 turn 上，同一台机器上其它 turn 的事件一起等。真实场景是一台机器同时跑多个 turn 且其中
  一个的消费者卡住；M2.4 做收敛与重连时会连同背压一起处理。
- **重复派发是"忽略"而不是"幂等"**：Hub 重发 `turn.dispatch` 时 Node 只是警告并忽略（不会回一个
  finish 把正在跑的 turn 打死）。真正的 at-least-once 语义（带派发代次、可安全重放）属于 M2.4。
- **一个 turn 属于"设备"，不属于"那条连接"**：设备重连顶掉旧连接时，Hub 放弃的是该设备名下所有
  turn。若在"换连接"的瞬间正好有新 turn 派发到新连接上，它会被一起误杀（窗口极小，且要两个 Node
  进程共用一个凭据才会稳定复现）。正确做法是把 turn 绑在派发它的那条连接上（`Turns.Open` 记住
  sender，路由与放弃都比对 sender）——这属于 M2.4 的收敛与重连。
- **`tasks` 的 `owner_user_id`/`origin_device_id`/`executing_device_id` 没有外键约束**：SQLite 加外键
  要重建表；而且 Hub 自己也是一个合法的 `executing_device_id`，它不一定有 `devices` 行。建任务时的
  校验已经盖住实用场景。

## M2.3 工作区锚点（2026-10-22 晚，✅ 已落地 `c8762f7` + 唯一键重建）

**要解决的问题**：`cwd` 是**一台机器上的地址**。两台机器通常在同一个路径上各有一份 checkout，
于是任何把远端任务的路径当本地路径用的地方都"看起来正确、实际动的是另一份"。M2.2 已经把四个
这样的口子堵上（见上）；锚点是把地址本身变可移植的那一层。

**落法**（尽量少加实体，不加新概念给用户）：

1. **每条根目录带上仓库身份。** Node 的 `hello` 里 `workspace_roots` 从 `[]string` 变成
   `[]{path, remote_url}`：声明的根如果在一个有 `origin` 的仓库里，报**仓库根**和**规范化后的
   remote**；否则报路径本身、remote 为空。规范化会丢掉 scheme、丢掉 userinfo（token 绝不能
   进 Hub 的库，D7）、`git@host:o/r` 与 `https://host/o/r` 收敛成同一个 `host/o/r`。
2. **Hub 落库。** `workspace_anchors`（`git_remote` / `device_path`）+ `workspace_anchor_roots`
   （每台设备一份"这个锚点在本机的绝对路径"）。hello 是快照不是日志：这台设备这次没报的根，
   连同只属于它的 `device_path` 锚点一起清掉——否则一台机器换了目录布局之后，旧路径会一直
   是"可解析"的。
3. **建任务时定锚点。** 跑在本机 → 就地 `git` 推；跑在别的设备 → 用那台设备已上报的根做匹配
   （`git_remote` 根按包含关系取子路径，`device_path` 根要求完全相等）。**那台设备报过根、
   却没有一条盖住这个 cwd → 建任务直接失败**（和 M2.2 的"设备报过 agent 清单就按清单判定"
   同一条政策：没报过的设备按原样接受，交给派发去拒）。
4. **派发时按锚点解析路径。** 任务带锚点 → 用**执行设备**的根解析出绝对路径
   （`join(根, 锚点内的相对路径)`）再放进 `turn.dispatch`；解析不到 → **明确失败并写进
   transcript**（还会列出哪几台设备有这个工作区），**不退回原路径、不换设备**。
5. **`agent_sessions` 唯一键重建**为 `(device_id, agent_id, external_ref)`（M1.1 推迟的那条）。
   原生会话绑定的完整身份从此是"哪台机器上的哪个 agent 的哪个 ref"。迁移 036 重建表（SQLite
   不能就地删 UNIQUE），schema 36。

**实际怎么落的（与上面三处偏离，都是实现时看清代价后改的）：**

- **第 3 条没有做"建任务直接失败"。** 原因是 `device_path` 根**只匹配它自己**（一个不是仓库的目录
  没有可移植身份），而 Node 的 `allowedCwd` 是**包含**判定：声明了 `/code` 这台机器的
  `/code/sub/dir` 是能跑的。按第 3 条硬失败会**误杀**这种"根的子目录"。所以建锚点是最尽力而为：
  匹配得上就记锚点，匹配不上就留空，真正的闸门是**派发时**——那台机器解析不到就明确失败
  （列出哪几台设备有），解析得到就用那台机器的地址。这样两边都不会"看起来对、动的是另一份"。
- **本机 turn 不走锚点解析。** 本机的 `cwd` 已经是本机地址；而隔离工作区（worktree / 共享克隆）的
  `cwd` 是 workspace 生命周期拥有的那份克隆，不是锚点派生自的项目路径。`dispatchCwd` 只服务
  "离开本 daemon 的 turn"。
- **`tasks.session_ref` 没换成三元组。** 三元组的完整身份落在 `agent_sessions`（`device_id` 是其
  一部分，写入点已按设备盖章）；`tasks.session_ref` 仍是"这台机器上的 ref"这一投影，因为
  真正消费它的是**本机**的 resume 路径。跨设备 handoff 是明确不做的那条，等它开工时一并换。

**迁移 036 的一个坑（已用测试钉住）**：`DROP TABLE agent_sessions` 会触发
`task_agent_sessions` 的 `ON DELETE CASCADE` —— 我第一次用 sqlite3 实测确认了这一点
（父表 drop 后子表行数从 1 变 0）。所以重建在一个**独占连接**上把 `foreign_keys` 关掉
（pragma 是每连接的，连接池里不止一个），并在事务内**前后数一遍子表行数**，不等就回滚报错，
宁可升级失败也不静默丢数据。把 `OFF` 改回 `ON` 能让测试立刻失败，非空洞已验证。

**未归位的两处（不阻塞，已记账）**：`AgentSession.DeviceID` 现在只是"记录并上行"，
控制台还没用它分组/过滤；`agent_sessions` 仍不索引**远端**会话（Hub 读不到别的机器的
agent 文件，索引了也只是空壳），远端 turn 的 ref 只写在任务的 `session_ref` 上。

### M2.3 的复审（2026-10-22 晚，0 blocker / 4 major 全修）

用恢复后的复审通道（与本会话同一个模型）审 `4cba1ce..79d018f`，结论是 0 blocker、4 major、4 nit。
四条 major 都是"看起来能解析、其实解析到别处"这一族，已逐条修掉并各带回归测试：

1. **（major）`..` 能穿过每一道闸门。** `cleanAnchorRel` 只做 `path.Clean`（保留开头的 `..`），
   `nodePathContains`/`relativeNodePath` 是纯文本前缀判定，`WorkspaceRoot.Validate` 的 `..` 检查漏掉
   了反斜杠那几种写法（`..\x`、`sub/..\..`）。于是一个 cwd `/code/repo/../x` 会被锚成
   "github.com/me/repo + ../x"，在另一台机器上解析成 `/b/repo/../x`。现在三处都改：
   `cleanAnchorRel` 对逃出 checkout 的相对路径**报错**（不再静默 clamp），
   `WorkspaceRoot.Validate` 先把 `\` 归一成 `/` 再逐段拒绝 `..`，
   `nodePathContains`/`relativeNodePath`/`sameNodePath` 共用一个 `cleanNodePath`（文本归一 + `..`
   出栈 + 爬不出去的 `..` 留在原地，于是任何包含判定都会说"不"）。
2. **（major）`device_path` 锚点每次 hello 都换 id。** `ensureAnchorTx` 对 `device_path` 每次
   `ulid.Make()` 新铸一个，上一次的根被当作 stale 删掉、锚点被孤儿清理扫掉，而
   `tasks.workspace_anchor_id` 没有外键，于是任务指向一个"查不到"的锚点，派发时报
   `workspace anchor not found` 而不是设计好的那句"它在某台机器上"。现在 `RecordDeviceWorkspaceRoots`
   先读这张设备已有的 `device_path` 锚点（一张 map），同一个 (设备, 路径) 复用同一个 id。
3. **（major）一台机器的两份 checkout 静默二选一。** 根行主键是 `(anchor_id, device_id)`，
   同一 remote 的第二个 `abs_path` 会 `DO UPDATE` 覆盖第一个；而 `git worktree` 恰好就是
   "同一 remote 的两份 checkout"。现在一次 hello 里同一个锚点被报到两个不同路径 → **两条根都不留**，
   那台机器对该仓库的解析直接失败（另一台只有一份 checkout 的机器不受影响）。宁可明确失败，
   也不把 turn 交给任务没点名的那份代码。
4. **（major）两条复制任务的路都不带工作区身份。** `Fork` 的 `dst` 字面量没写
   `WorkspaceAnchorID`（只有 `Create` 那一处会写），`/replay` 的 `rerun` 模式没带
   `ExecutingDeviceID`。前者让分支绕开锚点闸门，后者更糟：跨设备任务"再来一次"会在 Hub 上、
   按另一台机器的路径跑（同名目录存在时静默跑错代码）。现在 Fork 带上锚点（没有就地派生一个），
   rerun 带上设备。

同一轮修掉的 nit：**拒绝消息里报的是设备 id**（没人能查）→ 改成 label（没有 label 才退回 id）；
**wire 与 store 两份"规范化 remote"的规则不一致**（wire 少了开头的 `/`、`?`/`#`），
后者会让一台机器因为一条坏根被整个拒之门外 —— 两边规则对齐，并加了一条
`TestTheWireNeverAcceptsWhatTheStoreRefuses` 把"wire 接受的 store 必须也接受"钉住；

## M2.4 turn 终结与重连（收敛，2026-10-22 晚开工）

**要解决的问题**：一条 turn 可能因为**任何一方**消失而永远停在 `running`——机器被拔电、
socket 断了、Hub 重启、或者某个消费者卡住。收敛的意思是：这些情况都必须变成一个
**写进 transcript 的终结状态**，已经收到的事件一条不丢（对照 `store.FailOrphaned` 的先例）。

**已经有的（M2.2 留下的，本次只补测试不去重写）**：

- Node 掉线 →Hub 侧 `node.Turns.Abandon` 把该设备名下每个 turn 以 error 事件终结，原因写进
  transcript。
- Node 侧 turn 的生命周期挂在**派发它的那条连接的 read ctx** 上：socket 一断 ctx 就取消，
  本机 agent 被停，这个 turn 不会再产生事件。所以"Node 被 kill"和"Node 掉线"在 Hub 看来是同一件事。
- Hub 重启 → `Engine.Recover` 走 `FailOrphaned`，把 `queued` / `running` / `waiting_approval`
  落 `failed` 并追加一条 "daemon restarted" 事件。

**要做四件**（都是 M2.2 复审记账里明确推迟到 M2.4 的）：

1. **turn 绑在"那条连接"上，不是"那台设备"上。** `Connections.Attach` 顶掉旧连接时，
   `Abandon(deviceID)` 杀的是该设备名下**所有** turn——包括刚在新连接上派发的那个（窗口极小，
   但要两个 Node 进程共用一份凭据才会稳定复现）。做法：每条连接一个单调递增的 generation，
   `Turns.Open` 记住它，`Deliver` / `Finish` / `Abandon` 都比对 generation：旧连接上迟到的帧
   被拒，换连接的瞬间新 turn 不会被误杀。
2. **派发要有回执，收不到就明确失败。** 加 `turn.started`：Node 在真正起 adapter **之前**发一条；
   Hub 在 `Start` 时上表，N 秒没有回执 → 该 turn 落 `failed`（"设备没有开始这个 turn"）。
   单跳 WebSocket 上"重发"没有意义（帧要么到、要么连接断），所以 at-least-once 的诚实等价物
   就是**回执 + 超时明确失败**，不做派发代次（比"带代次的可重放"更少机制、同样的保证）。
3. **上行背压不再拖住整台设备。** 现在 Hub 的读循环会阻塞在 `item.events <- event` 上：一条 turn
   的消费者慢，同一台机器**其它** turn 的帧和心跳一起等。改成投递永不阻塞读循环：某个 turn 的
   缓冲满了 → **只终结那一条**（错误事件写进 transcript）并给 Node 发 `turn.cancel` 停掉本机
   agent。有界地失败，胜过静默丢事件或拖住心跳。
4. **Hub 重启后，Node 上还在跑的 turn 要被明确停掉。** 进程内的 turn 表随 Hub 重启消失，Node
   重连后上行的事件是"unknown turn"（今天直接丢弃，Node 那边继续跑到底、结果没人收）。改成：
   Hub 对未知 turn 的事件回一条 `turn.cancel`（"the hub is no longer running this turn"），
   Node 收到即停。配合第 1 条的落库，两边都收敛。

**验收测试**（不依赖真机，go test 全覆盖）：断开连接 → 该设备每个 turn 落 failed 且事件保留；
旧连接被顶掉 → 旧连接的 turn 落 failed、新连接的 turn 不受影响；派发后无回执 → 超时落 failed；
消费者停住 → 只终结那一条、其它 turn 与心跳照常；未知 turn 的事件 → Hub 回 cancel；
Hub 重启 → 远端 running 任务落 failed 且已收事件保留。

### M2.4 落地（2026-10-22 晚，✅）

四件都做了，落点与上面写的一致：

1. **turn 绑在连接上。** `node.Sender` 多了 `Generation()`（进程内单调递增），`connGenerations` 在
   `NewSender` 时取号；`turn` 记住派发它的 sender，`Turns.owned()` 同时比对 `deviceID` 与
   `Generation()`：旧连接迟到的 `turn.event`/`turn.finish`/`turn.started` 被拒（`turn ... belongs to
   another connection`），`Abandon(sender)` 只终结那条连接自己的 turn。`Connections.Attach` 顶掉旧连接
   时回调拿到的就是那条 sender，所以"被顶掉"和"断开"走同一个收敛路径。
2. **回执 + 超时。** 新帧 `turn.started`；Node 在**起 adapter 之前**发（`Executor.run` 第一件事），
   Hub 的 `Turns.Open` 挂上 `DefaultStartTimeout = 30s` 的定时器，收到回执就停。
   超时 → 那个 turn 以 `device X did not start the turn` 终结并写进 transcript。
   **不做派发代次/重放**：单跳 WebSocket 上"重发"没有意义，回执+超时是 at-least-once 的诚实等价物。
3. **上行不再拖住整台设备。** `Turns.push` 永不阻塞读循环：缓冲（64）满 → 该 turn 标记 overflow，

   看不到 `result`，本来就会把这次 run 判成 failed（`process exited without result`），
   所以丢的只是"原因"这一行，而那一行本来也只有那个不会回来的读者能看到。
4. **未知 turn 回 cancel。** `routeNodeFrame` 看到 `node.ErrTurnUnknown` 就按帧里的 turn id 回一条

之前显式调用（注释写明顺序是 load-bearing）。②`TestTurnsDoNotLetOneStuckReaderStallTheConnection`
一开始没有读者，宽限期一到原因就送不进去了，测试断言的"最后一条是 error"时有时无；现在测试分成两条：
一条"读者只是慢"（宽限放宽，必须读到原因）、一条"读者永远不回来"（只看 turn 是否从注册表消失、
channel 是否关闭）。

### M2.4 的复审（2026-10-22 晚，0 blocker / 1 major 全修）

两个子代理跑同一批改动（一个通读全 diff，一个专找"哪条不变式在并发下会破"）。通读的那个报
0 blocker / 0 major / 6 nits；对抗的那个报 **1 major，而且是真问题**：

> **等 socket 写权的那段等不到 ctx。** 加了"未知 turn 回 cancel"之后，Hub 的**读循环也开始写**
> （`routeNodeFrame` 回 cancel）。原来的 `conn.Send` 拿的是一把普通 `sync.Mutex`，而 `WriteFrame`
> 的 ctx 只约束写本身、不约束**排队等锁**。所以对端不读 socket 时：一条卡住的写 → 读循环
> 停在等锁上 → 这条连接再也不读、也就再也不会被 detach → 它身上所有 turn 都不收敛。
> 探针实测："a send with a 5s deadline is still blocked after 8s"。

修法：`conn.mu` 换成容量 1 的 `write chan struct{}` + `select` 抢，`ctx.Done()` 那一支直接返回
（等写权可中断）；另加 `sendTimeout = 10s`，给没带 deadline 的调用兜底。超时的写会让 nhooyr
自己 `close()` 掉 socket，而"socket 关了"是本包已经收敛得了的状态（reader 返回 → Detach →
Abandon → turn 带原因失败），所以这不是新增的失败面，是把一个卡死的状态换成已有的收敛路径。
回归测试 `internal/node/conn_test.go`（新文件）：对端 accept 后从不 read，用 4 MiB 帧占住写权，
断言 250ms-deadline 与无-deadline 两种 send 都在 2s 内返回错误。**在修前的代码上会红**
（实测等了 7.7s）。

同轮修掉的其余几条（都是 major 的邻域或 nit，但每条都是真缺口）：

| 问题 | 后果 | 修法 |

## M2.5 跨设备审批（2026-10-22 晚开工）

**问题**：agent 要权限时是 `kin approve-mcp` 往**本机 daemon** 的 loopback `/internal/approvals`
发的（`DaemonURL` 在 `internal/server/agents.go` 组装 adapter 时写死为本地）。在 Node 上这条请求落进
Node 自己的库：Hub 的控制台看不到，没人会批，一小时 TTL 一到自动过期=拒绝，而人根本不知道发生过。
用户人在 Hub 那边，所以这条请求必须过线。

**设计**：审批权仍在 Hub（ADR 0022 D1）。Node 的审批端点变成**代理**，判据是"这个执行是不是
我为 Hub 跑的那个 turn"——是就过控制通道转发，不是就照旧走本机引擎（Node 自己也是个 daemon，
本机任务不该被绕道）。

三帧（`allowedFrameKinds` + round-trip 表都要加，M2.4 的教训）：

| 帧 | 方向 | 载荷 |
|---|---|---|
| `approval.request` | ↑ | `request_id, turn_id, kind, payload, execution_{id,agent,step,model}` |
| `approval.status` | ↓ | `request_id` + 恰好一个：`approval_id` 或 `error` |
| `approval.decision` | ↓ | `request_id, decision`（approved / denied / expired） |

**为什么是三帧而不是一帧**：MCP 的 `CreateApproval` 是 15s 超时的 POST，`WaitApproval` 才是
35s 的长轮询。所以"Hub 收下了，行号是 X"必须先单独回一条，裁决再单独回一条；把两者塞进一帧就
只能二选一（要么 POST 等裁决等到超时，要么 Node 自己编 Hub 的行号）。

**定死的几条**：

1. **`task_id` 不由设备给**。设备只报 `turn_id`，Hub 用 `Turns.owned(sender, turn_id)` 反查这条
   turn 记住的 task。一台配过对的机器因此只能问**它自己正在跑的那个 turn**，问不到别人的任务。
2. **绝不自动批**。这条路径只产生 pending 行；裁决只可能来自人（控制台）或 TTL 到期（expired=拒绝）。
   `--allow-yolo` 那道闸门不动：派下来的 turn 依旧不能绕过审批。
3. **连接断了，两边同时收敛**。Node 侧所有等待者立刻失败（agent 的 tool call 报错，本机 agent 停），
   Hub 侧把该连接名下的 pending 审批以 `expired` + `decided_via=device_disconnected` 收尾——
   否则控制台会留一条一小时内谁都批不了的待办。**顺序是 load-bearing**：先结审批再 `Abandon` turn，
   这样 `Decide` 可能写的 `running` 一定发生在 run loop 写 `failed` 之前（M2.4 那条删掉活 turn 的
   bug 是同一类）。
4. **Hub 侧不加引擎钩子**。`Engine.WaitApproval` 本来就是"被裁决或过期唤醒"且非丢失的
   （`notifyApprovalWaiters` / `maybeExpire`），每 30s 一段循环就够。**bus 不能用**：它按设计会
   丢掉慢订阅者，丢一条裁决等于用户批了但 agent 没听见。
5. Node 侧不落库：没有本地行、没有本地 task 外键问题，控制台只有 Hub 那一行。

**落点**：`internal/remote/worker/approval.go`（三帧类型 + 校验）、`internal/node/approvals.go`
（Hub 侧注册表，形状照 `Turns`）、`internal/node/approvalrelay.go`（Node 侧代理）、
`internal/api`（`/internal/approvals` 两个 handler 加一条 broker 分支）、`internal/server/server.go`
（接线 + 连接结束回调里结审批）、`internal/node/turns.go`（turn 重新记住 task id，M2.4 当死代码删过）。

**不在这一步**：`ask_user_question`（用户提问）走同一条路的另一半。它有 TTL 兜底、过期返回空答案，
agent 能自己往下走，不像权限那样卡死；记在待办里。

### M2.4 复审的第二次对抗式复查（2026-10-22 深夜，1 major + 3 nit 全修）

改动落在 `799c289`，同一个模型跑了一遍对抗式复查（专找"哪条不变式在并发下会破"），报 1 major：

> **跟着派发一起到的 cancel 会被丢掉。** Hub 在"任务刚起步就被停"时是连着发 dispatch + cancel 的，
> 两帧落在同一次 read 里。而 Node 的 `run()` 是**先发 `turn.started`、再校验 cwd、再查 agent，
> 最后才 `track`**——cancel 恰好在这段窗口里被处理时，`cancel()` 查不到这条 turn，只打一行 warn
> 就返回，**没有任何"待生效的取消"记忆**。于是一个还没产出任何事件的 agent 会在用户的机器上继续跑，
> 而 Hub 已经放弃它了。探针：dispatch+cancel 背靠背 200 轮，cancel 生效 0 次；窗口下限实测 93µs。

修法不是加一张"待取消表"，而是**把注册提前到读循环里**：`dispatch()` 在起 goroutine 之前就
`track`（连 ctx 一起建好），`run()` 只负责跑。读循环是单线程的，所以"先 dispatch 后 cancel"这个
线上顺序直接变成"先注册后取消"，窗口彻底消失，也顺带让 `Owns()`（审批归属判断）在 agent 起来之前
就为真。回归测试 `TestACancelThatArrivesWithTheDispatchStopsTheAgent`：用一个可以被测试卡住的
`Runnable` 把窗口撑开，断言 cancel 之后 turn 自己结束。**在旧顺序上必红**（实测报
"cancel for unknown turn turn-1"）。

同轮修掉的（都是"同一个病、另一个出口"）：

| 问题 | 后果 | 修法 |
| --- | --- | --- |

**定死的几条**（写下来是因为每一条都对应一个真实会出问题的地方）：

1. **能力一律不上报**（`capabilities: {}`）。Kin 用的是自己这条路，不冒充 Zed；声明了不支持的东西只会让 agent 走我们没测过的分支。
2. **模型只能从 agent 自己给的选项里选**。`session/new` 之后读它返回的 models，人的选择落在 agent 自己的 selector 上——Kin 不往里塞模型名，塞了就是把一个这机器上不存在的模型发给它。
3. **`session/load` 的重放不写进 `events`**。load 会把历史再讲一遍，照单全收就是把整个会话写第二遍；用一个 `replaying` 标志挡掉，并且**如果它什么都没重放，就发一条 notice 说出来**（否则控制台看起来像是会话没了）。agent 不支持 load 却带着旧的 `session_ref` 时，也发一条 notice（第三轮复审补的：会话被换掉却不吭声，等于 agent 悄悄忘了之前干的活）。
4. **绝不自动批准**。`session/request_permission` 一律进收件箱；没有 daemon 可问、或问题没人回答，答案就是拒绝——"说不出是谁批的"从来不是批准（ADR 0022 D1）。
5. **取消的顺序是写死的**：先发 `session/cancel`，再释放这一轮的 context。反过来会先让挂着的权限桥自己答 `cancelled`，那个答案会**抢在取消通知前面**到达 agent——agent 被告知"被取消了"，却不知道是谁取消的。取消后 Kin 自己还有一道超时，因为 agent 可能根本不理会 `session/cancel`。

**写测试时抓出来的四个真问题**（每个都补了测试，都是会在生产里现形的）：

| 问题 | 后果 |
| --- | --- |

| major | **ACP 的成本是累计值，Kin 的 `usage` 是增量**。schema 原文：`cost.amount` = "Total cumulative cost for session"。上一版把它当一轮的成本发 `usage` → 每来一次 context 更新就按**会话总账**记一笔，跑得越久账越离谱；而且 `session/load` 会把整个会话再报一遍 | 花费虚高，且因为发了 `usage` 就置上 `sawUsage`，**这一轮 prompt 返回里带的真实 token 反而不再入账** | `usage_update` **一律只发 notice**：数字照显示，一分钱不记。本轮的 token 走 `session/prompt` 返回（schema 说那是"for this turn"）。payload 里带 `cost_scope: "session"`，下游读不出"这是这一轮的钱"。测试改成断言 `event.Type != "usage"` 且四种形态（无成本 / USD / 非 USD / 负数）都能过 `adaptertest.AssertEvents` |

顺带的 nit：`protocol.go` 里 `Modes` 字段删掉（Kin 不按 mode 动作，留着只会让人以为
模型可以从 mode 里取）；`adapter.go` 里"控制台已经渲染 notice"之类的措辞按事实改准；
删掉 `agentName()` 死代码与随之而来的 `path/filepath` 导入。

**教训**（值得记住）：第一轮复审修的是"会不会崩、会不会丢事件"，第二轮修的是
**"这个数字是谁的数字"**。协议的每个字段在 schema 里都写清了是累计还是增量、是整会话还是
这一轮，读文档比读测试更早发现问题。

### M2.6 的第三轮复审：1 blocker + 6 major（2026-10-23 凌晨）

这一轮复审专攻"上两轮的修法本身对不对"，结论是**两轮的修法有一条错、一条只修了一半**。
最重的一条不是崩溃，是**账**。（复审另外单列了一条"agent 只在 `usage_update` 里报用量时
账为 0"——和 blocker 同源，同一个修法一起解决。）

| 严重度 | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| **blocker** | 第二轮把记账来源换成了 `session/prompt` 返回里的 `usage`，并写下"schema 说那是 for this turn"。**但同一个 schema 里这个字段自己跟自己矛盾**：`PromptResponse.usage` 写 "Token usage for this turn"，而它里面的 `inputTokens` 写 "Total input tokens across all turns"、`totalTokens` 写 "Sum of all token types across session"；整个 `Usage` 类型还标着 **UNSTABLE**（"may be removed or changed at any point"），上游另有一个未决的 RFD（end-turn-token-usage）专门问"per-turn 还是 cumulative" | 引擎把 result 里带的 token 当**本轮增量**入账（`store.AppendUsageEvent` 是 `tokens_in = tokens_in + ?`）。一个按字段文档报累计值的 agent，跑五轮就把 1k/2.5k/4k/5.5k/7k 记成 20k——**账虚高且越跑越离谱**，还会喂给用量汇总和限额判断 | **口径没定的数字一律不进账**：`finishTurn` 不再往 result payload 里写任何 token 字段，改为发一条 notice 把 agent 报的数字显示出来（`reported_*` 字段名，写明"Kin 不记账"）。这与 `usage_update` 的处理一致：**能证明是本轮的数字才入账，证明不了就只显示**。集成测试断言 result 里没有 `input_tokens`/`tokens_in`/`cost_usd` 等字段、且 notice 带着 agent 的数字 |

| major | `plan` 事件**没有任何消费者**：ACP 是唯一发它的适配器，控制台投影没有这个 case，`Transcript.tsx` 也没有 | agent 在每一步工具调用前发的计划，用户一个字都看不到；而设计文档还写着"对齐 ADR 0018"（0018 讲的是持久化的 worker steps，不是这个事件类型） | 投影层新增 `case "plan"`：合成**一条** note（`pushNote(..., "plan", ...)`）放进流程框，后续 update 覆盖同一行（计划是边做边改的，堆一串草稿不是转录）。标记 `✓ / ▸ / ·` 表达每条的状态。设计文档那一行改对 |
| major | 预算：ACP 的 turn **既不记 token 也不记钱**（`defaultPriceModelForAgent` 没有 `acp` 分支，没钉模型时 `cost_usd` 恒为 NULL）→ 按金额的日限额对 ACP 永不触发 | 用户以为设了花费上限，实际什么都没在管 | **这是 blocker 那条修法的必然结果，也是有意的**：ACP 报的数字口径没定，进账就是记假账。转成"明确要告诉用户的事"——写进待办第 11 条（连同"限额对 ACP 不生效"），不在代码里假装它生效 |
| major | 被取消的 turn 的 usage 会**丢两次**：handle 在 `isCanceled()` 时不再推进（prompt 返回是 usage 的唯一载体），而引擎那边 run 已从 `activeRuns` 摘掉、事件一律跳过 | 用户取消一个烧了 30 万 token 的 ACP turn，账上一片空白 | **不在本轮修**：这是引擎"取消即不算账"的统一策略，对所有适配器一样，不是 ACP 引入的。记进待办 |
| major | `Retry` 删事件却保留 `usage_records`，也不回退 `tasks.tokens_in/out` | 重试一次，用量统计把同一份工作算两遍 | **不在本轮修**：既存行为、与 ACP 无关，记进待办 |
| major | agent 子进程能读到 daemon 的凭据（`KIN_NODE_TOKEN` 或 state dir 里的 token 文件），而 `POST /api/approvals/{id}/decision` **没有** `operatorOnly` | 最坏情况是 agent 自己批自己的权限请求，"人批了才动手"被绕过 | **部分是有意的**：device 主体能裁决是设计（手机就是配对设备，`clientTypeFromRequest` 专门给它 `ios:<id>`）。但**同一台机器上的 Node 凭据也能批自己**，这条记进待办（与第 8 条同一个修法：注册表层收窄子进程环境；被利用的前提是本地已能执行代码，那种情况下整台机器的状态目录都是可读的） |

顺带的 nit：控制台把 notice 画成 meta 行会切开正文/流程框（真机 agent 的 `usage_update`
若很频繁会碎——记进待办，等真机跑过再定）；`emit` 的三重防护里 `recover` 一项让"删掉
`eventsClosed` 标志"不再有测试变红（防护是纵深，最外层的 recover 才是兜底，这一点写在测试
的注释里）；`replaying` 标志在 `session/load` 失败的窗口里不会清（那个窗口以 turn 终结为界，
agent 已经答错，影响有限——记在这里，不改代码）；`rpcstdio` 包头措辞（当时只有 ACP 用它）
改成不预设"两个适配器"。

**教训（这一轮最值钱的一条）**：复审的第一件事不是读代码，是**读上游文档**。第二轮我据
schema 的一句话认定"prompt 返回是本轮的 token"，第三轮把同一个 schema 的字段逐条摊开，才发现
那句话和它自己的字段说明打架。**判据不是"文档里有一句支持我"，而是"文档里有没有一句反对我"。**

**明确不修的**（记账）：子进程继承 `os.Environ()`（`KIN_NODE_TOKEN` 在其中）——**每个适配器
都这样**，要改就在注册表层统一收窄，不属于 ACP（已记进待办第 8 条，安全相关）；
`rpcstdio.Conn.Write` 持锁写没有超时——和 droid 同形，先记账；
**ACP 的 turn 不进账本**（第三轮复审的决定，见上）——宁可显示不记账，也不记口径不明的数；
**取消的 turn 不计账**、**`Retry` 不清用量**：都是引擎既存策略，对所有适配器一致，记在待办
（第 9、10 条）。

**不在这一步**：把 droid 搬到 `rpcstdio` 上（它与 ACP 的信封确实不同，硬合会造出中间层，
记在待办里）；ACP 的 `fs/read_text_file` / `fs/write_text_file` 反向请求（现在按协议拒绝）。

`@zed-industries/codex-acp` 0.12.0（`codex-cli` 是 0.157.0）在 `initialize` 之前就退出：

```

expected `fast` or `flex`
```

即这行 `service_tier = "default"`（本机 `codex` CLI 认，0.12.0 的解析器不认）。这是**环境问题，

### M2.6 的第四轮复审：1 major + 4 nit（2026-10-23 凌晨）

### M2.6 的第五轮复审：1 major + 若干 nit（2026-10-23 凌晨）

第五轮只审"第四轮的修法本身"。结论：第四轮那条 major 确实修好了（有测试钉住），但**同一个
地方还有一扇没关的门**——而且这次不是"计划堆两行"，是**计划被抹掉**。

| 严重度 | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| **major** | `case "plan"` 是**唯一不先 `flushStream()` 的产步事件**（`tool_use` / `tool_result` / `notice` 都先收流），而 `pushNote` 的合并规则是"新 note 若与最后一条 running note 同 speaker/model 就并进去（连 key 一起改写）" | ACP 会把 prompt 回显按 `user_message_chunk` 流式发出来，那是**进程框里的一条流式 note**；一条 plan 更新正好落在它中间时——两边互相吞：plan 的文本变成半句回显、plan 的 key 被抢走，`upsertPlanNote` 再也找不到那一行，**计划从屏幕上消失且不会回来** | 两道一起上：`case "plan"` 补 `flushStream()`（与其它产步事件一致，先收流再写计划），并让合并规则**双向绕开 plan 行**（`plan-` 开头的 key 既不作为合并目标也不作为合并来源）。红验：只回退这两处，新测试立刻红 |
| nit | 计划行的身份是"在当前流程框里按前缀找"，而**一条回答会把流程框关掉**（`progressRef.current = null`），之后 plan 更新只能在**新框里另起一行**；撤回（`entries: []`）在那种情况下**完全无声** | 与第四轮同因：同一个计划在合并后的卡片里显示两行；撤回后屏幕上留着已经作废的计划 | 计划行改为**按步骤对象本身定位**（`planNoteRef` 持引用，就地改写，不管它落在哪个框里）；**新一轮（用户消息）开始新计划**——上一轮那行是历史，不再被改写。撤回时把那行改成「计划已被 agent 撤回」并把状态落回 `done`（不再闪"进行中"） |
| nit | `usageReportsNumbers` 数了 `totalTokens`，而 `reportedUsageNotice` 既没写进 message 也没进 payload | 一个只报总数的 agent 会得到「0 in / 0 out」并丢掉那个唯一的数字——第四轮刚修好的"判据与 payload 一致"在 total 上又破了一次 | total 一并写进 message 与 payload（`reported_total_tokens`）。schema 里 `inputTokens`/`outputTokens`/`totalTokens` 都是 **required**，所以"0 in / 0 out"是 agent 真报的值，不是我们编的 |
| nit | `planEvents` 的注释写着"控制台依赖 `replaces` 标志"——**控制台根本不读这个字段**（`ui/src` 里除了测试没有任何地方读它） | 与第四轮同类：注释描述了一个不存在的消费者 | 注释改成实话：控制台对每个 `plan` 事件都改写那一行，标志是留给"屏幕上同时保留多份计划"的消费者的 |
| nit | **ACP 的推理（`agent_thought_chunk`）发的是 `phase: "thought"`**，而控制台只认 `role=reasoning` / `phase=plan\|progress\|summary`（`eventMeta.isProgressMessageMeta`） | 推理被当成 **agent 的回答**画出来：一轮最后一段思维链就是"它的答复"。这是**假 agent 测不出来的那一类问题**（假 agent 只验信封，不验语义归类） | 改成全仓统一的推理形状 `role=reasoning` + `phase=progress`（kinagent、codex 都这样）；集成测试断言那段 thought 的 role/phase，控制台侧补一条"reasoning 进流程框"的测试——两侧都有测试，改坏任何一侧都会红 |
| nit | 新增的 `t("chat.progress.planCleared")` 断言**永远不会失败**：`t()` 找不到 key 时返回 key 本身，而测试和被测代码用的是同一个 `t()` | 两个语言文件少一个 key，转录里会显示 `chat.progress.planCleared` 这种点分路径，测试全绿 | 断言改成**字面值**（测试默认 locale 是 zh）；另加一个**语言文件对照测试**（`ui/src/i18n/locales.test.ts`：两种语言的 key 集合必须一致、值不能是空白）——这个测试本身也做了红验（把 en 的一个 key 改名即红） |
| nit | `web/dist` 没在第四轮改动后重新构建（`index.html` 指的还是 00:56 的 bundle，不含新字符串） | 用这棵树构建的 daemon 会把**第四轮之前的控制台**嵌进去——桌面壳里那个 major 还活着 | `npm run build` 重出（`index.html` 指向新 bundle，已确认新串在包里） |

**第五轮之后的结果**：0 blocker / 0 major。**同一条规则的收获**：这一轮和上一轮抓到的都是

### M2.6 的第六轮复审：1 major（2026-10-23 凌晨）

第六轮先给结论：**第五轮的五条修法全部验证通过**——而且不是靠读代码，是把投影模块单独打包出来
喂了**三万条随机事件序列**（plan / 回显 / 推理 / 工具 / notice / 用户消息 / result / error 的
组合），逐条检查"计划行的文本永远是计划或撤回语"、"引用还活着时最新计划一定可见"、
"同一个框里永远不会出现两条计划行"，零反例。然后抓到一条**与 plan 无关、但更严重**的 major。

| 严重度 | 问题 | 后果 | 修法 |

## 跨设备终端：Codex 与 Lody 怎么做的（2026-10-22 调研）

**Codex**（本机 0.157 的 app-server 协议；用 `codex app-server generate-json-schema --experimental` 导出，
逐条读的 schema）：

- 会话 = `thread`，一次执行 = `turn`，两者之下每个动作（消息、命令、文件改动、推理）都是 `item`；
  所有流式输出走**同一条**通知流：`turn/started` → `item/started` → `item/commandExecution/outputDelta`
  → `item/completed` → `turn/completed`。
- 终端就是其中一个 item：`process/spawn` 的原文是"在 app server 所在的那台主机上"起进程，带 PTY 尺寸；
  配套 `process/resizePty` / `writeStdin` / `kill`。**pty 属于跑会话的那台机器，不属于客户端。**
- 重连：`thread/backgroundTerminals/list|terminate|clean`——后台终端挂在 thread 上，客户端重连后能列出来再挂回去；
  另有 `thread/resume`、`thread/read`、`thread/turns/list`、`thread/items/list` 做历史分页。
- 跨机：`environment/add {environmentId, execServerUrl}`（WebSocket，可设连接超时）+ `thread/environment/connected`
  ——一个 thread 可以绑到远端 exec server 上。配对是协议的一等公民：`remoteControl/pairing/start` 返回
  `{pairingCode, manualPairingCode, expiresAt}`，`remoteControl/client/list|revoke` 管客户端。

**Lody**（`~/Workspace/works/Lody`，只读查看）：

- 会话是 Loro CRDT 文档，经它自己的云 API 同步 + E2EE（`packages/loro-streams-rpc`、`packages/e2ee-core`）。
  和我们的选择不同：我们让 Hub 当权威并独占分配 `seq`。
- 终端在 CLI daemon 里（`apps/cli/src/lib/terminal-pty-service.ts`，`@lydell/node-pty`），经**本机 unix socket**
  （`local-terminal-server.ts`）给 Electron 用；打开参数只有 `{sessionId, cols, rows}`。
  即 **Lody 的终端只在本机**，跨机器没做（它有 agent 的 machine target 概念，但没有远端终端）。
- 可借的一条原则（它 spec 里的原话）：多个 machine target 之间"没有回退"——和我们"解析不到就明确失败"一致。

**给我们的结论**：走 Codex 那条路最省。终端输出变成会话流上的 item（和 ADR 0022 D8
"远端执行就是一个 `adapter.Adapter`"同一条原则），pty 归拥有工作区的那台机器，Hub 只转发 + 分配 `seq`，
控制台不需要第二条通道，重连复用现成的游标。**一条安全边界必须先定**：远端终端比派发 turn 的洞更大
——它是不经任何审批通道的交互式 shell，所以必须是 Node 操作者自己的显式开关（如 `--allow-terminal`，
默认关），拒绝时给出理由。这件事排在 M2.3 的设备选择之后。

   droid 的信封与 ACP 不同，读循环硬合会造出一个两边都不像的中间层，所以那一步故意没做。
   要做的话是"把 droid 的读写换成 `rpcstdio.Conn`、读循环留在 droid 自己这里"，属于纯重构，
   不急。
7. **用一个真实 ACP agent 跑一次真机验收**（M2.6 残留风险）。本机 `codex-acp` 0.12.0 读不了这台
   机器的 `~/.codex/config.toml`（`service_tier = "default"` 比它认识的枚举新，`codex-cli` 已经是
   0.157.0），所以协议侧目前只有假 agent 的证据。升 `codex-acp`（或换一个 ACP agent）之后，
   照 M2.7 那套两个 daemon 的做法跑一遍，把结果补进「M2.6 落地」。
8. **子进程不该继承 `KIN_NODE_TOKEN`**（M2.6 复审记账，安全相关）。设备凭据可以从环境变量读
   （`internal/server/node.go` 的 `resolveNodeToken`：flag → `KIN_NODE_TOKEN` → state dir 里的文件），
   而**每个适配器都把 `os.Environ()` 交给子进程**（`droid`/`genericcli`/`claudecode`/`acp`…）。
   所以用 `KIN_NODE_TOKEN=… kin serve --hub …` 起的 Node，它跑的每个 agent 进程都能读到这台机器的
   设备凭据（能冒充该设备对 Hub 说话）。走 state dir 文件那条路（默认、也是 `kin hub node-token`
   的写法）不受影响。修法是在**注册表层**统一收窄子进程环境（白名单，或至少剥掉 `KIN_*`），
   不要一个适配器一个适配器地改——这是所有适配器共有的一个洞。
   **同一类的另一半（第三轮复审补记）**：`POST /api/approvals/{id}/decision` 没有 `operatorOnly`。
   device 主体能裁决是**有意的**（手机就是配对设备：`clientTypeFromRequest` 专门给它
   `ios:<设备 id>`），但这也意味着**一台 Node 的凭据可以批自己的权限请求**——"人批了才动手"
   在这条路上退化成"机器批自己"。被利用的前提是本地已经能执行代码（那时整个 state dir 都可读），
   所以按同一优先级处理：收窄子进程环境是第一刀，要不要给裁决加一道"哪类主体能批"的判断，
   留待与 owner 权限（ADR 0023）一起看。
9. **被取消的 turn 不计账**（第三轮复审记账）。取消后引擎把 run 从 `activeRuns` 摘掉、事件一律
   跳过，而 usage 只可能随 prompt 返回到达，所以一个烧了 30 万 token 才被取消的 turn 在账上是
   空白。**对所有适配器一致**，不是 ACP 的问题——要改是引擎策略（取消后仍接收一条终局 usage）。
10. **`Retry` 不清用量**（第三轮复审记账，既存）。`DELETE FROM events` 删掉了事件，但
    `usage_records` 保留（主键含 `event_seq`）、`tasks.tokens_in/out` 也不回退，所以重试会让
    同一份工作统计两遍，且旧记录指向已经不存在的事件序列。
11. **ACP 的 turn 不记钱、也不记 token**（第三轮复审的**有意**取舍，不是待修的 bug）。口径没定的
    数字不进账（见「第三轮复审」的 blocker）。后果要说清楚：**按金额的日限额对 ACP 永不触发，
    token 限额也不动**，控制台只在转录里显示 agent 自己报的数字。等上游把 `PromptResponse.usage`
    的口径定下来（`unstable_end_turn_token_usage` RFD），或真机 agent 表现出稳定语义，再决定要不要
    按轮记账。
12. **notice 会把正文/流程框切开**（第三轮复审的 nit）。一条 notice 就是一条 meta 行，会先 flush
    流式文本、再断开流程框。真机上如果 `usage_update` 很频繁，转录会被切碎。修法是在投影层按
    `kind` 合并相邻的同类 notice（`payload.kind` 已经在发），但**先要真机数据**：等第 7 条的真机
    验收跑过，看 codex-acp 到底多久报一次，再决定要不要合并。
13. **`emit` 的纵深防护里，最外层 recover 才是兜底**（第三轮复审的 nit）。删掉 `eventsClosed`
    标志测试不会变红（recover 把 panic 吞了）——这不影响正确性（能崩溃的路径已被覆盖：
    去掉整组防护即 panic，实测过），但"测试能证明哪一层"值得记一笔，别以为三条护栏各自都有测试。
    同一处还有一条**与所有适配器同形**的性质：缓冲区满时 `emit` 会阻塞，而 `finish` 在关
    channel 之前会等反向请求的 goroutine——如果读者不再排空，两边会互相等。droid / genericcli
    用的是同样的裸阻塞发送，所以是既有形状而非 ACP 引入；真出现挂死再统一改成"发送带
    select + 超时"。

14. **带 message id 的 note 在 flush 之后续写同一 id，会出现两个同 key 的步骤**（第五轮复审记账，
    既有形状，不是 ACP 引入）。条件是适配器同时打 `message_id` 和 `index`（ACP 只打 `message_id`，
    所以复现不了）：`message-<sp>-<role>-<id>-<idx>` 这条 note 在中间隔了一次 flush 之后又续写，
    会在同一张卡里出现两个同 key 的步骤。同一类的表现（React key 重复）第四轮在 `plan` 上抓到过，
    机制不同。要修的话是投影层给流式 note 一个"还在同一次流里"的判据，等真机数据。

15. **`CreateApproval` 丢回执时会多记一条"没人被问过"**（第七轮复审记账）。`approvalbridge` 把
    **所有**错误都当成"行没建"，而派发轮里 Hub 那条中继回复超过 `DefaultApprovalRequestTimeout`
    （10s）时 Node 回 502——**Hub 其实已经建了行、也已经写了规范事件**。于是转录里既有 Hub 的
    "需要你的审批"卡片，又有适配器的一条 `notice`（"the agent asked to use X and was told
    cancelled"）。窄：要正好卡在丢回执上，裁决本身不受影响，卡片也只有一张。修法不是改适配器，
    而是先定契约：**"502 算不算建过行"**——现在 `responseError` 不带状态码，客户端无从区分
    "没建" 和 "建了但回执丢了"。定了契约再让 `requestPermission` 少发/不发那一条。

### 一处结构性更正（针对 M2.1 已提交的做法）
上面 M2.1 那条里原先写的命令是 `kin node --hub …`——**一个独立的瘦客户端进程，这是错的**。
一个会干活的机器本身就是一个 daemon（自己的 state dir、自己的 agent registry、自己的 adapter），
不持有数据库的旁路进程根本起不了 turn，两个进程抢一个 `~/.kin` 也是自找麻烦。所以 Node 角色搬进
daemon：`kin serve --hub URL --token TOK [--root DIR]`，`kin node` 命令与其解析器直接删除，
不留第二条路径。M2.7 的验收口径（"两个 daemon（不同 state dir）+ 一个 Hub"）本来就该这么读。
