## 1. 要回答的两个问题

**问题一（审计 A，§12 说「属于 P0-入口」）**：跑在**节点**上的会话，PR 面板一定是空的，
而 GitHub 的观测其实不需要本地文件——只需要 `owner/repo` + 分支 + 一个凭据。
三个候选：① 节点自己观测并报上来；② 手机在开会话时告诉 Hub；③ 走 workspace anchor。
真正要先定的是**用谁的凭据**。

**问题二（`2026-10-24-p0-entry.md` §3.6 的最后两条）**：
「远端隔离 = 让 Node 拥有 workspace 层（generation / worktree / 清理），
那是独立的一层，且是 **P0b（publish 需要分支）的前置**」。

这两个问题其实是同一个问题的两半：**工作区在哪台机器上，那台机器就该回答关于它的问题。**
Hub 读不到节点的文件系统，但节点能——而且节点上跑的就是同一份 `kin`。

## 2. 决定

### 2.1 用谁的凭据：**拥有工作区的那台机器的**

- 节点上的会话，工作区是那台机器自己的 checkout。它的 `git` 凭据（credential helper /
  SSH key）和它的 `gh` 登录，是**用户的身份**；Hub 的 `gh` 是 Hub 自己的身份，
  节点的私有仓库它可能根本看不见（Hub 可能在别人的 NAS 上）。
- 于是 §8.4「Kin 不持有 GitHub token」原样成立：凭据从来不离开它已经在的那台机器。
  Kin 只是**在正确的机器上调用用户已有的凭据**，而不是搬运它。
- 这条同时回答了问题一：**候选 ①**（节点自己观测）。② 不成立——手机在通用路径下
  只知道一个目录，`owner/repo` 是那台机器上的事实；③ 是同一个答案的另一半
  （anchor 让路径跨机器可移植，但**凭据仍然按机器解析**，所以锚点解决寻址，不解决身份）。

### 2.2 谁记账：**Hub**，表不变

`pr_observations` 的主键是 `(repo, head_branch)`，本来就与设备无关。
节点查到什么就答什么（原始 `LookupResult`），**写表的是 Hub**——一个读模型、一个 SSE 源，
控制台不需要知道答案是从哪台机器来的。行上已有的 `source`（`gh` / `anonymous`）说的仍是
**用了哪一类凭据**，不是哪台机器。

`Reconcile` 的巡检集合也不新增列：一个远端任务该由谁去查，由 `tasks.executing_device_id`
决定（`store.Task.ExecutingDeviceID`，`internal/store/store.go:106-109`）。行上的 `task_id`
就是通往它的边。（审计 F 说这条边今天根本没被 `ListOpenPRObservations` 走——这次要走。）

### 2.3 谁 push / 开 PR：**同一台机器**，用户点击触发，走 Kin 的 runner

- 只有两个写动作，`git push --set-upstream origin <branch>` 与 `gh pr create`，
  与 finalize 同级：**只有用户在 diff 上显式点击才会发生**（§8.1），任何后台路径不碰写。
- 走 `internal/workspace/git.go` 的 argv-only runner（不走 shell、`GIT_TERMINAL_PROMPT=0`、
  stdout 有硬上限）与 `internal/toolpath` 解析出来的 `gh`（**不用 PATH 上的、拒绝垫片下的**，F1/F3）。
- **不替用户提交**：工作区脏 → 直接拒绝（复用 finalize 的判据口径）。
- 描述**由 agent 写**：控制台手里就有会话消息，草稿预填 agent 最后一条回复的正文，
  标题取它第一行；用户可改。Kin 只负责把文件改动清单一起摆在确认面板上。
  （不为这件事发明协议：agent 已经用自然语言写完了，再去要一份结构化回复才是多余的机器。）

### 2.4 问题二的答案：**远端隔离不是 publish 的前置**（改判，理由如下）

§3.6 那句话的推理是「publish 需要分支」。分支确实需要，但**分支不必由 Kin 造出来**：

- publish 的语义是「把这个工作区当前所在的分支放到远端」。共用工作区里，
  当前分支是**那台机器 checkout 上的事实**，随时可问（`workspace.git`），不必持久化。
- 隔离要解决的是**两个任务互相踩**，不是「有没有分支」。把它当 publish 的门，
  等于用一个大层去换一个小功能。
- 但**有一个真实的坑**：checkout 停在默认分支上时，publish 就等于「把 main 推上去」，
  而 Kin 永远不会自动做这件事。所以默认分支上的 publish **被拒绝**，并给出一条一键出路：
  在那台机器的 checkout 上 `git checkout -b kin/task/<id>/g1`（从当前 HEAD 起步，
  提交跟着走），然后照常发布。这一步是用户点的，不是 Kin 自作主张。

于是顺序反过来：**先把「工作区在哪台机器上」这条路打通（§3），publish 只是它上面的一个写动词。**
真正的远端隔离（每任务 worktree + 生成行 + 清理）仍然要做，仍然是独立的一层，
但它不再是 publish 的门，而是「同一台机器上两个会话不互相踩」那一层的事。

## 3. 形状

```
                      手机 / 桌面控制台
                             │  HTTP（守卫不变）
                    ┌────────▼─────────┐
                    │      Hub         │  pr_observations（唯一读模型）
                    │  TargetForTask   │  tasks.workspace_repo / workspace_branch
                    └───┬──────────┬───┘
        executing_device_id = 本机 │   │ = 某台节点
                    ┌────────────▼┐  │  ┌──────────────────────────┐
                    │ LocalMachine│  └─▶│  Queries.Ask（已有机制）  │
                    │  responder  │     │  fs.list … + 本次新增     │
                    └─────────────┘     └────────────┬─────────────┘
                                                     │  同一份代码
                                          ┌──────────▼──────────┐
                                          │   节点上的 Responder │
                                          │  workspace.* / pr.*  │
                                          └──────────┬──────────┘
                                    那台机器的 git / gh / 文件系统
```

**一句话**：新增的问题全部落在**已有**的「Hub 向 Node 提问」机制上（`worker.Query`，
方法名闭表，`internal/node/responder.go`）。没有新协议、没有新通道。

### 3.1 方法表新增（v1 + S1 + 本次）

| 方法 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `workspace.changes` | `{path}` | `{changes[], truncated?}` | 那个目录的实时改动清单。**就是** `ListLiveChanges` 对 `sharedWorkspace(path)` 的结果——共用工作区在 Hub 上本来也是这么读的，只是这次在那台机器上算。 |
| `workspace.tree` | `{path, dir}` | `{path, entries[], truncated}` | `ListLiveTree`，只列一层，上限沿用。 |
| `workspace.file` | `{path, file}` | `{path, content, truncated, binary?}` | `ReadLiveFile`，1MiB 上限，非 UTF-8 拒绝——与 Hub 本机同一份判据。 |
| `workspace.git` | `{path}` | `{is_git, repo?, branch?, default_branch?, dirty?, upstream?, head_oid?, reason?}` | 那台机器对这个目录的 git 事实。`repo` 是 canonical（`github.com/owner/name`，凭据已剥）。这也是**分支 chip** 与 publish 前置检查的数据来源。 |
| `git.branch.create` | `{path, branch}` | `{cwd, current}` | 表里第二个写。`git checkout -b <branch>`（从当前 HEAD 起步）。`branch` 过 `argument()` 后才成为参数；`path` 过 `resolvePath` + `withinRoots`，与 `git.checkout` 同一道闸。 |
| `pr.observe` | `{repo, branch}` | `{source, pr?}` | 在那台机器上跑一次观测（它的 `gh`，失败回落匿名），**不写库**：答的是原始 `LookupResult`。 |
| `pr.publish` | `{path, title, body}` | `{repo, branch, number, url, head_oid}` | 表里唯一的对外写。先自查（干净、非默认分支、有 GitHub remote），再 `git push --set-upstream origin <branch>` + `gh pr create`。 |

边界（每一台机器自己判，不交给 Hub）：所有 `path` 一律过 `resolvePath` + `withinRoots`
（与 dispatch 同一道闸，`internal/node/responder.go` 已有），`repo` 复用
`workspace.CanonicalRemote`，`branch`/`title`/`body` 过长度与字符检查。

### 3.2 Hub 侧路由（替换今天的「文件在别的机器上」死胡同）

今天的 `errWorkspaceElsewhere`（`internal/api/workspace.go:129`）是一句**正确但没用**的话。
它要变成一次提问。判据只有一条：`tasks.executing_device_id` 是不是本机。

| 今天 | 之后 |
|---|---|
| `GET /api/tasks/{id}/workspace/list` | 远端 → `workspace.tree` |
| `GET /api/tasks/{id}/workspace/file` | 远端 → `workspace.file` |
| （改动面板读的是生成行的 `diff`） | 远端任务没有生成行 → 新增一条**同形状**的实时读：`workspace.changes` |
| `GET /api/tasks/{id}/pr` | 远端 → 先用行上记的 `workspace_repo/workspace_branch` 读缓存（**不提问、不联网**，§8.1 的规矩不变） |
| `POST /api/tasks/{id}/pr/refresh` | 远端 → `pr.observe`（提问）→ Hub 记账 |
| （无） | `POST /api/tasks/{id}/pr/publish` → `pr.publish`（提问）→ Hub 记账 |

`workspace.git` 在**开会话时**问一次（通用路径下 Hub 只有目录，不知道仓库与分支），
结果落到 `tasks.workspace_repo` / `tasks.workspace_branch`——一列新增（可空），
让面板的读路径保持「只读缓存、不提问」。分支是活事实，所以在
refresh / publish / 巡检时会更新这一列，UI 也就能顺手把「这个会话在哪条分支上」显示出来
（P0-入口 的目标之一：开工那一刻显式化）。

### 3.3 数据模型：一列

```sql
ALTER TABLE tasks ADD COLUMN workspace_repo TEXT NOT NULL DEFAULT '';
```

`pr_observations` **不动**：主键已经是 `(repo, head_branch)`，与设备无关。

## 4. 硬编码的边界（不交给模型判断）

1. **Kin 永不自动 push**。只有用户在 diff 面板上点「发布」才会发生。
2. **不替用户提交**。脏 → 拒绝，并说清是哪个文件脏。
3. **默认分支拒绝**（否则等于一键推 main），给一键建任务分支的出路。
4. **不用 PATH 上的 `gh`**，拒绝垫片路径下的候选（F1）；git 同理（F3）。
5. **Kin 不持有 token**；凭据只在它已经在的那台机器上被使用。
6. **远端 URL 里的凭据不外流**：canonical 化已剥 userinfo（ADR 0022 D7）。
7. **写路由的守卫是 `holderOnly`**（配对手机是这台机器的完全客户端；成员账号不是）。
   这条是 §9 决策 7 留给这里定的那道门：**读**已经放开给配对设备（`githubQueryOnly`），
   **写**跟着「操作者自己的机器」走，不跟着「查询配额」走。

## 8. 风险与未验证

- **匿名配额按 IP 记**：节点做匿名读花的是**节点出口 IP** 的额度，Hub 的
  `anonymousBudgetPerHour` 看不见它。缓解：远端目标的查询由 Hub 的节奏与 floor 兜底，
  且节点路径优先用 `gh`（有凭据就不吃匿名额度）。**未实测**。
- **节点的 `gh` 可能没登录**：那就如实报「这台机器上没有可用的 gh」，
  并且**不回落成一句「没有 PR」**（§8.2：失败不写 `number`）。
- **两个控制台同时点发布**：第二个人拿到的是 GitHub 的「已存在」——如实转达，
  不吞掉，也不自动 `gh pr edit`。
- **Hub 与节点的时钟**：观测时间戳仍由 Hub 取（写库的是 Hub），节点不参与。
- **锚点在那台机器上解析不出时不去读**（复审改判，见 §9 复审第 4 条）：规则与
  `Engine.dispatchCwd` 一致——没有工作区身份才用任务创建时的路径，有锚点但解析不出就**拒绝**并把原因写在
  行上。代价是「origin 改名 / 根目录重报过、但目录本身还是那一个」这种少见情况下读会被拒；换来的是不会
  拿另一个同名检出当答案，也不会把它写进任务行。

## 9. 进度

### S1 完成（commit `d1cc76b` `9230c40` `a52b776`）

节点现在能回答三个问题（`workspace.changes` / `workspace.tree` / `workspace.file`），Hub 把远端任务的
`/source/tree`、`/source/file`、`/source/changes`、`/workspace/list`、`/workspace/file` 五个读接口转到
那台机器上。写接口仍旧 409（发布是 S4 那扇单独的门）。

**顺带修的**：`ListLiveTree` 对空目录报 `read live tree: EOF` —— 有界读取读完就返回 io.EOF，被当成
失败了。本机调用方都在刚走进去的目录上列，所以一直没暴露；远端问答会经常被问到空目录（刚建的、
内容全被 ignore 的），所以先修它（`d1cc76b`）。

**验收**（`/tmp/kin-accept.sh`，真起两个 `kin serve`：hub :7788 + node :7789，配对后直接插一行任务，
不花 agent 轮次）：15/15 通过。改动清单认得出未跟踪文件（added）与已改文件（modified）；空目录返回
空列表而不是错误；`.git` 不出现；`?path=../../etc/passwd` 被拒（400）；杀掉节点后同一请求返回
**409 + "not connected"**（说的是机器离线，不是「文件在别的机器上」）。

**红验证**：把 `RunsElsewhere` 分支去掉、把地址从锚点路径换成行里的路径，`workspace_remote_test.go` 里
四个测试同时变红，报的正是「读到了同一地址上的另一个检出」。

**过程中的两个判断**：
- 线格式类型改为协议包自己定义（`worker.WorkspaceChange` / `WorkspaceTreeEntry`），不是直接借用
  `workspace.Change`：`internal/hub` 的边界测试盯着 ADR 0025 D5（协议包不许 import 本模块任何东西），
  借用会破戒。两边各自转换，代价是十几行，换来的是「Hub 与 Node 约定的字段写在协议里」。
- 任务行的 `cwd` 不是地址。`Engine.RemoteWorkspaceCwd` 用 workspace anchor 在该机器上解析出的路径，
  解析不出来就拒绝，不回退到行里的路径（回退等于读本机同址目录）。

### S2 完成（commit `bf5a1a4` `ca7a5f8` `d8af7d3`，外加 `801ab69` 一个布局修复）

分层是「机器回答，Hub 记账，面板读账」：

1. **机器回答** `workspace.git`（`bf5a1a4`）：一条问题，回答一个目录的仓库、分支、默认分支、
   upstream、HEAD、有没有未提交的东西。全部本地读，不联网、不弹凭据；remote 走
   `workspace.CanonicalRemote` 归一成 `host/owner/name`，所以带 token 的 remote 不会有一个字节
   离开这台机器（有测试盯着 `ghp_` 与 `x-access-token` 不出现在回答里）。
   **没有 git 的机器是「回答」而不是「拒绝」**：`reason` 里写清是「没有 git」还是「这不是检出目录」——
   「这里没有检出」和「这台机器说不出来」是两件事，面板要能分开说。
2. **Hub 记账**（`ca7a5f8`）：只在**创建时刻**、只对 `RunsElsewhere` 的任务、用 5 秒预算问一次；
   问到什么写什么（空的字段不写，所以 detached HEAD 不会把已有分支抹掉），之后就是纯粹的读缓存。
   问不到（机器不在、超时、拒绝）不写、也不影响创建——远端任务照样起得来。
3. **面板读账**（`d8af7d3`）：`TargetForTask` 在本机没有生成行时回落到任务行上的记录，
   于是 `/api/tasks/{id}/pr` 对远端任务返回真实仓库与分支；控制台在目录与分支之间多一个仓库 chip
   （`github.com` 上是可点的链接，别的主机只显示名字，不给一个看着像 404 的链接）。

**验收**（`/tmp/kin-accept-s2.sh`，真起两个 `kin serve`，节点上是一个真仓库、真 origin、真分支）：12/12 通过。
创建回答、`GET /api/tasks/{id}`、`GET /api/tasks/{id}/pr` 三处都写着 `github.com/owner/app` 与
`feature/scratch`；不是检出的目录一个字都不记；节点离线时创建仍旧 201 且什么都没记。

**红验证**：remote 不归一 → 两条凭据测试变红；去掉 `r.own` → 越界测试变红；去掉默认分支读取 →
默认分支测试变红；去掉创建时的记账调用 → 创建测试变红；回落到行记录的兜底去掉 → github 包的测试变红。

**顺带修的**（`801ab69`）：手机宽度下，composer 下面那一条本来会横向滚动，但 flex 先把可压缩的
项压成 0 宽、再让它的内容画在隔壁 chip 上——模型选择器整个消失、路径压在仓库 chip 上。

1. **major｜掉队的远端行会被永远地问**：任务换过分支后，旧分支那行既不会被答也不会过期，
   时钟冻住、还占着每趟的批量名额——25 个就能把整趟饿死。修在 store：`ListOpenPRObservations`

2. **major｜没记分支的远端任务，面板一次也不会问**：机器不在时建的会话、以及 fork 出来的会话，
   `branch` 是空的，而旧规则把「没分支」当成「没有仓库可问」，于是永远停在「还没查过」。
