## 1. 切片

### P6a — 组件测试台（验收就是这一条）

- 依赖：`jsdom`、`@testing-library/react`、`@testing-library/dom`、`@testing-library/user-event`（都是 devDependencies）。
- 环境：**不把全局环境改成 jsdom**。现有 832 条测试是纯逻辑，跑在 node 环境里 3 秒结束；
  把它们全部搬进 jsdom 只是让每次提交慢几倍。组件测试用文件头 `// @vitest-environment jsdom`
  逐文件声明，另加一个 `src/test/setup.ts`（只做 `afterEach(cleanup)` 与 `matchMedia` 之类的桩）。
- 测哪三条关键路径（挑的都是「坏了只有人眼能发现」的那种）：
  1. `Sidebar` 的导入菜单：导入中两类菜单项都 `disabled`（不是点了没反应）；点 provider 那一行，
     回调收到的是**那个 provider 的 id**。
  2. `useAgentSessionImport`（`renderHook`）：两个实例共享同一个 busy；
     `importsInFlight()` 在导入开始后**同步**为真、结束后为假 —— 自动同步那一跳读的就是它。
  3. `LocalAgentSettingsSection`：`importingSessions` 为真时主按钮是「Importing…」且禁用；
     per-provider 行渲染出「Import」并回调 provider id。
- **红验证**：逐个把组件改坏（删 `disabled`、把 busy 判断反过来、把回调参数换成常量），
  确认**为对的原因**变红，再逐字节还原。这一条就是验收原话。

### P6b — 首屏预算钉住

- 目标已达标（321 kB gzip），所以这一片的产出不是「优化」，是**防止它悄悄退化**：
  `scripts/check-bundle-budget.sh` —— gzip 量入口 chunk，超过 1 MiB 就非零退出；

## 3. 风险

| 项 | 说明 |
|---|---|
| 组件测试的假绿 | 渲染测试最容易写成「断言组件渲染了它自己写的东西」。三条都断言**与输入有关的行为**（busy 与 disabled、回调参数、标签随状态变），不是快照 |
| jsdom 拖慢测试 | 用逐文件环境声明，不换全局环境；量一次 `npm test` 的耗时并记下来 |
| 删死代码删错 | 判据是「零 importer」，且删除前对每个文件再 grep 一遍全仓（含动态 import、`.md`）。`monacoSetup.ts` 就是这样被抓回来的：它是 `import "./monacoSetup";` 这种裸副作用导入，第一版扫描没认出来 |
| 预算脚本误报 | 阈值 1 MiB 是上游目标；脚本量 gzip 后的入口 chunk。若哪天入口真的变大，应当**先看它变大的原因**再决定是调阈值还是拆包 |

### P6b — 首屏预算钉住（`scripts/check-bundle-budget.sh` + CI 一步）

量的是 `web/dist/index.html` **自己点名**的文件：入口 module script 与样式表。
动态 chunk 不计入（`CodeViewer` 光它自己就 865 kB gzip，算进去这个数就没有意义）；
反过来，一个 chunk 一旦变成静态 import，它自己就会走进这个集合 —— 这正是要抓的退化。

| 项 | 实测（2026-10-26 构建） |
|---|---|
| `assets/index-BfbBf8Q6.js` | 1,149,144 raw / **319,187 gzip** |
| `assets/index-IqBsd6jZ.css` | 64,963 raw / **12,607 gzip** |
| 首屏合计 | **331,794 gzip = 预算（1 MiB = 1,048,576）的 31.6%** |

阈值是脚本里的常量（出处写在上游计划 §6），**故意不做成命令行开关**：
真要放宽，先回答「入口为什么变大」，而一个能随手调高的阈值就是个会被随手调高的阈值。

**红验证（4 条，含一条真实 fixture）**：

| 编号 | 情形 | 结果 |
|---|---|---|
| B1 | 把预算改成 1000 字节 | `First screen is 331794 bytes gzip, over the 1000 byte budget (33179.4%)`，exit 1 |
| B2 | 资源匹配规则改坏 | `names no /assets/ script or stylesheet; there is nothing to measure.`，exit 1 |
| B3 | 把入口 chunk 改名（半截构建） | `names … but … does not exist; the build is incomplete.`，exit 1 |
| B4 | 把 `index.html` 改名（没构建） | `No built console at …; Run 'cd ui && npx vite build' first.`，exit 1 |
| B5 | index 指向一个不存在的文件 | 同 B3 的提示，exit 1 |

B2 第一次跑是**假的红**：报错文本一句没有、只退 1。查下去是 `set -o pipefail` 下
`grep` 无匹配就会带着整条管道一起死，**那个 `-z "$assets"` 守卫根本走不到** ——
也就是说这段「解释为什么失败」的代码是死的，CI 里只会看到一步静默失败。
改成管道尾加 `|| true`，守卫才活了。这条是这一片真正的收获。
（B3/B4/B5 是 fixture 场景，脚本没改；`index.html` 跑完 `shasum` 与跑前一致。）

### P6d — 桌面壳接入 CI

`ci.yml` 末尾新增独立的 `desktop` job（不是一个 step）：它不需要 Go、不需要 UI 构建，
独立跑就能和 `build` 并行。三步 —— `npm ci --ignore-scripts`（`postinstall` 会去下
Electron 二进制，`tsc` 与 esbuild 都不读它；但 electron 这个包本身要装，`electron.d.ts`
是 typecheck 的输入）、`npm run typecheck`（`tsc --noEmit`，且 tsconfig 里
`strict` + `noUnusedLocals` + `noUnusedParameters` 都开着）、`npm run build`
（esbuild 打 `main.ts` / `preload.ts`，`external: ["electron"]`，不需要 Electron 运行时）。

本地把这三条按 CI 的写法跑过一遍（`npm ci` exit 0，typecheck 无输出，build 出
`dist/main.js` + `dist/preload.js`）；`desktop/.gitignore` 已经忽略 `node_modules/` 与
`dist/`，所以这个 job 的产物不会弄脏工作树。

**红验证（3 条，都按 CI 的 `--prefix desktop` 写法）**：

| 编号 | 改坏什么 | 红在哪 |
|---|---|---|
| D1 | 主进程里写一个类型错误 | `src/main.ts(7,7): error TS2322: Type 'string' is not assignable to type 'number'`，exit 2 |
| D2 | preload 里留一个没人读的局部变量 | `error TS6133: 'neverRead' is declared but its value is never read`，exit 2 —— 顺带证明 `noUnusedLocals` 真的在 |
| D3 | 一个解析不到的 import | esbuild `✘ [ERROR] Could not resolve "./module-that-does-not-exist"`，exit 1 —— 证明 `build` 那一步不是白跑的 |

诚实记一笔：这是**编译门，不是测试**。2,784 行仍然没有一条测试，
「桌面壳补测试」是另一片的事，这条只保证它还能编译、还能打包。
