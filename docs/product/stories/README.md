# 用户故事（stories）

一条故事是**一个人要完成的一件事**：新建一段对话、接着问一段对话、看它改了什么、管理对话、改默认设置。不是"改一个控件"，也不是"某个设备上的页面"。

六条故事写在同一份方案里，总览在 [`PLAN.md`](PLAN.md)。**不分阶段**：一条故事就是一次交付，做完、验收、截图、复审，再开下一条。顺序按优先级排队，不按 Phase。

参考了本地两份实现：Lody 用 24 条 journey 覆盖整个应用（`~/Workspace/works/Lody/e2e/journeys/registry.json`），Magpie 没有故事表，靠 `LESSONS.md` 累积规则再升级成 `docs/code-standards.md`（`~/Workspace/works/magpie`）。OpenKin 取中间：**故事少而厚，规则从真实缺陷长出来**。

## 六条故事

| 意图 | 故事 | 交付后用户能做什么 |
|---|---|---|
| 接着问一段对话 | `KIN-CONTINUE-001` | 找回那段对话，发下一条，必要时换 agent / 模型 / 权限 |
| 被叫回来 | `KIN-NOTIFY-001` | 离开控制台后收到原生通知，点开落到那一条 |
| 新建一段对话 | `KIN-START-001` | 任一端写一句、选好、开始 |
| 看它改了什么 | `KIN-RESULT-001` | 看改了哪些文件、打开 diff 或产物、分享 |
| 管理对话 | `KIN-MANAGE-001` | 改名、置顶、归档、删除 |
| 设置与环境 | `KIN-SETTINGS-001` | 改 agent、模型、设备、权限的默认值 |

## 开发任何功能之前

```bash
python3 scripts/stories.py new CONTINUE "一句话说清这件事" --journeys J1,J2 --surfaces mac,phone
```

它分配编号、复制模板、写进 `registry.json`、重生成 `COVERAGE.md`。然后照
[`AUTHORING.md`](AUTHORING.md) 填：选意图 → 定范围 → 列步骤 → 写各面差异 → 写验收 → 画设计稿。
填完跑 `python3 scripts/stories.py`，它会指出还缺什么（缺章节、某一步缺六项中的一项、
还是模板占位符没换）。签字后才动代码。

## 审批包

签字看的不是 Markdown 表格，是三样东西：

1. `KIN-XXX-000.md`：行为合同（步骤、六项预期、各面差异、验收）。
2. `KIN-XXX-000.figma/frames/`：**设计源**。每个界面一帧（Mac 1100×760、手机 390×844，状态和修改/收尾可用更宽的状态板），是 Figma 可导入的 SVG；不依赖网络也能打开。
3. `KIN-XXX-000.review.html`：审阅编排，不依赖网络/CDN 的单页（帧在旁边的 `.figma/frames/`），**手机可读**：单列、正文 16px、390px 不横滚、深色模式可读、不引外链，页内有粘性目录。开头是 **MECE 一节**——意图地图（这条在哪一格、别的格归谁）、job map 覆盖、设备为什么只是差异维度、不在这一条的去处、四条大小自检；然后 **Figma 帧是主体**，每一屏先放帧，帧下面写六段用户流程（起点、动作、立刻看到、慢/空/失败/断线、键盘与焦点、离开再回来），宽帧只在卡片内左右滚动；最后是要你拍板的几条，每条写推荐和代价，并给可长按复制的回复模板。先确认切法，再看帧和流程。

在手机上用 Lody 的 **Browser** 按钮打开这一页；`open` 或直接发文件也能读。页面必须带 `kin-review-format=figma-flow-v1` 标记，包含“用户流程”，并引用至少一个 `.svg` 帧或 Figma 链接。

状态从 `draft` 改成 `approved` 之前，Figma 帧和审阅页必须存在、写了编号、有 MECE 一节、带 figma-flow-v1 标记，检查器会拦。帧或流程改了要重新签。

## 怎么切才 MECE

按**意图**切，不按设备切。

- **主导轴是意图**：新建 / 接着问 / 看结果 / 管理对话 / 设置与环境，加上"离开控制台后被叫回来"。前五件覆盖控制台内的全部动作，第六件覆盖人不在控制台时的注意力入口（互斥且穷尽）。
- **设备是修饰维度，不是切分轴**。每条故事必须给 Mac 和手机各写一行差异，或者写明这一面没有这个能力、为什么。按设备切成两条故事，同一条要求就会写在两处，然后其中一处漏掉——Mac 上弹 iPhone 的底部面板就是这么来的。
- **步骤骨架用 Ulwick 的 job map**：定义、定位、准备、确认、执行、监控、修改、收尾。每件事都要经过这几段，所以按它列步骤不会漏，也不会互相重叠。
- **每一步写固定六项**：起点、动作、立刻看到、慢/空/失败/断线、键盘与焦点、离开再回来。有一项写不出来，说明这一步还没想清楚。
- **验收写成 Given/When/Then**（Gherkin），每条规则至少一个例子；想不清的记成疑问，不要假装知道。
- 故事卡只是索引（Ron Jeffries 的 3C：Card / Conversation / Confirmation）：细节在正文，验收在 Confirmation。

## 一条故事多大

- 一条 = 一件事，80–170 行。不是十个微故事，也不是整个产品。
- **一条故事就是一次交付**，不再分轮、分阶段。提交信息写 `KIN-CONTINUE-001`。
- 装不下就按意图拆成另一条故事（例如"接着问"和"看结果"分开），不要在同一条里写"先做 Mac 再做手机"。
- 反面例子：把"Mac 权限菜单"单独写成一条。它只是"接着问"里的一个控件——那种粒度会让 agent 每次都在写合同，而不是改产品。
- 反面例子：把"手机接着问"和"Mac 接着问"写成两条。同一个要求写两遍，迟早漏一遍。

判断大小合不合适，看四条：

1. 标题是一个动作，不需要"和"。
2. 一次验收走查能走完：一个人、一台设备、一件事。
3. 一次交付能做完：测试、复审、390/1100 截图都在里面。做不完，按意图拆成两条故事，不要分阶段。
4. 少于 3 步，说明它其实是别的故事里的一步，并回去。

## 一次交付多大

一次交付 = **一条故事**：一个用户能做完的动作，声明的每个面都成立。它不只是写代码：验收测试（先红后绿）、复审、390/1100 截图、提交、必要的桌面重打包都在里面。

- 合适：整条"接着问"——列表合成一份、设备 → 项目 → 对话、搜索、切换不白屏、发送、批准、改运行设置；删页面和改控件都是凑齐这件事的手段。
- 太小：只删 `/tasks`、只删两份重复列表、只做一个权限菜单。那不是一条故事，只是某条故事里的手段。
- 太大：一条故事装不下测试、复审和截图。这时按意图拆成两条故事，不是在同一条里分两轮。

## 状态

```
draft ──签字──▶ approved ──测试绿、截图看过──▶ covered
                    ▲                          │
                    └──────── failing ◀────────┘
blocked（写原因）
```

| 状态 | 意思 | 测试要求 |
|---|---|---|
| `draft` | 合同写好了，还没签字 | 不要求 |
| `approved` | 人签了字，可以开工 | 验收表里的测试文件必须存在，允许红 |
| `covered` | 验收表全部绿，截图看过 | 必须存在且提到故事编号 |
| `failing` | 回归挂了或发现新缺陷 | 必须 |
| `blocked` | 做不了 | 不要求，写 `blockedReason` |

## 一条故事怎么交付

1. 选一条 `approved` 的故事。没有别的进行中的故事。
2. 先让这条故事的验收测试红。
3. 改代码，让它绿。
4. 复审整条故事的 diff，修掉 blocker / major。
5. 拍 390 / 1100 截图。
6. 同一个提交：代码 + 测试 + 故事（补证据）+ `registry.json`（状态改成 `covered`）。
7. `./scripts/check.sh` 跑 `scripts/stories.py`：状态、编号、测试对不上就失败。

交付的是整条故事，不是一个页面、一个控件、一个面。做不完就把故事标 `failing` 写清楚，或者拆成两条故事重签，而不是把测试改松。

## 缺陷怎么变成规则（自进化）

写进 `docs/product/LESSONS.md`，不写进故事正文：

1. 记一条：日期、发生了什么、为什么没拦住、证据（提交或截图）。
2. 同一模式再次出现，`seen` 加一。
3. **第三次出现**，升级成 `TASTE.md` 的规则或 `AGENTS.md` 的硬规定，并补一个测试。
4. 没满三次的，写进相关故事的 `Do not`，不升级。

Magpie 就是这么做的：每晚复盘当天合并的提交，从"又被修了一次"的地方长规则，看满三次才进 code standards。规则因此是证据的副产物，不是开会想出来的清单。

## 和 IA / TASTE 的关系

- `IA.md` 说：哪个面归谁，列表什么层级。
- `TASTE.md` 说：所有面长什么样。它靠 LESSONS 慢慢加，不靠每次重写。
- `PLAN.md` 说：六条故事、顺序、不做的。
- 故事说：这件事必须发生什么，怎么证明。

故事只写这件事特有的东西；凡是所有面都该遵守的，属于 TASTE，不重复写。

## 目录

- `PLAN.md` —— 一份方案：六条故事、顺序、共用的规则、不做的。
- `_TEMPLATE.md` —— 骨架，复制它开始（`new` 会替你复制）。
- `_REVIEW.html` —— 审阅页骨架：Figma 帧为主体、每屏六段用户流程，不依赖网络的单页，带 `figma-flow-v1` 标记。
- `AUTHORING.md` —— 怎么写：六步、签字前 12 问、检查器会拦什么。
- `registry.json` —— 机器读的索引，状态的唯一真相。
- `COVERAGE.md` —— 脚本生成，不要手改。
- `KIN-CONTINUE-001.md` —— 接着问一段对话，Mac 和手机（`approved`）。
- `KIN-CONTINUE-001.review.html` —— 它的设计草图，审批看这一页。
- `KIN-NOTIFY-001.md` —— 离开时被叫回来（原生通知），Mac 和手机（`approved`）。
- `KIN-NOTIFY-001.review.html` —— 它的审阅页：Figma 帧 + 每屏用户流程，审批看这一页。
- `KIN-NOTIFY-001.figma/` —— 它的设计源帧（SVG，Figma 可导入；含状态板和决策板）。
- `KIN-START-001.md` —— 新建一段对话，Mac 和手机（`draft`）。
- `KIN-RESULT-001.md` —— 看它改了什么，Mac 和手机（`draft`）。
- `KIN-MANAGE-001.md` —— 整理一段对话，Mac 和手机（`draft`）。
- `KIN-SETTINGS-001.md` —— 改默认设置，Mac 和手机（`draft`）。
- `../LESSONS.md` —— 教训台账，规则从这来。
