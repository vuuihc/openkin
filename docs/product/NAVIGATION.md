# 导航契约：一个面，一条返回路径

状态：**draft（待签字）** · 建立 2026-11-10
配套：[`IA.md`](IA.md)（谁拥有哪个概念）、[`TASTE.md`](TASTE.md)（视觉规则）、[`stories/KIN-CONTINUE-001.md`](stories/KIN-CONTINUE-001.md)（列表合并）

## 0. 一句话

手机上有三个导航面（底部 dock、K 抽屉、页面列表），同一条「左缘右滑」被写死成「开抽屉」，所以它不是返回。这份文档把「每一页保留什么、怎么进、怎么出」写成一张可测的表；代码照表收敛，不再逐版打补丁。

## 1. 一条真实路径

从一段对话回到对话列表，现在要走五步：

```
对话 /tasks/:id → 左缘右滑 → 抽屉（又一份列表）→ 点「例行任务」
→ 抽屉关掉、落到例行任务页 → 点底部 dock「会话」→ 列表
```

期望是一步：**左缘右滑 = 返回**。这不是手势偏好，是模型缺失：侧滑被绑定在「抽屉」这个控件上，而不是「返回」这个动作上。

## 2. 现状：三个导航面

| 面 | 装什么 | 怎么打开 | 什么时候在 |
|---|---|---|---|
| 底部 dock（`MobileDock`） | 会话 / 例行任务 / 项目 三个地方 + 新建 FAB | 常驻 | 非详情路由、非草稿 |
| K 抽屉（`Sidebar` 的手机形态） | **完整对话列表 + 搜索** + 底部目的地 | 点左上角 K，**或左缘右滑** | 所有路由，包括对话里 |
| 页面列表（`SessionsPage`） | 对话列表（手机目前两层） | dock「会话」 | 会话地方的根 |

三者都在做「去哪儿」；侧滑又只认第一个。于是同一个手势在不同页面含义不同，而代码里没有任何一处定义「返回」。

已有的返回机制只覆盖浮层：`lib/backStack.ts` 管理 sheet 之上的层，浏览器 Back 先关层。**页面与页面之间没有同样的契约**——`navigate(-1)` 只在草稿页的关闭按钮里出现过一次。

## 3. 规则（每条都要有测试）

| # | 规则 | 反例（现在会发生的） |
|---|---|---|
| R1 | **只有一份对话列表**：`SessionsPage`；抽屉里不许有列表和搜索 | 抽屉里是第二份列表（IA D3 已签字，未落地） |
| R2 | **每个面只有一个父级**；「返回」= 弹出一个面。浏览器返回、系统返回、左缘右滑、页头返回按钮，四者同一行为 | 侧滑开抽屉；页头返回和手势各走各的 |
| R3 | **左缘右滑永远是返回**，永远不开抽屉 | 在对话里侧滑，弹出抽屉 |
| R4 | **抽屉只由显式控件打开**（K），且是一个「层」：任何导航都关掉它，Back 先关它 | 侧滑开抽屉；开着抽屉点目的地后状态残留 |
| R5 | **dock 是顶层**；一个地方的根页面，返回 = 回到上一个地方（没有上一个就退出），不是回到某个列表 | 从例行任务「返回」掉进会话列表 |
| R6 | **浮层在面之上**：Back 先关浮层，再弹面（沿用 `backStack`） | — |
| R7 | **深链冷启动要合成父级**：直接打开 `/tasks/:id`，返回必须落到列表，而不是无路可走或跳出应用 | 冷启动进对话后，Back 直接退出 |
| R8 | **新增导航面必须改这张表**；没有表里的行，不许上线 | — |

R2 的实现建议：不要在每个页面各写一个 `navigate(-1)`，而是让「面」进 history（现在的路由已经如此），手势和按钮都调用同一个 `goBack()`，由它决定「弹面 / 关层 / 退出」。

## 4. 每一页保留什么

「父级」= 返回会去哪儿；「不该出现」= 这一页上不允许有的东西（新增控件前先查这一列）。

| 路由 | 面 | 保留什么 | 父级 | 侧滑 | 不该出现 |
|---|---|---|---|---|---|
| `/sessions` | 会话地方的根 | 唯一一份列表（设备 → 项目 → 对话）、搜索、收件箱/归档入口 | 上一个地方 / 退出 | 无（根） | 第二份列表；抽屉里的列表 |
| `/tasks/:id` | 一段对话 | 消息流、输入框、运行设置底部面板 | `/sessions`（来处） | 返回列表 | **dock**；抽屉；第二份列表 |
| `/new` | 新建对话 | 选 agent / 模型 / 项目、输入框 | 来处（有 history）否则列表 | 返回来处 | dock |
| `/inbox` | 收件箱 | 待处理卡片 | 会话地方的根 | 返回 | 第二份列表 |
| `/routines` | 例行任务地方的根 | 机器选择、列表、run-now | 上一个地方 / 退出 | 无（根） | 对话列表 |
| `/projects` | 项目地方的根 | 项目列表 | 上一个地方 / 退出 | 无（根） | 对话列表 |
| `/projects/:id` | 项目详情 | 项目信息、会话入口 | `/projects` | 返回 | dock |
| `/artifacts` | 产物库 | 产物列表 | 会话地方的根 | 返回 | — |
| `/artifacts/:id` | 产物详情 | 内容、分享 | `/artifacts` | 返回 | dock |
| `/agents` | Agent 运维 | 机器、agent、用量 | 会话地方的根 | 返回 | — |
| `/settings` | 设置 | 全部设置分区 | 会话地方的根 | 返回 | — |
| `/agent-sessions/:id` | 外部会话 | 会话内容 | `/sessions` | 返回列表 | **dock**；抽屉 |

「保留什么」一列只写**这一页拥有的概念**；同一个概念在别处出现就是重复。未核实的格子标「待核」，review 时逐行过。

## 5. 待定的决策

| # | 决策 | 建议 | 取舍 |
|---|---|---|---|
| D1 | 手机还留不留抽屉？ | **留，但只作为 K 菜单**：导入、归档、产物库、例行任务、Agent 运维、设置等入口，没有列表、没有搜索、不可侧滑打开 | 删掉更干净，但 K 是现在唯一能放「低频入口」的地方；删了要另找位置 |
| D2 | 对话是「压在列表上」还是「替换列表」？ | **压在列表上**（现在路由就是这样），返回必然回到列表 | 替换会让返回落到上一个地方，和用户预期不符 |
| D3 | 地方的根再返回，回到哪儿？ | 回到**上一个到过的地方**；没有历史就退出 | 固定回会话列表更好预测，但会把「项目 → 返回」变成绕路 |
| D4 | iPad（≥768 宽、触屏）算手机还是 Mac？ | **算 Mac 的布局 + 手机的返回**：没有抽屉侧滑，但手势仍是返回 | 现在 iPad 有抽屉侧滑（`pointerType` 判断），是同一处混乱的来源 |

D1–D4 用语言定即可，不需要画图。

## 6. 顺序

上一轮把 Tailwind 4 排在前面；这份契约改变了顺序——**模型先于底座**：

| 轮次 | 内容 | 为什么 |
|---|---|---|
| N0 | 本文件签字（D1–D4） | 一条规则不写清楚，后面每一轮都会再发明一次 |
| N1 | 侧滑 = 返回；详情页不许开抽屉；抽屉改为层 | 小改动，直接消灭第 1 节那条五步路径；每条规则配一个 DOM/浏览器测试 |
| N2 | 交付 `KIN-CONTINUE-001` 的列表合并（R1、R5） | 已签字的故事，按新契约落地 |
| N3 | Tailwind 4（~2 天） | 技术底座，和导航解耦 |
| N4 | G0.5：Astryx 两页验证 | **必须排在 N0 之后**：`AppShell` 自带「sideNav + 移动抽屉 + 汉堡」的导航假设，模型没定就采用它，等于把现在的乱复制一遍；若 D1 选「无抽屉」，我们只能用它的 `Layout`/`Stack`/`Grid`，不能直接用 `AppShell` |

## 7. 怎么防止再腐烂

- 每条规则一个测试，写进对应 story 的验收表：R2/R3 → 手势与浏览器返回；R4 → 抽屉开合；R5 → 根页面返回；R7 → 冷启动深链。
- 新增页面或导航控件，先改 §4 的表，再写代码；表里没有的行就是没定义。
- 每轮结束时只改两处：§2 的现状表、§4 的行。
